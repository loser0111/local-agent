### 🟡 表现一般的部分

**7. 秒杀扣库存（4/10）**

面试官问：携程秒杀扣库存怎么实现的？

**你的回答：**
> 预热库存写 Redis → 查 Redis 库存够不够 → 加全局 Redis 锁 → 写 DB 扣减 → 更新 Redis。

**面试官的质疑（关键）：**
> "为什么不直接 Redis 扣减库存？你加锁扣 DB，性能瓶颈很大，行锁竞争激烈，秒杀场景几万用户下单失败。"

**问题分析：**
- 你的方案是"Redis 查库存 + Redis 锁 + DB 扣减"——这确实不是秒杀的最优方案。
- 标准秒杀方案应该是：**Redis 原子扣减（DECR/Lua）→ 扣减成功即下单成功 → 异步 MQ 更新 DB**。
- 你把性能瓶颈放在了 DB 行锁上，面试官指出"没有利用 Redis 高性能"。
- 你承认"只是看了一下机票产线同学的代码，没有实际接触过"——诚实但暴露了经验不足。

**正确方案：**
```
秒杀请求 → Redis DECR 原子扣减
  → 库存 > 0 → 下单成功 → 异步 MQ 发消息 → 消费者更新 DB
  → 库存 ≤ 0 → 直接返回"已售罄"
```
- Redis 原子扣减无锁竞争，性能极高。
- DB 更新异步化，不影响用户下单响应。
- DB 最终一致，兜底对账。

**评分：4/10** — 方案不是最优，被面试官指出性能瓶颈，且承认没有实际经验。

### 🟡 中优先级

**4. Redis 哨兵原理**
- 心跳检测：哨兵定期向主/从发 PING，超时（down-after-milliseconds）标记主观下线（SDOWN）。
- 客观下线：超过 quorum 个哨兵都标记 SDOWN → 标记 ODOWN。
- 选举新主：从节点优先级 → offset 最大（数据最新）→ runid 最小。
- 客户端感知：哨兵通过 pub/sub 通知客户端新主地址（不是"写失败查从节点"）。

**5. 规则引擎选型**
- 被问 Java 方案时不要只说内部组件，要提业界通用方案：Aviator / QLExpress / Groovy / Drools。

**6. HR/薪酬领域**
- 如果面 HR 系统岗位，提前了解：薪酬计算（基本+绩效+补贴-社保-公积金-个税）、多国差异化、汇率快照。
