# RAG 全流程指南：环节、问题、方案与取舍

> 按**数据流**顺序讲解 RAG 的每个环节：**解决什么问题 → 有哪些方案 → 优劣对比**。
>
> ⚠️ **时效说明**：涉及具体模型型号/榜单排名（embedding、reranker）的部分**会随时间过期**，请以选型时的最新榜单（如 MTEB）为准。架构与方法论部分是结构性的，不易过时。

---

## 零、全景：RAG 只有两个阶段

RAG 本质就两半，**边界是「索引是否已经建好」**：

```
【离线·索引期】只跑一次 / 定期跑
  数据接入 → 解析 → 切块 → 元数据增强 → 向量化 → 建索引 → 入库
                                                          │
【在线·查询期】每次提问都跑                        ┌──────┘
  查询理解/改写 → 检索 → 重排 → 上下文组装 → 生成 → 校验 → 评估
```

**关键认知**：绝大多数「RAG 效果差」的问题，根因在**索引期**（解析烂、切块烂），但大家习惯性去调**查询期**（换 embedding、加 reranker）。**先把左边修好，右边才有的调。**

---

## 一、数据接入（Ingestion）

**解决什么问题**：知识散在 PDF、网页、Confluence、数据库、代码库里，得先「搬」到一起。

| 方案 | 优点 | 缺点 |
|---|---|---|
| 手动上传文件 | 简单、可控 | 不 scale，无法保持最新 |
| 连接器（Confluence/Notion/Drive/Slack 官方 API） | 自动化、能带权限信息 | 每个源都要单独适配 |
| 爬虫（网页） | 覆盖公开信息 | 噪音大、格式乱、易失联 |
| CDC / 数据库直连 | 结构化数据最准 | 需要 schema 理解 |

**最容易踩的坑**：**权限同步**。企业场景里，检索出来的内容必须按「提问者有没有权限看」过滤——这是**索引期**就要打进去的元数据，事后补不回来。Onyx（原 Danswer）这类项目主要卖点就是这块。

---

## 二、文档解析（Parsing）

**解决什么问题**：PDF/PPT/扫描件是「给人看的」，不是给机器读的。这一步把二进制变成**保留结构**的文本。

这是**整条链上最被低估、性价比最高的一环**。

| 方案 | 代表 | 优 | 劣 |
|---|---|---|---|
| 纯文本抽取 | PyMuPDF / pdfplumber / pypdf | 快、免费 | 表格/双栏/公式全乱，扫描件直接空 |
| 布局感知解析 | **Docling**(IBM)、**MinerU**、**Marker**、unstructured、LlamaParse | 表格、多栏、版面还原好 | 慢、吃资源、需要调参 |
| OCR | Tesseract / PaddleOCR / 云 OCR | 扫描件唯一解 | 错字、慢、版面丢失 |
| **VLM 直接读** | GPT-4o / Gemini / Qwen-VL 直接喂图 | 效果天花板最高，公式/图表都能懂 | 贵、慢、不可控 |

> **RAGFlow 的 92k star 主要就赢在 DeepDoc 这一层**——它的文档解析是真下了功夫的。如果你手上是大量扫描版合同/研报，解析层选型比后面所有环节加起来都重要。

**经验**：解析质量决定了**召回上限**。解析丢了的内容，后面再强的 embedding 也找不回来。

---

## 三、切块（Chunking）

**解决什么问题**：LLM 上下文有限，且**检索粒度要匹配问题粒度**。一个 100 页的 PDF 不能整篇检索，切成句子又丢上下文。

这是**最「玄学」但影响最大**的环节。

| 方案 | 做法 | 优 | 劣 |
|---|---|---|---|
| 固定长度 + overlap | 按 512 token 切，重叠 50 | 简单、可预测 | 常从句子中间切断，语义破碎 |
| 递归字符分割 | 按 段落→句子→词 逐级切（LangChain 默认） | 尽量在自然边界切 | 仍不理解语义 |
| 结构感知 | 按 Markdown 标题 / HTML 层级切 | 保留章节语义，元数据天然好 | 依赖解析质量 |
| 语义切块 | 相邻句子 embedding 相似度骤降处断开 | 块内语义内聚 | 慢、贵、边界不稳定 |
| **父子块**（small-to-big） | **用小块检索、返回大块** | 兼顾检索精度与上下文完整 | 存储翻倍、需维护映射 |
| **Late Chunking** | 先整篇过 embedding 再切，块向量带全文语境 | 解决「代词指代丢失」 | 依赖长上下文 embedding 模型 |
| 命题化（Proposition） | LLM 把文本改写成原子事实句 | 检索极准 | 成本爆炸、信息损失 |

**核心权衡**：

```
块小 → 检索准（向量不被稀释），但上下文残缺、答案拼不起来
块大 → 上下文全，但向量被平均化、检索变模糊、噪声进 prompt
```

**建议**：默认从**结构感知 + 父子块**起步。它在「检索用小块、生成用大块」这个最实用的模式上，收益/复杂度比最好。

## 四、元数据与增强（Enrichment）

**解决什么问题**：光靠语义相似度不够——你还需要**过滤**（时间、权限、部门）和**额外召回线索**。

| 增强项 | 作用 |
|---|---|
| 来源/时间/作者/权限 | **硬过滤**，也是合规底线 |
| 章节路径（H1>H2>H3） | 给块补上下文，也让模型知道「这属于哪节」 |
| LLM 生成的摘要 | 用摘要做检索比原文更准 |
| **假设问题**（反向生成该块能回答的问题） | 缩小「问题↔文档」的表达鸿沟，召回提升明显 |
| 关键词/实体 | 喂给 BM25，增强混合检索 |

**优劣**：LLM 增强效果实打实，但**成本和索引时间是数量级的增加**。建议只对高价值文档做，或者用便宜小模型做。

---

## 五、向量化（Embedding）

**解决什么问题**：把文本映射到语义空间，让「意思相近」能算出来。

| 类别 | 代表（**会过期，需查最新榜**） | 优 | 劣 |
|---|---|---|---|
| 商业 API | OpenAI text-embedding-3、Cohere embed v3/v4、Voyage、Gemini | 开箱好、免运维 | 按量付费、数据出境、有速率限制 |
| 开源（可本地） | BGE-M3、GTE、E5、Nomic、Qwen3-Embedding、Jina | 免费、数据不出域、可微调 | 要自己扛算力、效果看调优 |
| 多语言 | BGE-M3、multilingual-e5 | 中英混排友好 | 单语言效果略逊专用模型 |
| 学习稀疏 | SPLADE | 可解释、能当关键词用 | 生态较小 |
| 多向量/晚交互 | ColBERT | 精度高、细粒度匹配 | 存储爆炸（每 token 一个向量） |

**关键注意**：
- **索引和查询必须用同一个 embedding 模型**，换模型 = **必须全量重建索引**。这是选型时最贵的锁定。
- **维度不是越高越好**：1024 维通常够，过高增加存储和检索成本。
- 领域专有（医疗/法律/内部黑话）时，**微调 embedding 的收益常大于换更大的模型**。

---

## 六、索引与存储（Vector Store）

**解决什么问题**：几十万到几十亿向量里，毫秒级找最近邻。

| 方案 | 定位 | 优 | 劣 |
|---|---|---|---|
| **FAISS** | 库（不是服务） | 极快、免费、灵活 | 无持久化/无过滤/无并发，得自己包 |
| **Chroma** | 轻量 | 上手 5 分钟、适合原型 | 规模化弱 |
| **Qdrant** | 专用向量库 | 过滤强、Rust 快、易部署 | 生态比 ES 小 |
| **Milvus** | 分布式 | 十亿级、功能全 | 运维重、组件多 |
| **pgvector** | Postgres 扩展 | **和业务数据同库、有事务、SQL 过滤** | 超大规模型能不如专用库 |
| **Elasticsearch / OpenSearch** | 搜索引擎 | **BM25+向量一体**，混合检索天然 | 向量性能不如专用库、贵 |
| **LanceDB** | 嵌入式 | 列存、适合多模态 | 较新 |
| **Neo4j / 图库** | 图 | GraphRAG 必备 | 和向量库是两套东西 |

**选型心法**：
- 数据 < 100 万条、想要省事 → **pgvector**（如果本来就有 PG）或 Chroma
- 要混合检索、已有 ES 栈 → **ES/OpenSearch**
- 大规模、独立演进 → **Milvus / Qdrant**

> **反直觉的建议**：**别为了 RAG 单独上一个向量数据库**。如果你已有 Postgres，pgvector 起步能省掉一整个运维面。等真的撑不住了再换。

---

## 七、检索（Retrieval）

**解决什么问题**：把「用户那句话」变成「库里最相关的 k 个块」。

| 方案 | 原理 | 优 | 劣 |
|---|---|---|---|
| 稠密向量 | 语义相似 | 懂同义、跨表达 | 专有名词/编号/精确匹配弱 |
| 稀疏 BM25 | 词频统计 | 精确匹配强、可解释、零训练 | 不懂同义词 |
| **混合检索 + RRF** | 两路各取 top-N，用 RRF 融合排名 | **几乎总是优于单路**，工程简单 | 要维护两套索引 |
| 查询改写 | LLM 把口语化问题改写成检索式 | 弥合表达鸿沟 | 多一次 LLM 调用、可能改歪 |
| 多查询（Multi-Query） | 生成多个变体分别检索再合并 | 提升召回 | 成本×N |
| **HyDE** | 先让 LLM 编一个「假答案」，用它去检索 | 短问题提升明显 | 幻觉会污染检索方向 |
| 自查询 Self-Query | LLM 抽出过滤条件（时间/部门） | 结构化+语义结合 | 需 schema 定义 |
| 图检索 GraphRAG | 沿实体关系走 | **「全局性/总结性」问题唯一解**（如「这批文档的主要争议是什么」） | 建图贵、更新难 |

**最重要的一条**：**先上混合检索 + RRF**。这是投入产出比最高的一步，很多时候做完就不用折腾别的了。

---

## 八、重排（Reranking）

**解决什么问题**：向量检索是「**双塔**」——query 和 doc 各自编码，没交互，快但粗。重排用「**交叉编码**」让 query 和 doc 逐 token 交互，**精但慢**。所以：**粗筛用向量（召回 50~100），精排用 reranker（留 3~5）**。

| 方案 | 优 | 劣 |
|---|---|---|
| Cross-Encoder（bge-reranker、Cohere Rerank、Jina Reranker） | 精度提升显著，成熟 | 延迟增加（几十~几百 ms） |
| ColBERT 晚交互 | 精度高、可预计算 | 存储大 |
| LLM-as-reranker | 最灵活、可解释 | 贵、慢、不适合大候选集 |
| 不加 reranker | 零成本 | 精度差一截 |

**注意**：reranker 是**唯一一个「加了基本不会变差」的环节**——只要控制好候选集大小。但它是**纯延迟成本**，实时性要求高的场景要权衡。

---

## 九、上下文组装（Context Assembly）

**解决什么问题**：reranker 选出 10 个块，但全塞进去会爆 token、还会因噪声降低质量。

| 手段 | 作用 |
|---|---|
| 截断到 token 预算 | 硬约束 |
| 去重（同一文档多块） | 省 token |
| **重排顺序** | LLM 有 **「lost in the middle」** 效应——**最相关的放头尾**，别放中间 |
| 上下文压缩（LLMLingua 等） | 省 token，但可能丢信息 |
| 带引用标注（[1][2]） | 让模型能溯源，也方便你验证 |

---

## 十、生成（Generation）

**解决什么问题**：基于给定上下文回答，**不能自由发挥**。

| 要点 | 做法 |
|---|---|
| Prompt 约束 | 「只依据给定上下文回答，没有就说不知道」 |
| 引用强制 | 要求标出依据的块编号 |
| 拒答机制 | 检索结果相关性低于阈值 → 直接说不知道 |
| 结构化输出 | JSON / schema，方便下游 |

**核心矛盾**：模型天然倾向「编得像样」，而非「老实说不知道」。**拒答阈值**是控制幻觉最有效的一个旋钮。

---

## 十一、评估（Evaluation）—— 最容易被跳过，也最该做

**解决什么问题**：**没有评估，你就是在盲调**。你改了切块参数，怎么知道是变好还是变坏？

**分两层评**（这点很重要，能定位问题出在哪）：

| 层 | 指标 | 含义 |
|---|---|---|
| **检索** | Recall@k、Precision@k、MRR、NDCG | 「该找的找到了吗」 |
| **生成** | Faithfulness（是否忠于上下文）、Answer Relevancy、Context Precision/Recall | 「答得对不对、有没有编」 |

| 框架 | 优 | 劣 |
|---|---|---|
| **RAGAS** | RAG 专用、指标齐全、社区大 | 部分指标依赖 LLM 裁判，有成本 |
| TruLens | RAG 三元组（context/groundedness/answer） | 生态略小 |
| DeepEval | 类 pytest 体验、CI 友好 | — |
| Phoenix (Arize) | 可视化强、可追踪 | 偏观测 |
| LangSmith | 和 LangChain 一体 | 绑生态 |

**定位心法**：
- **Recall 低** → 问题在解析/切块/embedding（**索引期**）
- **Recall 高但答案差** → 问题在重排/组装/生成（**查询期**）

合成测试集（用 LLM 从文档反向生成 QA 对）能让没标注数据的团队也跑起评估。

---

## 十二、Agentic RAG

传统 RAG 是**一条直线**：检索一次 → 生成。Agentic RAG 把它变成**循环**：

| 模式 | 做什么 |
|---|---|
| 查询路由 | 先判断「这问题该查哪个库/要不要查库」 |
| 多轮检索 | 检索→看→不够→换词再检索 |
| Self-RAG | 自我批判：检索到的够不够？答得对不对？ |
| CRAG | 检索质量差时触发「纠正」（重写查询/上网搜） |
| 工具化 | 把检索当成一个 tool，由模型决定何时调 |

**优劣**：
- **优**：复杂问题（多跳、需要整合多文档）效果好得多
- **劣**：延迟×N、成本×N、**不可控**（可能绕圈、可能不检索就答）

**建议**：**先用好传统 RAG + 评估**，确认瓶颈真的在「单次检索不够」时，再上 agentic。多数场景下，把切块和混合检索调好，比上 agentic 收益更大且更便宜。

---

## 十三、常见失败模式速查

| 症状 | 最可能的原因 | 该修哪 |
|---|---|---|
| 该找到的找不到 | 解析丢内容 / 块切碎 / embedding 不适配领域 | **索引期** |
| 找到了但答非所问 | reranker 缺失 / 噪声块进 prompt | 查询期 |
| 答案编造 | prompt 约束弱 / 没有拒答阈值 | 生成期 |
| 长文档问题答不好 | 块太小、上下文断裂 | 切块（父子块） |
| 全局总结类问题全错 | 用了向量检索解「总结题」 | 换 GraphRAG |
| 专有编号/型号搜不到 | 只用向量、没 BM25 | 加混合检索 |
| 效果时好时坏 | **没有评估集**，在盲调 | 先建评估 |

---

## 十四、一句话收束

RAG 的**权重分配**大概是：

- **解析 + 切块占 50%**（决定上限，且最难返工）
- **检索策略（混合+重排）占 30%**
- **生成与 prompt 占 20%**

而**评估是贯穿始终的地基**——没有它，上面全是玄学。

**选型通用原则**：别一上来就堆最新最贵的组件。先用下面这套**朴素组合**跑通、建立评估基线：

> Docling 解析 + 结构感知父子块 + BGE-M3 + pgvector + 混合检索 + bge-reranker

然后**用评估数据驱动**你换哪个环节——而不是凭感觉。

### Agent「接入」RAG 的三条路

1. **工具化（tool / function call）** —— 把检索封装成工具，agent 按需调用。最贴合 agent 架构，检索时机由模型决定。
2. **MCP 协议** —— 把知识库暴露成 MCP server，任何支持 MCP 的 agent 零改造接入。跨 agent 复用最好。
3. **HTTP API** —— R2R / Dify / RAGFlow 都提供 REST API，agent 当外部服务调。耦合最低、最易替换，代价是多一跳网络。
