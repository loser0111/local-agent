## 一、插件定位

### 1.1 一句话定位

> local-agent 的**常驻侧翼**：把「在什么时间、做什么事」这件事从人脑里挪到系统里，到点用 Windows 通知把人拉回来；需要动手的任务则复用主程序的 agent 能力自动执行，把结果摘要推送回来。

### 1.2 落地形态的界定（重要）

Wails 是**单进程、Go 代码编译期链接**的应用，不存在运行期加载 `.dll` / `.so` 的热插拔机制。因此「插件」在本项目里的落地形态只能是：

| | 形态 | 说明 |
|---|---|---|
| 后端 | 一组新增的 Go 文件（建议归入 `plugin/` 或 `scheduler*.go` + `task*.go`），在 `NewApp()` 里装配 | 与 `plan.go` / `subagent.go` 同级的平级能力模块，不是外挂 |
| 桥接 | `App` 上新增导出方法，自动生成到 `frontend/wailsjs/go/main/App` | 沿用现有绑定机制 |
| 前端 | 设置页新增 tab + 工作区新增任务面板（改造现有 `TasksPane.vue`） | 沿用现有挂载点 |

**结论**：本插件是「编译期内置的能力模块」，但要在**代码组织与依赖方向上保持插件化**——即插件的新增代码尽量只通过少量显式接口触碰主程序（见第四节），以便独立测试、独立开关、后续可整体剥离。

### 1.3 它是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 本地、单机、离线优先的定时提醒与定时执行 | 云端任务编排 / 多机协同 / 团队共享任务 |
| 面向**自己的机器**的自动化助手 | 通用 cron / 任务调度平台的替代品 |
| 复用主程序 agent 能力的**触发器** | 第二套工具循环、第二套权限体系 |
| 「到点了把人叫回来」+「无人值守跑一次」 | 有向无环图编排、跨任务依赖、复杂重试策略矩阵 |
| 通知 + 应用内面板 + 执行历史 | 移动端推送、邮件/IM 多渠道通知（列为后续可扩展） |

### 1.4 命名

- 插件能力对外名称：**定时任务（Scheduled Tasks）**
- 后端事件通道：`task:event`
- 数据文件：`~/.local-agent/tasks.json`（运行历史建议 `~/.local-agent/task-runs/`）

## 二、目标用户与使用前提

### 2.1 目标用户画像

**主要用户：本机开发者本人。**

- 身份：使用 local-agent 做日常开发工作的开发者，机器就是开发机
- 典型一天：开着 IDE / 终端 / 浏览器，agent 窗口常驻但**大部分时间不在前台**
- 关注点：别漏事（提醒可靠）、别打扰（通知要克制）、别乱动代码（自动执行必须可控）
- 技术水位：能看懂 cron 表达式，但**不想手写**；愿意为可靠性做一次性配置
- 明确**不需要**：多用户隔离、权限分级、审批流、配置分享

### 2.2 使用前提与假设（设计必须建立在这些之上）

| # | 假设 | 对设计的约束 |
|---|---|---|
| A1 | 应用**已实现常驻托盘**（单实例锁 + 关窗隐藏） | 若托盘未落地，插件必须能降级为「仅应用开启期间生效」，不能因此不可用 |
| A2 | 机器会休眠/睡眠/关机，任务可能被**错过** | 调度器必须有「错过补偿」策略（补发提醒 / 跳过 / 顺延），并把选择权交给用户 |
| A3 | 后台执行 agent 任务时**无人可以问答** | 必须复用 `subagentEnforcer` 那套「ask 降级为带理由的拒绝」的思路，禁止后台任务无限阻塞等待授权 |
| A4 | 用户大部分时间不在 agent 窗口前台 | 通知是**一等公民**，不是附属品；点击通知必须能唤醒/聚焦窗口并定位到对应任务 |
| A5 | 单实例、单用户 | 任务文件无并发多进程写入问题，但仍需 `sync.RWMutex` 保护（托盘与窗口可能并发操作） |
| A6 | 自动执行会消耗 token / 改动工作区 | 每次自动执行必须**可追溯**（谁触发的、跑了什么、花了多少、改了什么），且默认不碰主会话 |

## 三、典型使用场景

场景编号 `SC-x`，`优先级`为 P0（先做）/ P1（紧随）/ P2（可延后）。

### SC-1 定时提醒（基线场景）· P0

- **触发方式**：时间驱动（一次性 / 每天 / 每周 / 工作日 / 间隔）
- **用户故事**：我在写代码时容易忘记「11:30 该去吃饭」「每周五下班前提交周报」，希望到点弹一条 Windows 通知，我点一下就能确认或推迟。
- **期望行为**：
  1. 到点弹出系统 Toast：标题 = 任务名，正文 = 备注
  2. Toast 上提供动作按钮：`完成` / `推迟 10 分钟` / `打开 agent`
  3. 点 `完成` → 标记本次触发为 done；点 `推迟` → 生成一次 10 分钟后的临时触发
  4. 错过（机器睡眠）后按策略处理，并在面板上以「已错过」样式标出
- **插件职责**：计时、生成通知内容、处理按钮回调、写触发记录
- **主程序职责**：提供通知能力与窗口唤醒；不参与
- **价值**：验证「调度→通知→交互回调」这条主干链路，风险最低

### SC-2 每日/每周工作汇总 · P1

- **触发方式**：时间驱动（如每个工作日 18:30）
- **用户故事**：我希望下班前自动收到一份「今天工作区改了什么、计划还剩哪些没做、有哪些未提交改动」的摘要，而不用自己回忆。
- **期望行为**：
  1. 到点由插件**触发一次 agent 运行**，用预设 prompt 采集信息（读 git 状态 / 计划进展 / 今日会话摘要）
  2. 运行在**独立会话**中进行，不污染我正在用的会话
  3. 跑完把结论压缩成通知正文（超长截断），完整内容写入面板的「执行历史」，可点开查看
  4. 运行期间面板显示「运行中」；失败时通知里说明失败原因，不留黑箱
- **插件职责**：调度、prompt 模板、结果→通知的呈现、历史落盘
- **主程序职责**：执行 agent（复用 `agentRun` / `runToolLoop` 这条无 UI 执行链）
- **价值**：本插件相对「普通提醒闹钟」的核心差异点，直接体现 B 层能力

### SC-3 任务完成通知（事件驱动，无定时）· P0

- **触发方式**：运行事件驱动（非时间驱动）
- **用户故事**：我让 agent 跑一个长任务（或一个会跑很久的计划 / 子代理）后切去写别的，跑完了希望有通知告诉我，而不是回来发现早就结束了。
- **期望行为**：
  1. 监听运行生命周期：一次运行/一个计划/一个子代理结束（成功、失败、被取消）
  2. 若结束时不满足「不打扰」条件 → 弹通知，正文给一句话结论 + 耗时
  3. 窗口不在前台时才弹（或按配置强度调整）
- **插件职责**：把主程序已有的运行事件转成通知
- **主程序职责**：暴露「运行开始/结束」事件（现有 `chat:event` 已含部分信息，可能需要补一个稳定的「运行生命周期」事件）
- **价值**：零调度风险、收益立竿见影，且是 SC-4 的基础设施

### SC-4 长时间无响应告警 · P1

- **触发方式**：看门狗（心跳超时）
- **用户故事**：agent 有时候会卡住（等模型超时、等一个不该等的交互），我不想盯着它，但如果它 5 分钟毫无进展，请告诉我，最好让我一键中止。
- **期望行为**：
  1. 监控运行中的「最后活动时间」（任何流式分片、工具调用、事件都算活动）
  2. 超过阈值（默认 5 分钟，可配）→ 弹通知：`任务 X 已 300 秒无进展`，附动作按钮 `查看` / `中止`
  3. 点 `中止` → 调用现有运行取消链路（`runControl` 软/硬取消），并把「已中止」结果回写通知
  4. 同一运行的通知**只弹一次**（防轰炸），除非用户主动问
- **插件职责**：心跳聚合、阈值判定、通知与中止按钮
- **主程序职责**：提供「运行活动心跳」与「按运行 ID 取消」的稳定接口
- **价值**：把已有的取消能力搬到用户手边；**风险点是误报**，阈值与「什么算活动」需明确定义

### SC-5 定时巡检/自动化动作 · P2

- **触发方式**：时间驱动（如每个工作日 09:00）
- **用户故事**：我想每天开工时自动让 agent 检查一下工作区状态（有没有忘提交、有没有 build 产物、TODO 有多少），有问题就提醒我。
- **期望行为**：
  1. 到点自动跑预设 prompt（由模版提供，用户可改）
  2. 结果分两路：完整报告进面板历史；若有「需要关注」的结论则弹通知
  3. 允许用户配置「静默模式」：只在有问题时才通知（避免每天一条无意义的「一切正常」）
- **插件职责**：调度、模板、通知判定（含静默条件的表达）
- **主程序职责**：执行 agent；权限网关（默认应是只读倾向）
- **价值**：把 agent 变成「定时值班」；**风险点**是权限与成本，需有明确默认值与一键停用

### 候选场景（本期不做，留作演进）

- SC-6 番茄钟/久坐提醒：与开发工作关联弱，用户画像里优先级低
- SC-7 IM/邮件外发通知：需要额外凭据与网络，属「通知渠道扩展」
- SC-8 任务模板市场/分享：目标用户是自用，无分享需求

### 场景优先级汇总

| 场景 | 触发类型 | 优先级 | 依赖 |
|---|---|---|---|
| SC-1 定时提醒 | 时间 | P0 | 托盘常驻、通知 API |
| SC-3 任务完成通知 | 事件 | P0 | 运行生命周期事件 |
| SC-2 每日汇总 | 时间 + 执行 | P1 | SC-1 调度主干 + agentRun 触发入口 |
| SC-4 无响应告警 | 看门狗 | P1 | 运行活动心跳 + 取消接口（SC-3 同源） |
| SC-5 定时巡检 | 时间 + 执行 | P2 | SC-2 同路径 + 权限策略 |

## 四、插件与主程序的职责边界

### 4.1 边界总表

| 能力 | 归属 | 具体分工 |
|---|---|---|
| 进程生命周期（单实例锁、关窗行为、托盘、退出确认） | **主程序** | 插件只「声明自己需要常驻」，不自己管窗口。托盘是全局唯一资源，属主程序职责 |
| 通知能力初始化（`InitializeNotifications`、Category 注册） | **主程序** | 启动时初始化一次，插件不重复初始化（否则注册表/COM 注册重复） |
| 通知内容与时机 | **插件** | 什么时候发、发什么、有哪些按钮、按钮点了做什么 |
| 时间源与调度（周期、错过补偿、去重） | **插件** | 主程序不感知定时概念 |
| 任务数据模型与持久化（`tasks.json`、执行历史） | **插件** | 复用主程序的「JSON 整文件 + RWMutex + 启动加载」范式与数据目录约定 |
| agent 执行（工具循环、上下文、模型调用） | **主程序** | 插件**不自己跑循环**，只调用一个受控触发入口 |
| 权限网关 | **主程序** | 复用 `permissionEnforcer`；插件仅提供「无人值守策略」参数（后台不可问答 → 需预先明确允许/拒绝范围） |
| 运行取消（软/硬） | **主程序** | 插件通过运行 ID 调用既有取消链路 |
| 事件推送通道（`EventsEmit`） | **主程序提供机制，插件定义自己的事件名** | 插件新增 `task:event`，不与其他通道混用 |
| UI 挂载点（设置页 tab、工作区面板） | **主程序提供挂载机制** | 插件提供组件与其中逻辑 |
| 前端交互回路（阻塞等待用户作答的 broker 范式） | **主程序提供范式** | 插件可复用「发事件→等结果→超时→前端轮询兜底」这套已有做法 |

### 4.2 三条边界原则

**原则一：调度归插件，执行归主程序。**
插件到点后**不自己实现**任何工具调用、上下文拼装或模型调用，只调用主程序暴露的执行入口。理由：主程序已经为「子代理」把执行链参数化过（`agentRun` + `runRecorder`：会话、权限网关、事件通道都可替换）。再写一份循环必然与主循环漂移——这是本项目在 P3 阶段已经付过一次学费的教训（见 `agentrun.go` 开头注释）。

**原则二：主程序管「生命周期与能力」，插件管「策略与内容」。**
托盘、窗口、通知初始化这些全局且唯一的能力不进插件；「几点提醒、提醒时说什么、按钮做什么、错过怎么办」这类策略全在插件。这样插件整体可关停（一个开关就能让主程序回到今天的样子）。

**原则三：插件不得阻断主程序。**
后台常驻功能的失败模式必须被隔离：调度器运行在独立 goroutine，任务执行**逐个串行 + panic recover**，任何单个任务/通知的异常都只记录到执行历史，不得影响聊天主流程，不得让应用崩溃或退出。这是本插件的硬约束（对应第七节非功能需求）。

### 4.3 边界上的灰区与结论

| 灰区 | 结论 | 理由 |
|---|---|---|
| 关窗之后应该隐藏还是退出？ | **主程序决定**，插件只做消费者 | 托盘是全局行为，且影响没有装插件时的默认体验；插件未启用时应保持今天的「关窗即退出」 |
| 点通知要唤醒窗口，谁来唤醒？ | 主程序提供「显示并聚焦窗口 / 定位到某任务」的接口，**插件调用** | 窗口控制属主程序；「定位到哪个任务」属插件语义 |
| 自动执行用哪个会话？ | **每次自动执行建独立会话**（对齐子代理的隔离做法），不写进用户正在用的会话 | 复用现有按 `sessionID` 键控的隔离机制，无需新增归因字段 |
| 自动执行要不要走权限网关？ | **要走，且走「无人值守」降级策略** | 与 `subagentEnforcer` 同思路：需要用户授权的操作降级为带理由的拒绝，并要求模型改用不需授权的做法或写进结论 |
| 任务定义要不要暴露给模型（当工具用）？ | 建议**暴露为工具**（模型可帮用户建任务），但归属 `exposure: internal/router`，且复用 `Ask` 回路让用户确认 | 与现有 `ask_user` / `spawn_agent` 一致；「模型能自己给自己排任务」是强能力也是风险点，需用户确认 |
| 执行历史放哪？ | 独立目录按次落盘，任务文件只存定义与最近状态 | 避免 `tasks.json` 因历史膨胀而频繁整文件重写 |
| 通知强度的默认值？ | 默认**克制**：仅「窗口不在前台」时弹系统通知；后台静默任务默认不弹成功通知 | 目标用户是自用的开发者，打扰成本高；宁可少弹也不要弹无意义通知 |

### 4.4 明确不做（Non-goals）

1. 不引入云端/远程调度，不做跨设备同步
2. 不做多用户、权限分级、审批流
3. 不做任务间依赖编排（DAG）、不做复杂重试策略矩阵（最多「失败重试 N 次」）
4. 不做第二条工具循环、第二套权限判定
5. 不改动现有会话/计划/子代理的行为语义（插件只新增，不重构主链路）
6. 不保证「应用未运行时的提醒」（除非后续把调度常驻化到系统级服务，本期不做）

## 五、功能需求清单与优先级

### 5.0 优先级定义与判据

| 级别 | 含义 |
|---|---|
| **P0** | MVP 必须。缺失则插件不可用，或可用但**不可信**（漏提醒、误打扰、数据丢失、拖垮主程序） |
| **P1** | 紧随其后。显著提升可用性/可用范围，但不做也能跑通主干 |
| **P2** | 增强项。可延后，或明确留作演进接口 |
| **不做** | 本期明确排除（对应 4.4 的 Non-goals） |

**进入 P0 的判据**（需至少满足两项）：① 属于 SC-1/SC-3 主干链路；② 缺失会让用户不再信任提醒（漏 / 误 / 丢 / 崩）；③ 实现所依赖的能力已在第 1 步调研中确认为现成（低风险）。

功能点编号 `F<模块>.<序号>`。

### 5.1 M1 任务管理

## 六、技术选型与整体架构

### 6.0 结论速览

| 问题 | 结论 |
|---|---|
| 用什么 UI 框架承载插件？ | **都不用**。不加 Electron / Tauri / WinUI3 / WPF，直接复用 local-agent 现有的 Wails + Vue 外壳 |
| 进程模型？ | **嵌入 agent 进程（in-process Go 模块）**，不启独立进程 |
| 与 agent 的通信方式？ | **进程内 Go 函数调用**（不是 HTTP / WebSocket / 命名管道 / CLI）；前端经 Wails 绑定 + `task:event` |
| 需要新引依赖吗？ | **托盘**是唯一缺口（Wails v2 无 tray API）。首选用 `golang.org/x/sys/windows` 调 `Shell_NotifyIconW` 自研最小实现，**零新依赖**；其余全部复用现成能力 |
| 唯一需要一次技术验证的点 | 托盘图标的消息窗口方案（见 6.9 未决问题 1） |

**一句话**：这不是一个「选框架」的问题，而是一个「Wails 单进程应用如何增加一个常驻能力模块」的问题——因为 B 层能力要求**在同一进程内调用 agent 执行链**，任何外部 UI 框架都会把这一点变成跨进程问题，代价远大于收益。

### 6.1 四种 UI 框架对比与否决理由

体积/内存为**数量级估算**（未在本机实测，仅用于说明差异级别；实际值随打包尺寸与负载波动）。

| 维度 | Electron | Tauri | WinUI3 | WPF | **本方案：嵌入式 Wails 模块** |
|---|---|---|---|---|---|
| 安装体积增量 | ~120–200 MB（自带 Chromium + Node） | ~5–15 MB（复用系统 WebView2） | ~20–40 MB（需 Windows App SDK 运行时） | ~30–60 MB（.NET 运行时） | **≈0**（复用现有 exe 与 WebView2） |
| 内存增量 | 150–400 MB（空闲，独立 Chromium 进程树） | 30–80 MB | 60–150 MB | 60–150 MB | **几 MB**（Go 侧调度器/看门狗）+ 复用已加载的 WebView |
| 开发成本 | 低（JS/TS 熟练）但需自建 IPC 桥 | 中高（Rust + 前端，学习曲线陡） | 中（C#/XAML 上手快，独立发布配置繁琐） | 中（C#/XAML 成熟稳定） | **低**：Go 写后端 + 复用现有 Vue 组件与 Pinia store |
| 与现有技术栈契合度 | 差（引入 Node + 第二套构建链） | 差（引入 Rust 工具链） | 差（引入 .NET） | 差（引入 .NET） | **完全契合**（Go 1.25 同一模块内新增包 + 现有 Vue 工程） |
| 能否直接调用 agent 能力 | **不能** | **不能** | **不能** | **不能** | **能**（同进程直接调 `agentRun`/`runControl`） |
| 托盘/通知成熟度 | 内置 Tray + Notification，成熟 | 内置 tray 与通知，较成熟 | 需自行封装 | 需自行封装（NotifyIcon） | **需自研托盘**（通知复用 Wails 内置） |
| 与主程序数据/权限/会话体系的整合 | 需跨进程同步，易漂移 | 同左 | 同左 | 同左 | 天然共享内存中的 store 与权限网关 |
| 是否采纳 | ❌ | ❌ | ❌ | ❌ | ✅ |

#### 否决的结构性理由（而非成本理由）

四种方案都**先天无法满足** 4.2 的原则一「调度归插件、执行归主程序」：

1. **无法调用 agent 执行链。** 本项目**没有 headless / CLI 入口**（已核实：全仓库无 `os.Args` / `flag` / `cobra` / `urfave` 使用，`main.go` 只做 `wails.Run`）。外部框架进程想触发一次 agent 任务，要么让 Go 侧先长一个 CLI/HTTP 服务出来（= 新增一套对外接口与安全面），要么在外部框架里**重写一遍工具循环**——后者正是第 4.2 节明确禁止的。
2. **会造成双份调度与重复通知。** Wails v2.15 **自带** `SingleInstanceLock`（已核实），但那只约束 agent 自身；外部进程不受约束，两个进程各跑一套定时器 → 通知重复，直接违背 F8.5。
3. **资源开销与目标用户画像不符。** 目标用户是「本机开发者自用」，为一个定时提醒常驻 150–400 MB 内存不成比例。
4. **多一套构建/分发链路。** 本项目现在 `wails build` 一条命令出包；引入第二种打包链会显著抬高维护成本。

#### 反过来：什么情况下该选它们

诚实地说，如果需求演变成下面任一条，就应当重新评估（届时本节的结论不再成立）：

- 插件需要**脱离 agent 独立运行**，且在 agent 未启动时也要能提醒（即 F4.9 升级为 P0）→ 应选 **Tauri**（体积小、托盘成熟）
- 插件需要**大规模跨平台 UI**（macOS/Linux 同等重要）→ **Tauri** 或 **Electron**
- 插件主要用户是**非开发者的 Windows 用户**，需要系统级集成深度 → **WinUI3**

### 6.2 进程模型：嵌入式（in-process）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 嵌入 agent 进程** | 可直接调 `agentRun`/`runControl`/权限网关；共享 store 与配置；零 IPC；单实例天然一致；开销几 MB | 插件 bug 理论上可能影响主进程（用 5.8 的 panic 隔离 + 串行执行约束） | ✅ **采纳** |
| B. 独立进程（Go 小程序 + IPC） | 崩溃隔离彻底；可独立升级 | 无法调 agent 执行链（无 CLI 入口）；双定时器风险；需自建 IPC 与协议版本管理；仍需托盘 | ❌ |
| C. 独立进程（复用同一 exe 加子命令） | 便于「系统级定时唤醒」演进 | 需要新增 headless 入口与参数解析，改动主程序启动路径；本期收益为零 | ❌（留作演进，见 6.3） |

**取舍说明**：A 的唯一实质代价是「插件异常可能影响主进程」。但这项风险在**第 5 步（SC-3/SC-4）**已经证明有成熟解法——子代理同样在主进程内跑完整工具循环，靠 `panic` 隔离、串行执行与超时约束把风险控制在可接受范围。插件沿用同一套约束，风险等级与现有的子代理能力相同，不引入新的风险类别。

**但要避免的写法**：不能把插件代码直接堆进 `main` 包。要求「**进程内模块化**」——插件放在独立包，只通过一个窄接口（6.3 的 `Host`）依赖主程序，从而可独立测试、可整体停用、可后续剥离。

### 6.3 与 agent 的通信方式

#### 五种候选通信方式的评估

| 方式 | 在「独立进程」下是否必要 | 本方案是否使用 | 理由 |
|---|---|---|---|
| 本地 HTTP | 是（若选独立进程） | **不用** | 需监听端口 → 攻击面（本机任意进程可调）、需处理端口占用与生命周期、需鉴权。进程内直接调用零收益成本 |
| WebSocket | 是（同上，双向推送） | **不用** | 同上；且「服务端 → 前端」的推送已有 `EventsEmit`，无需再引一条 |
| 命名管道 | 是（同上，Windows 首选 IPC） | **不用** | 只有独立进程才需要 IPC；已决定不启独立进程 |
| 共享文件 | 可作为降级 IPC | **不用于通信，但用于持久化** | `tasks.json` / `task-runs/` 是**状态落盘**，不是进程间通信机制。单实例下无需用它传消息 |
| CLI 调用 | 是（跨进程触发 agent 的唯一无协议路径） | **不用** | 项目无 headless 入口。**但这是未来「应用退出仍能提醒」的唯一可行路径**，故在架构上预留：将来给 `main.go` 加子命令（如 `--run-task <id>`），交给 Windows 计划任务定时唤醒 |
| **Go 函数调用（进程内）** | — | ✅ **主通道** | 零开销、编译期类型检查、可直接复用 `ctx` 取消链 |

#### 实际的三条通道

**通道 1：插件 → 主程序（需要主程序提供的窄接口 `Host`）**

这是本步最重要的设计产物——插件对主程序的**全部**依赖收敛到一个接口，接口之外插件不碰主程序任何内部结构：

```go
// plugin/host.go —— 插件对主程序的唯一依赖面（提案）
type Host interface {
    // —— 通知能力（主程序负责初始化，插件只负责内容与时机）——
    NotifyAvailable() bool                       // 包 IsNotificationAvailable + 授权检测
    Notify(req NotifyRequest) error              // 包 Send/WithActions + 失败降级到应用内提醒
    RegisterCategories(cats []NotifyCategory) error // 启动时一次性注册（Windows 需落 HKCU）
    OnNotifyResponse(fn func(NotifyResponse))    // 点击/按钮/回复回调

    // —— 窗口（点通知要唤醒并定位）——
    RevealWindow(payload RevealPayload)          // 包 WindowShow（已核实自带聚焦）+ 前端跳转事件

    // —— agent 执行（插件绝不自己跑循环）——
    RunAgent(ctx context.Context, req RunRequest) (RunResult, error)
    CancelRun(runID string) error                // 复用 runControl 软/硬取消
    SubscribeRuns(fn func(RunEvent))             // 运行生命周期（SC-3 / SC-4）

    // —— 基础设施 ——
    BaseDir() string                             // ~/.local-agent，复用数据目录约定
    AppVersion() string
}
```

`RunRequest` 关键字段（对齐 SC-2/SC-5 与 4.3 灰区结论）：prompt、模型、工作区目录、**独立 sessionID**、无人值守权限策略（预授权范围 + ask 降级为带理由拒绝）、超时。

**通道 2：插件 → 前端（推送）**

沿用 `EventsEmit`，插件自带独立通道 `task:event`，不与其他通道混用：

| 事件子类型 | 触发时机 | 前端反应 |
|---|---|---|
| `task:changed` | 任务增删改、启用/停用 | 刷新列表 |
| `task:fired` | 一次触发发生 | 列表状态更新、角标 |
| `task:run:started` / `task:run:finished` | 执行型任务开始/结束（含结果摘要） | 显示运行中/结果 |
| `task:missed` | 检测到错过（启动补偿时） | 高亮「已错过」 |
| `task:notify:fallback` | 系统通知不可用，已降级 | 展示应用内提醒 + 原因 |

**通道 3：前端 → 插件（调用）**

沿用现有绑定机制：`App` 上导出方法（任务 CRUD、启用/暂停、立即执行一次、历史查询、配置读写），前端经 `frontend/wailsjs/go/main/App` 调用。**不需要手写任何 HTTP 客户端**。

### 6.5 关键技术选型逐项结论

| 议题 | 选项 | 选择 | 理由与代价 |
|---|---|---|---|
| UI 框架 | Electron/Tauri/WinUI3/WPF/嵌入式 | **嵌入式复用 Wails** | 见 6.1；代价是必须自研托盘 |
| 进程模型 | 独立进程 / 嵌入 | **嵌入** | 见 6.2；代价是需 panic 隔离（已有成熟范式） |
| 通信 | HTTP/WS/管道/文件/CLI/函数调用 | **Go 函数调用** | 见 6.3 |
| 通知 | Wails 内置 / go-toast 直调 / 自研 WinRT | **Wails 内置** | 无需新依赖；已含动作按钮与点击回调 |
| 托盘 | 第三方 systray 库 / 自研 shell32 | **自研最小实现（首选）** | 模块缓存中**无** systray 库（已核实），引入需联网；`x/sys/windows` 已在依赖树内且提供 `NewLazyDLL`/`NewLazySystemDLL`，可零新依赖实现「图标 + 右键菜单 + 点击」。代价：需自己写 Windows 消息处理 |
| 单实例 | 自研互斥体 / Wails 内置 | **Wails `SingleInstanceLock`** | 已核实 v2.15 自带，含 `UniqueId` 与 `OnSecondInstanceLaunch` |
| 关窗隐藏 | 自研 / Wails 内置 | **Wails `HideWindowOnClose` + `OnBeforeClose`** | 已核实自带；退出确认走 `OnBeforeClose` |
| 开机自启 | 启动文件夹 / HKCU Run 键 | **HKCU `Run` 键** | `x/sys/windows/registry` 已在依赖树内；可精准增删，便于一键关闭（F4.7） |
| 调度器 | 第三方 cron 库 / 自研 | **自研最小调度器** | F2.2–F2.4 的周期类型不需要完整 cron 语义；模块缓存中**无**成熟 cron 库（已核实），引入需联网。代价：cron 表达式（F2.5）若需完整语义，需自写解析或用子集并明确说明 |
| 时间源 | `time.After` / `time.Ticker` / 单调时钟 + 重算 | **单调时钟测间隔 + 每次重算下次触发点** | 这是 F2.10（休眠唤醒、改系统时间）的唯一可靠做法 |
| 持久化 | SQLite / JSON 整文件 | **JSON 整文件 + RWMutex** | 复用 `PlanStore` 范式；任务量级（几十条）远未到需要 DB 的规模 |
| 事件推送 | 新增 WS / 复用 EventsEmit | **复用 `EventsEmit`** | 零成本，前端已有 `EventsOn` 封装范式 |
| 窗口聚焦 | 自研 SetForegroundWindow / Wails | **Wails `WindowShow`** | 已核实其 Windows 实现内部即 `ShowWindow` + `SetForegroundWindow` + `SetFocus`，无需自研 |

### 6.6 架构决策记录（ADR 简表）

| # | 决策 | 主要理由 | 接受的代价 |
|---|---|---|---|
| ADR-1 | 插件以「进程内 Go 模块」形态落地 | 需同进程调用 agent 执行链；项目无 headless 入口 | 需 panic 隔离；无法脱离 agent 独立运行 |

| ADR-6 | 执行型任务复用 `agentRun`，不另写循环 | 避免与主循环漂移（P3 已付学费） | 受主程序执行链能力边界约束 |
| ADR-7 | 每次都建独立会话执行 | 隔离，避免污染用户会话 | 会话数量增长，需保留策略（F6.4） |
| ADR-8 | 本期不做「应用退出后仍提醒」 | 需 headless 入口或系统服务，成本高 | 退出后提醒失效，须在 UI 明确告知（F4.9 + F4.4） |

### 7.0 结论速览

| 问题 | 结论 |
|---|---|
| 主载体 | **Windows 系统 Toast**（复用 Wails 内置通知 + 动作按钮 + 点击回调） |

| 声音 | 只能用系统默认 Toast 提示音，**无法自定义也无法静音单个 Toast** → 以「降级为应用内提醒」实现静音（见 7.7.1） |

| 最需要注意的三个坑 | ①**无法程序化关闭或替换已送达通知**（完成标记不能更新 Toast）；②点击通知是 **Foreground 激活**，应用未运行时需处理**冷启动激活参数**；③`IsNotificationAvailable()` 在 Windows 上**恒为 true**，不可用作可用性探测 |

### 7.1 四种载体与分工

#### 7.1.1 Windows 系统 Toast —— 主载体（P0）

**定位**：负责「**过去发生的事**」——到点了、跑完了、卡住了、错过了。它的价值是**把人从别处拉回来**，因此必须能脱离应用窗口独立存在。

**已核实的能力边界（决定了后续所有设计）**

| 能力 | 状态 | 依据 |
|---|---|---|
| 标题 + 正文 | ✅ | `SendNotification` |
| 动作按钮 | ✅ 需先注册 Category，否则**静默降级为普通通知**（仅打日志） | `SendNotificationWithActions`：`CategoryID` 未注册 → 退回 `SendNotification` |
| 点击按钮 / 点击正文 | ✅ 携带动作标识与自定义数据回传 | 正文点击 → `ActionIdentifier = "DEFAULT_ACTION"`（`DefaultActionIdentifier`）；`encodePayload` 把 `NotificationOptions.Data` 编进激活参数 |
| 回复输入框（收文本） | ✅ 回传至 `Response.UserText` | Windows 实现插入 `Input{ID:"userText"}` |
| 副标题 Subtitle | ❌ **Windows 不显示**（仅 macOS/Linux） | 代码注释明示 "retained but was not shown" |
| 关闭/替换已送达通知 | ❌ **Windows 实现全为空操作** | `RemovePendingNotification` / `RemoveDeliveredNotification` / `RemoveNotification` 均 `return nil` |
| 可用性探测 | ⚠️ **不可用**：`IsNotificationAvailable()` 硬编码 `return true` | `windows/notifications.go:152` |
| 通知来源显示名 | ⚠️ 取 exe 文件名 → 当前会显示 **`wails-tmp`** | `appName = filepath.Base(exePath)` + `wails.json` |
| 通知图标 | ✅ 从 exe 提取为临时 PNG（`temp/<exe名><GUID>.png`） | `saveIconToDir` |
| Category 持久化 | ✅ 存 `HKCU\SOFTWARE\<exe名>\NotificationCategories`，启动时自动加载；同名重复注册为覆盖 | `saveCategoriesToRegistry` / `loadCategoriesFromRegistry` |
| 激活方式 | ⚠️ **Foreground 激活**：点通知会**拉起 exe**，激活参数经单实例锁转交 | `ActivationType: toast.Foreground` + `SingleInstanceLock.OnSecondInstanceLaunch(SecondInstanceData{Args})` |

> **对第五节 F3.4 的修订**：F3.4 原定「先用 `IsNotificationAvailable` 探测可用性」，此路不通（恒为 true）。改为：**以发送结果为准的被动降级**——`Send` 返回错误，或首次发送失败即判定为不可用，降级到应用内提醒并在面板提示原因（每会话只提示一次，防刷屏）。详见 7.10.1。

#### 7.1.2 托盘图标与右键菜单（P0）

**定位**：负责「**我现在想操作**」——轻量快捷入口，不打断、不弹窗。通知与托盘是互补的：通知是「推给我」，托盘是「我去拿」。

详见 7.6。

#### 7.1.3 应用内提醒（P1）

**定位**：双重身份——① 系统通知不可用时的**降级出口**；② 窗口在前台时的**克制形态**（不弹系统 Toast 打扰，改为窗口内横幅）。

形态：
- **顶部横幅**（可堆叠，最多 3 条，自动消失）
- **任务面板置顶区**：把「未处理 / 已错过 / 失败」的任务固定在列表顶部
- **侧边角标**：面板入口显示未处理数量（替代任务栏数字角标）

#### 7.1.4 明确不做的两种形态

**A. 悬浮小组件 / 桌面卡片 —— 本期不做**

| 维度 | 说明 |
|---|---|
| 它是什么 | 常驻桌面/置顶的小窗，实时显示「下一条提醒倒计时」「今日任务」 |
| 为什么不做 | ① Wails v2 **无多窗口 API**，实现需新增第二个 Webview 窗口，改动侵入主程序启动路径（与 ADR-1「嵌入式、改动尽量小」冲突）；② 需自行处理置顶、穿透点击、多显示器与 DPI，工作量接近再写一个 UI 外壳；③ 自用场景下，**托盘 tooltip + 面板已覆盖同等信息**；④ 长期常驻小窗对目标用户是视觉噪音 |
| 演进路径（将来真要做） | 用 Wails 第二个窗口（或独立 toy 小窗）+ `AlwaysOnTop`，内容复用现有面板组件；或接入系统原生小组件（Win11 Widgets），后者成本更高 |

**B. 任务栏数字角标 —— 不做**

Wails **未暴露** badge / overlay icon API（`Frontend` 接口中无对应方法，已核实接口全表无 badge/overlay）。替代方案：
- 托盘图标叠加状态点（有未处理 → 加红点）
- 应用内面板入口角标
- 窗口标题前缀（如 `(3) local-agent`）——成本最低，可作为 P2 补充

### 7.2 通知类型与内容规范

#### 7.2.1 六类通知模板

| 类型 | 触发 | 级别 | 标题 | 正文模板 | 动作按钮 |
|---|---|---|---|---|---|
| N1 定时提醒 | 到点 | L2 | `<任务名>` | `<备注>\|下次：<时间>`（无备注则省略） | 完成 / 稍后提醒 / 打开 agent |
| N2 执行成功 | 执行型结束（成功） | L1（默认可静默） | `<任务名> · 完成` | `<一句话结论>（耗时 <m>s）` | 查看结果 / 打开 agent |
| N3 执行失败 | 执行型结束（失败/超时/中止） | **L3** | `<任务名> · 失败` | `<可读失败原因>（耗时 <m>s）` | 查看结果 / 重新执行 / 打开 agent |
| N4 无响应告警 | 心跳超阈值 | **L3** | `<任务名> · 已 <n> 秒无进展` | `最后活动：<动作>；可一键中止` | 查看 / 中止 |
| N5 错过补偿 | 启动/唤醒时发现错过 | L2（合并） | `你有 <n> 条提醒未处理` | `最早：<任务名>（<时间>）` | 全部知道了 / 稍后提醒 / 打开 agent |
| N6 系统事件 | 自启失败、配置损坏、托盘初始化失败等 | L2 | `定时任务：<事件>` | `<原因与建议动作>` | 打开设置 |

> 所有通知的 `Data` 都携带：`taskId`、`triggerId`（本次触发的唯一序号）、`kind`（N1–N6），用于点击回传时精确定位与幂等判断。

#### 7.2.2 内容规范（硬约束）

| 项 | 约束 | 理由 |
|---|---|---|
| 标题 | ≤ 40 字符，且**必须包含任务名** | 用户在通知中心能一眼分辨来源 |
| 正文 | ≤ 120 字（约 2 行） | 超出部分系统会截断；长内容走面板 |
| 关键结论前置 | 执行型正文的**第一句必须是结论** | 通知是不可展开的，结论必须零成本可见 |
| 不使用 `Subtitle` | Windows 不显示，避免把关键信息写进去丢失 | 已核实 |
| 不用 Markdown | Toast 不渲染，会显示原始符号 | — |
| 失败必须带原因 | 禁止只写「失败」 | 对齐 F6.5 |
| 时间格式 | 相对时间优先（「10 分钟后」「今天 18:30」） | 减少心算 |

#### 7.2.3 通知 ID 规范

- `NotificationOptions.ID = "task:<taskId>:<triggerId>"`：稳定、可关联、便于去重与日志排查
- 由于**无法替换已送达通知**，ID 仅用于我方记录与回传匹配，**不要指望它能做到「同 ID 覆盖」**
- `triggerId`：单调递增或「计划触发时刻的时间戳」，用于幂等（同一触发重复点击只生效一次）

### 7.3 动作按钮与点击行为

#### 7.3.1 按钮数量约束

Windows Toast 的动作按钮存在系统上限（≤5）。自用场景下按类型精选 **≤3 个**，理由：按钮越多越难选，且提醒类通知的核心动作只有一个（完成）。

**Category 注册方案**（启动时一次性注册，同名覆盖，持久化在 HKCU）：

| CategoryID | 动作（ID / 文案） | 回复框 |
|---|---|---|
| `reminder.basic` | `done`/完成、`snooze10`/稍后 10 分钟、`open`/打开 agent | 无 |
| `exec.result` | `view`/查看结果、`rerun`/重新执行、`open`/打开 agent | 无 |
| `exec.abort` | `view`/查看、`abort`/中止 | 无 |
| `reminder.batch` | `ackAll`/全部知道了、`snooze10`/稍后提醒、`open`/打开 agent | 无 |
| `reminder.reply`（P2） | `snooze10`/稍后 10 分钟、`open`/打开 agent ＋ 回复框「回复内容…」 | ✅ |

> 注册失败（注册表无权限等）不阻塞启动，但需记 N6 通知 —— 否则会退化成「所有通知都没按钮」而用户不知原因。

#### 7.3.2 逐动作语义定义

| 动作 | 语义 | 状态迁移 | 幂等要求 | 备注 |
|---|---|---|---|---|
| 点击**正文** | 打开 agent 并**定位到该任务** | `notified → 保持` | — | `DEFAULT_ACTION`；不改变任务状态，避免「点一下就被标记完成」的意外 |
| `done` 完成 | 标记本次触发为已完成 | `notified → done` | 是 | 一次性任务同时置为「已完成」，不再安排下次 |
| `snooze10` 稍后提醒 | **生成一次 10 分钟后的临时触发**，不改动原任务规则 | `notified → snoozed → scheduled` | 是 | 对齐 F2.6；snooze 次数可累计但需记录（面板可见「已推迟 2 次」） |
| `open` 打开 agent | 显示并聚焦主窗口 + 跳转到任务详情 | 不变 | — | 复用 `runtime.WindowShow`（已核实其内部含 `SetForegroundWindow` + `SetFocus`） |
| `view` 查看结果 | 打开该次运行记录（含被拒权限列表） | 不变 | — | 对齐 F6.3 |
| `rerun` 重新执行 | 二次确认后重跑一次 | 追加新触发记录 | 是 | **必须二次确认**：无人值守的重复执行可能反复改动工作区、反复消耗 token |
| `abort` 中止 | 取消当前运行 | `running → aborted` | 是 | 复用 `CancelRun(runID)`；需区分「用户中止」与「超时中止」（语义不同，F5.5） |
| `ackAll` 全部知道了 | 批量确认 N5 汇总里的所有错过项 | 批量 `missed → acknowledged` | 是 | — |
| 回复文本（P2） | 把文本写入本次触发的备注/记录 | 不变 | — | 来自 `Response.UserText` |

#### 7.3.3 无动作与超时兜底

- 用户**直接关掉 Toast**、或在通知中心里划掉、或**从不点击** → 一律视为「无动作」
- 兜底：`notified` 状态在超过**未处理窗口**（默认 2 小时）后自动转 `ignored`，并写入触发记录
- 理由：这些通知**事后无法查询**（`Remove*/Delivered*` 是空实现，也没有「已送达通知列表」API），所以我方必须自己维护「已发通知及其未处理状态」，否则会丢失可观测性

#### 7.3.4 点击路径的实现要点（关键坑）

Windows 通知使用 **Foreground 激活**：点击动作会以激活参数**启动 exe**。因此必须处理两条路径：

| 场景 | 路径 | 要求 |
|---|---|---|
| 应用**已在运行** | 新进程启动 → 单实例锁拦截 → 把 `SecondInstanceData.Args` 转交既有实例 | 在 `OnSecondInstanceLaunch` 里解析动作参数并路由 |
| 应用**未运行**（已退出） | 直接启动新进程，Args 在 `os.Args` 中 | 需在启动早期解析 `os.Args` 中的激活参数，**不能只依赖 `OnSecondInstanceLaunch`**（它只在已有实例时触发） |

两条路径必须复用**同一个参数解析与动作分发函数**，否则会出现「应用开着时点通知有效、应用没开时点通知无效」这类难查的不一致缺陷。

### 7.4 通知优先级与打断级别

#### 7.4.1 四级定义

| 级别 | 名称 | 典型场景 | 是否弹 Toast | 声音 | 合并 |
|---|---|---|---|---|---|
| **L3** | 需立即处置 | 执行失败（N3）、无响应告警（N4）、配置损坏（N6） | ✅ 必弹，**即使窗口在前台也弹** | 系统默认音 | 不合并 |
| **L2** | 常规提醒 | 定时提醒（N1）、错过补偿（N5） | ✅ 弹（前台活跃时降级为应用内） | 系统默认音 | 同时刻多条 → 合并 |
| **L1** | 低打扰 | 执行成功汇总（N2） | ⚙️ 默认**不弹**，仅进面板；可配置为弹 | 无 | 可合并 |
| **L0** | 仅记录 | 静默模式的执行结果、被 DND 压制的项 | ❌ 不弹 | 无 | 进面板 |

#### 7.4.2 级别判定规则

- **由任务类型 + 结果共同决定**，而非只由任务类型决定：「执行型任务成功」是 L1，同一任务失败升为 L3
- 允许**逐任务覆盖**（F7.7）：任务可指定「最高级别」或「强制静默」
- 级别只影响我方行为，**无法影响 Windows 的提示样式**（无 API 控制 Toast 的紧急程度），故 L3 的「更强打断」是通过「不受 DND 与前台克制约束 + 不合并」来近似的

### 7.5 免打扰与克制规则

#### 7.5.1 统一决策树（按序判定，命中即停）

```
一次触发到点
 └─ 1. 任务级覆盖？   → 该任务显式指定「强制静默 / 强制提醒」→ 按指定执行
 └─ 2. 全局暂停开启？ → 按 F2.7 错过策略处理（记为 paused-skipped），不发通知
 └─ 3. 级别 = L0？    → 仅记录，不发
 └─ 4. 全屏/演示中？  → 静默 → 应用内提醒（等级降一级）
 └─ 5. 处于 DND 时段？→ 按 DND 策略（7.5.2），默认「顺延到时段结束」
 └─ 6. 触发频率超上限？→ 合并进「汇总通知」，不单独弹
 └─ 7. 主窗口前台活跃？→ 仅应用内提醒（不弹系统 Toast）
 └─ 8. 否则          → 发系统 Toast
```

#### 7.5.2 DND 时段策略（对齐 F7.1/F7.2）

| 策略 | 行为 | 适用 |
|---|---|---|
| **顺延（默认）** | 到期不通知，登记为「顺延」，DND 结束后汇总为一条 N5 提醒 | 最符合直觉，不丢事也不打扰 |
| 静默记录 | 只写触发记录（状态 `dnd-suppressed`），事后不进汇总 | 用户明确「这个时段的事不重要」 |
| 照常提醒 | 无视 DND（仅 L3 任务可设） | 关键告警 |

**DND 结束时的恢复提醒**：把时段内累积的顺延/静默项汇总成 **一条** N5 通知，而不是逐条补发——这是「不打扰」与「不丢事」的唯一平衡点。

#### 7.5.3 合并与折叠规则

| 情况 | 处理 |
|---|---|
| 同一任务在短时间内多次触发（含 snooze 反复推迟） | 合并为一条，正文标注「已推迟 n 次」 |
| 同一时刻（±60 秒）多条不同任务到期 | 合并为一条 N5：「<n> 条提醒：<任务1>、<任务2>…」 |
| DND/暂停结束后的堆积 | 合并为一条 N5 |
| L3 级别 | **永不合并**（每个都需独立处置） |

#### 7.5.4 前台活跃判定（重要实现设计）

Wails **没有**「窗口是否处于前台/聚焦」的查询接口。已核实的窗口状态查询只有 `WindowIsMinimised()` / `WindowIsNormal()` / `WindowIsFullscreen()`，**不足以判断用户是否正在看窗口**（窗口可见但被别的应用盖住，仍算「不在看」）。

**方案：由前端上报，而非后端猜测。**

```
前端监听 → 上报给插件 → 插件用它做决策树第 4/7 步的判定
  document.hasFocus() / window.blur / window.focus   → 聚焦状态
  visibilitychange                                   → 是否被切到后台
  fullscreenchange                                   → 是否全屏（第 4 步）
```

- 状态默认值：**未知 = 视为「不在前台」**（宁可弹通知，也不要在用户切去别的应用后悄悄不提醒）
- 上报通道：复用现有前端调用方式（或 `task:event` 的反向通道），节流合并（如 500ms），避免高频事件冲刷
- 兜底：若前端长时间未上报（窗口异常），按「不在前台」处理，并在日志中记录

#### 7.5.5 频率上限（对齐 F7.4）

| 维度 | 默认值 | 说明 |
|---|---|---|
| 同一任务 | 1 分钟内最多 1 条 | 防 snooze 循环刷屏 |
| 全局 | 5 分钟内最多 3 条 | 防大量任务同时到点轰炸 |
| 超出后 | 合并为汇总通知（L3 不受限） | — |

#### 7.7.1 声音

|---|---|

### 7.8 一次提醒的完整状态机

```
                    ┌──────────────────────────────────────────┐
   创建/保存 ──→ scheduled ──(到点)──→ firing ──(决策树放行)──→ notified
                    ↑                    │                        │
                    │                    └─(被DND/暂停拦下)──→ dnd-suppressed / skipped
                    │                                             │
                    │        ┌──────────────┬──────────────┬──────┴───────┐
                    │        │              │              │              │
                    │     [完成]        [稍后提醒]      [打开agent]    [无动作]
                    │        │              │              │              │
                    │        ↓              ↓              │         (超时 2h)
                    │      done        snoozed ───────────┐│              ↓
                    │        │              │             ││           ignored
                    │        │         (10min后)          ││
                    │        │              ↓             ││
                    │        └──────────→ scheduled ←─────┘┘
                    │
   （一次性任务完成 → 终态 done / expired，不再排下次）
```

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `scheduled` | 已排期，等待触发 | 否 |
| `firing` | 正在触发（发通知 / 启动执行） | 否 |
| `notified` | 通知已发出，等待用户动作 | 否 |
| `snoozed` | 已推迟（临时触发已生成） | 否 |
| `done` | 用户确认完成 | ✅ |
| `ignored` | 超时未处理 | ✅（记录保留） |
| `missed` | 错过（休眠/关机），待补偿 | 否 |
| `dnd-suppressed` | DND 期间被压制，待汇总恢复 | 否 |
| `skipped` | 暂停/策略决定跳过 | ✅ |
| `running` / `succeeded` / `failed` / `aborted` / `timeout` | 执行型任务的运行态与终态 | 部分是 |

> 状态迁移必须**只由插件单点驱动**并持久化，禁止前端推断状态（否则托盘、面板、通知三处显示会不一致）。

### 7.9 执行型任务的交互（N2 / N3 / N4 联动）

| 阶段 | 通知 | 面板 | 托盘 |
|---|---|---|---|
| 开始执行 | **默认不发**（L0，仅记录） | 任务行显示「运行中」+ 可中止 | 图标切「运行中」态 |
| 执行中超过阈值无活动 | N4（L3） | 高亮「疑似卡住」 | 红色点 |
| 成功 | N2（L1，默认不弹；可在设置里改为弹） | 写运行记录 + 结论摘要 | 恢复正常态 |
| 失败/超时/中止 | N3（L3，必弹，带原因） | 高亮失败 + 可查看详情 | 红色点 |
| 用户点「查看结果」 | — | 打开该次运行记录（含被拒权限列表，对齐 F5.4） | — |
| 用户点「中止」 | 可选补发一条确认（默认不发） | 状态转 `aborted` | 恢复正常态 |

### 7.10 边界情况与降级

#### 7.10.1 通知发送失败 / 系统通知被关闭

| 环节 | 行为 |
|---|---|
| 探测 | **不做主动探测**（`IsNotificationAvailable` 恒 true，不可信） |
| 判定 | `Send` 返回非 nil 错误 → 判定「当前不可用」 |
| 降级 | 立即改用**应用内提醒**（横幅 + 面板置顶 + 角标），托盘图标加状态点 |
| 告知 | 面板顶部提示一次：「系统通知不可用，已改为应用内提醒。请在 Windows 设置中允许 local-agent 发送通知。」每会话仅提示一次 |
| 恢复 | 后续发送成功即恢复系统通知（无需用户操作）；连续失败则保持降级 |

#### 7.10.2 应用已退出时点击通知

走 **冷启动激活**路径（7.3.4）：启动早期解析 `os.Args` 中的激活参数 → 还原任务与触发 → 执行对应动作（如「完成」「打开并定位」）→ 若动作需要 UI 则显示窗口。

注意：若应用**被设置成不常驻**（未启用托盘），此路径仍应工作——它只依赖「能启动并解析参数」，不依赖托盘。

#### 7.10.3 睡眠/关机期间的堆积

| 场景 | 处理 |
|---|---|
| 唤醒后多条已错过 | 合并为一条 N5，按 F2.7 策略（默认补发提醒） |
| 重启后 | Windows 会清空通知中心，**我方记录里仍是 `notified`** → 启动时把超过未处理窗口的 `notified` 按错过策略处理，避免状态永久悬挂（对齐 F8.2 崩溃恢复） |

#### 7.10.4 其他

| 情况 | 处理 |
|---|---|
| 多显示器 / 高 DPI | Toast 由系统管理，无需特殊处理；托盘图标需多尺寸资源 |
| 用户改系统时间 / 时区 | 决策树与状态不受影响；触发点按 F2.10 重算 |
| 通知点两次（用户手快） | 幂等去重（`triggerId`），第二次直接忽略并记日志 |
| Category 注册失败 | 不阻塞启动；记 N6 通知说明「通知按钮不可用」，并降级为无按钮通知 |
| 同一触发既被 snooze 又被完成 | 以**先到达者**为准，后者忽略（幂等） |

## 八、任务数据模型与配置持久化

### 8.0 结论速览

| 问题 | 结论 |
|---|---|
| 存储方案 | **JSON 整文件**，不引 SQLite（理由见 8.4；本机模块缓存中**无任何 sqlite 驱动**，引入需联网） |
| 落盘位置 | `~/.local-agent/tasks.json`（定义 + 全局配置，**单文件原子写**）；`~/.local-agent/task-runs/<taskId>/<runId>.json`（运行记录） |
| 全局配置放哪 | **同一个 `tasks.json`**，不放前端 localStorage（关键：调度器在窗口隐藏时也要读配置，后端读不到 localStorage） |
| 执行输出（完整 transcript）放哪 | **不重复存**，复用现有 `~/.local-agent/sessions/<id>.json`（每次自动执行本来就建独立会话），运行记录只存元数据 + `runSessionId` 指针 |
| `nextFireAt` 要不要持久化 | **不持久化**——它是由「触发规则 + 上次触发时间」**推导**出来的，启动时重算（这条同时解决了休眠/改系统时间后定时器卡死的问题） |
| 并发写入 | 单写者互斥 + **临时文件 + rename 原子替换**（现有 `os.WriteFile` 直接覆盖是弱点，见 8.5） |
| 版本迁移 | `version` 字段 + 迁移函数表 + 首迁备份；**高版本文件保护**（拒绝写入而不是降级覆盖） |
| 数据丢失防护 | 损坏文件改名 `tasks.json.broken`（沿用现有 `tools.json.broken` 惯例）+ `.bak` 首迁备份 |

---

### 8.1 数据模型的建模原则

**原则 1：严格区分「定义」「状态」「历史」三类数据。**

| 类别 | 内容 | 变化频率 | 存放 |
|---|---|---|---|
| **定义** | 用户配置的：名称、触发规则、策略、模板、工作区 | 极低（用户手改） | `tasks.json` |
| **状态** | 运行时推进的：上次/下次触发、上次结果、连续失败数、待处理 snooze | 高（每次触发） | `tasks.json`（但**只写必要的**，见 8.3） |
| **历史** | 每次触发的记录、结论、耗时、被拒权限 | 每次触发追加 | `task-runs/`（独立目录） |
| **推导值** | `nextFireAt` | 每次触发重算 | **不落盘** |

这三类混在一起是这类功能最常见的设计失误：历史会把定义文件撑爆，而状态的高频写入又会让定义文件频繁重写。第 5 步 F6.2 已按此拆分，这里落实为具体结构。

**原则 2：沿用仓库既有的「判别字段 + 分类配置」写法。**

`ToolSource` 的做法是 `Kind` 判别 + `CLI`/`HTTP`/`MCP` 三个**各自类型化的指针**，并且注释明确写了「不再是一个弱类型的 `json.RawMessage`」。触发规则是同一类问题（一次性/间隔/日历/工作日/cron 是互斥的几种形状），因此**照搬这个写法**，而不是塞一个大而全的结构体或一个裸 `map`。好处是编译期能穷尽分支，校验逻辑可以按 Kind 分派，JSON 也自解释。

**原则 3：模型里不放「前端才需要」的展示字段。**

例如「距下次触发还有多久」「是否已错过」这类，一律由前端或面板从 `lastFiredAt` / `nextFireAt` / 状态推导，不进模型。否则同一个事实有两个来源，托盘、面板、通知三处必然不一致（第 7.8 节已定下「状态只由插件单点驱动」）。

### 8.2 任务数据模型

#### 8.2.1 顶层结构

```go
// TaskFile 落盘结构（~/.local-agent/tasks.json）
// 沿用 tools.json 的 {version, ...} 对象形状，便于迁移与人工检查。
type TaskFile struct {
    Version  int           `json:"version"`
    Settings *GlobalConfig `json:"settings"`
    Tasks    []*Task       `json:"tasks"`
}
```

#### 8.2.2 Task（任务定义 + 状态）

```go
type Task struct {
    // ===== 身份 =====
    ID        string `json:"id"`                  // task_<UnixMilli>_<6位hex>
    Title     string `json:"title"`               // 任务名，同时是通知标题
    Note      string `json:"note,omitempty"`      // 提醒型的正文备注（也可作执行型的说明）
    Kind      string `json:"kind"`                // reminder | exec   （F5.1：不可互转）

    // ===== 何时触发 =====
    Trigger   *Trigger `json:"trigger"`
    Enabled   bool     `json:"enabled"`           // F1.4 启用/停用

    // ===== 触发后做什么 =====
    Reminder  *ReminderSpec `json:"reminder,omitempty"` // kind=reminder 时必填
    Exec      *ExecSpec     `json:"exec,omitempty"`     // kind=exec 时必填
    Notify    *NotifySpec   `json:"notify,omitempty"`   // 可覆盖全局通知策略（F7.7）
    Policy    *RunPolicy    `json:"policy,omitempty"`   // 错过补偿/重试/DND 逐任务覆盖（F2.7/F7.2）

    // ===== 运行时状态（由插件单点推进）=====
    State     *TaskState `json:"state,omitempty"`

    // ===== 元数据 =====
    CreatedAt int64 `json:"createdAt"`
    UpdatedAt int64 `json:"updatedAt"`
}
```

**字段与需求的对应**（第 3 步清单里的每一项都能落到这里）：

| 第 3 步要求 | 落点 |
|---|---|
| id | `Task.ID` |
| 标题 | `Task.Title` |
| 触发规则 | `Task.Trigger`（8.2.3） |
| 重复策略 | `Trigger.Recurring` 的结束条件 + `Task.Policy`（错过/重试） |
| 消息模板 | `ReminderSpec` / `ExecSpec` 的模板字段（8.2.4） |
| 关联会话/上下文 | `ExecSpec.ContextMode` + `ContextSessionID`（8.2.5） |
| 状态 | `Task.Enabled`（用户意图）+ `TaskState`（运行时，8.2.6）；**两者必须分开** |
| 上次与下次触发时间 | `TaskState.LastFiredAt` / `NextFireAt`（后者推导，8.3） |

> **`Enabled` 与 `State` 必须分开**：`Enabled=false` 是「用户要我别跑」，`State=aborted/failed` 是「跑失败了」。合成一个字段后，「暂停一个正在失败的任务」与「重新启用一个上次失败的任务」在语义上就无法区分了——这是状态机设计里最常见的坑。

#### 8.2.3 Trigger（触发规则）

```go
type TriggerKind string
const (
    TriggerOnce     TriggerKind = "once"      // 一次性（F2.1）
    TriggerInterval TriggerKind = "interval"  // 每 N 分钟（F2.2）
    TriggerRecurring TriggerKind = "recurring" // 每日/每周/每月/工作日（F2.3/F2.4）
    TriggerCron     TriggerKind = "cron"      // cron 表达式（F2.5）
)

// Trigger 判别字段 + 分类配置（照搬 ToolSource 的写法）
type Trigger struct {
    Kind TriggerKind `json:"kind"`

    Once      *OnceTrigger      `json:"once,omitempty"`
    Interval  *IntervalTrigger  `json:"interval,omitempty"`
    Recurring *RecurringTrigger `json:"recurring,omitempty"`
    Cron      *CronTrigger      `json:"cron,omitempty"`

    TZ string `json:"tz,omitempty"` // 创建时的时区标识（F2.9）；空=跟随系统
}

// OnceTrigger 一次性：绝对时间点
type OnceTrigger struct {
    At int64 `json:"at"` // Unix 毫秒
}

// IntervalTrigger 固定间隔
type IntervalTrigger struct {
    EveryMinutes int `json:"everyMinutes"` // 下限 1（F2.2 保护）
    AnchorAt     int64 `json:"anchorAt"`   // 首次锚点（Unix 毫秒），用于「从某一刻起每 N 分钟」
}

// RecurringTrigger 日历型：每日/每周/每月/工作日共用
type RecurringTrigger struct {
    Mode       string `json:"mode"`       // daily | weekly | monthly | workday
    TimeOfDay  string `json:"timeOfDay"`  // "HH:MM"（本地时间）
    DaysOfWeek []int  `json:"daysOfWeek,omitempty"` // weekly：0=周日…6=周六，多选
    DayOfMonth int    `json:"dayOfMonth,omitempty"` // monthly：1-31

    // 结束条件（重复策略的一部分）
    Until    int64 `json:"until,omitempty"`    // 到此时间止（Unix 毫秒）
    MaxFires int   `json:"maxFires,omitempty"` // 最多触发 N 次
}

// CronTrigger cron 表达式（F2.5）
type CronTrigger struct {
    Expr string `json:"expr"` // 支持范围见 6.9 未决问题 4
}
```

**为什么 `RecurringTrigger` 四种模式共用一个结构**：`daily`/`weekly`/`monthly`/`workday` 的差异**只在「哪些日子」**（`DaysOfWeek` / `DayOfMonth` / 是否跳过周末），时间点、结束条件、时区完全一致。拆成四个结构会让「下次触发点计算」出现四份几乎相同的代码——这正是第 4 步 ADR-6 想避免的「逻辑漂移」。

**`Until` / `MaxFires` 放在 Trigger 而非 Policy 里**：它们改变的是「还有没有下次」，属于触发规则本身；而 `Policy` 管的是「到点了但没能正常通知时怎么办」。判据是：**影响 `nextFireAt` 是否存在的放 Trigger，影响「这次触发怎么处理」的放 Policy**。

#### 8.2.4 ReminderSpec / ExecSpec（消息模板与执行配置）

```go
// ReminderSpec 提醒型任务
type ReminderSpec struct {
    TitleTemplate string `json:"titleTemplate,omitempty"` // 空=用 Task.Title
    BodyTemplate  string `json:"bodyTemplate,omitempty"`  // 空=用 Task.Note
}

// ExecSpec 执行型任务（B 层能力核心）
type ExecSpec struct {
    PromptTemplate string `json:"promptTemplate"` // 必填；支持占位符

    // 执行环境（F5.2）
    WorkspaceDir   string `json:"workspaceDir,omitempty"`   // 空=用默认工作区
    Model          string `json:"model,omitempty"`          // 空=用默认模型
    PermissionMode string `json:"permissionMode,omitempty"` // 空=用无人值守默认档

    // 无人值守权限策略（F5.4）
    AllowedTools []string `json:"allowedTools,omitempty"` // 预授权工具白名单（映射现有 EnabledTools）
    DenyMessage  string   `json:"denyMessage,omitempty"`  // 被拒时的说明（写入结果，替代裸拒绝）

    // 关联会话/上下文（F5.3）
    ContextMode      string `json:"contextMode,omitempty"`      // fresh（默认）| inherit
    ContextSessionID string `json:"contextSessionId,omitempty"` // ContextMode=inherit 时读取的会话
    InheritDepth     int    `json:"inheritDepth,omitempty"`     // 继承多少条历史消息（默认 0=不带历史）

    // 执行约束
    TimeoutSeconds int `json:"timeoutSeconds,omitempty"` // F5.5，默认 600
    SilenceUnless  string `json:"silenceUnless,omitempty"` // F5.9 静默条件：never|nonempty|keyword|changed
    SilenceKeyword string `json:"silenceKeyword,omitempty"`
}
```

**模板占位符（白名单，不做通用模板引擎）**

| 占位符 | 可用处 | 含义 |
|---|---|---|
| `{{task}}` | 两者 | 任务名 |
| `{{time}}` | 两者 | 本次触发时间（本地） |
| `{{date}}` / `{{weekday}}` | 两者 | 日期 / 星期 |
| `{{snoozeCount}}` | 提醒 | 本条已推迟次数 |
| `{{workspace}}` | 执行 | 工作区目录 |
| `{{lastSummary}}` | 执行 | 上一次运行结论摘要（实现「每天对比昨天」这类） |

> **刻意不做通用模板语言**（无循环、无条件、无函数调用）。理由：模板只有 6 个已知变量，通用引擎带来的是「用户能写出跑不通的模板，而错误只能在触发时才发现」；白名单占位符可以在**保存时**就校验出非法变量（对齐 F2.8「保存前自检」的精神）。渲染时对未知占位符**原样保留**而非报错，避免历史数据因变量更名而整条失效。

#### 8.2.5 关于「关联会话/上下文」的取舍

第 4 步 4.3 已定：**每次自动执行建独立会话**（隔离，不污染用户正在用的会话）。在此基础上，`ContextMode` 提供受控的上下文注入：

| 模式 | 行为 | 优先级 |
|---|---|---|
| `fresh`（默认） | 每次新建独立会话，不带历史 | **P0** |
| `inherit` | 新建独立会话 + 从 `ContextSessionID` 复制最近 `InheritDepth` 条消息作为前置上下文 | P1（对齐第 3 步 F5.2/F5.3 之外的补充） |

要点：
- `inherit` **只复制消息，不共享会话**：新会话是独立文件（`sessions/<newId>.json`），旧会话一字不改。这样「定时任务的污染」永远不会回流到用户会话
- 任务定义里**不存**运行时会话 ID；每次运行的会话 ID 存在**运行记录**里（8.2.7），因为一个任务会有很多次运行
- 这也让「查看结果」有了实现路径：运行记录 → `runSessionId` → 读出完整 transcript（F6.2）

#### 8.2.7 TaskState（运行时状态）

```go
type TaskState struct {
    // 触发时间线
    LastFiredAt int64 `json:"lastFiredAt,omitempty"` // 上次**实际**触发（Unix 毫秒）
    LastResult  string `json:"lastResult,omitempty"` // success|failed|missed|aborted|timeout|skipped|ignored
    LastError   string `json:"lastError,omitempty"`  // 可读失败原因（F6.5）

    FiredCount int `json:"firedCount,omitempty"`

    // 失败与重试（F8.4）
    ConsecutiveFailures int   `json:"consecutiveFailures,omitempty"`
    NextRetryAt         int64 `json:"nextRetryAt,omitempty"`

    // 待处理的 snooze（F2.6）：只保留最近一次
    Snooze *SnoozeState `json:"snooze,omitempty"`

    // 待补偿的错过（F2.7）：批量场景下可能多条，设上限防膨胀
    MissedPending []int64 `json:"missedPending,omitempty"` // 错过的计划触发时刻

    Notified *NotificationLedger `json:"notified,omitempty"`

    // 一次性任务是否已终结
    Finished bool `json:"finished,omitempty"`
}

type SnoozeState struct {
    Times      int   `json:"times"`      // 本条已推迟次数（面板显示「已推迟 2 次」）
    NextFireAt int64 `json:"nextFireAt"` // 临时触发时刻
}

type NotificationLedger struct {
    TriggerID  string `json:"triggerId"`  // task:<taskId>:<triggerId>（7.2.3）
    SentAt     int64  `json:"sentAt"`
    Action     string `json:"action,omitempty"`     // done|snooze10|open|ignored…（用户动作）
    ActionedAt int64  `json:"actionedAt,omitempty"`
    IgnoredAt  int64  `json:"ignoredAt,omitempty"`  // 超过未处理窗口自动转 ignored
}
```

> **`Notified` 台账是本模型里唯一「看似冗余」的字段，但它不可省**。第 7 步已核实：Windows 上通知**无法事后查询**（`RemoveDeliveredNotification` 等是空实现，也没有「已送达列表」API），所以「这条通知发出去之后用户处理了吗」只能自己记。没有它，`notified` 状态会永久悬挂（7.3.3、7.10.3）。

> **`MissedPending` 需要上限**（建议 50 条）：长时间关机后可能堆积大量错过项。超限时只保留最近 N 条 + 在前 N 条上标「还有更多」，避免状态文件膨胀。

#### 8.2.8 运行记录（历史，独立文件）

```go

    TaskTitle string `json:"taskTitle"` // 冗余存一份：任务删除后历史仍可读（8.7）

    TriggerKind string `json:"triggerKind"` // scheduled|snooze|manual|catchup|retry

    StartedAt int64  `json:"startedAt"`
    EndedAt   int64  `json:"endedAt,omitempty"`
    DurationMs int64 `json:"durationMs,omitempty"`

    RunSessionID string `json:"runSessionId,omitempty"` // ★ 完整 transcript 的指针（不重复存）
    Summary      string `json:"summary,omitempty"`      // 结论摘要（进通知正文）
    DeniedTools  []string `json:"deniedTools,omitempty"` // F5.4 被拒的操作（透明化）

```

`State` 取值（与第 7 步 7.8 状态机对齐）：`success` / `failed` / `aborted`（用户中止）/ `timeout`（超时）/ `missed`（错过未执行）/ `skipped`（策略跳过）/ `suspended`（被 DND 压制）。

**关键设计：`RunSessionID` 而非内嵌 transcript。** 每次自动执行本来就创建一个独立会话，而会话已经有完整的落盘机制（`sessions/<id>.json`，含消息、工具结果、diff）。运行记录只存指针，好处是：
- 不产生第二份可能不一致的执行记录
- 「查看结果」直接复用现有的会话详情 UI，不必为新格式再写一套渲染
- 会话保留策略（F6.4）天然同时管理了运行输出的保留

**为什么全局配置与任务放同一个文件**：
1. 两者**语义上强耦合**（`SnoozeDefault` 影响每个任务的 snooze、`DNDBehavior` 影响每个任务的触发处理），拆两个文件就会出现「改配置成功了、但任务文件写入失败」的不一致
2. 一次写、一次备份、一条迁移路径，维护成本最低
3. 全局配置项很少（<25 个），不会显著放大单文件体积

**为什么绝不放 localStorage（重要）**：现有前端偏好（`stores/setting.js`）走 localStorage，但**插件配置不能这么做**。调度器运行在 Go 侧，且**窗口可能处于隐藏状态**（常驻托盘的核心场景）——此时 localStorage 根本不存在，后端读不到配置。这个约束直接否决了「配置放前端」的省事做法。

### 8.3 推导值：`nextFireAt` 为什么不落盘

这是本步最重要的一个设计决定。

**若把 `nextFireAt` 持久化**，会同时引入三个问题：
1. **写放大**：每次触发都要重写 `tasks.json`（任务文件变成高频写入文件）
2. **休眠/改时间后失效**：持久化的 `nextFireAt` 是一个**绝对时刻**，机器休眠 3 小时后它已过去，而基于它的定时器不会自己醒过来——正是 F2.10 要防的「静默卡死」
3. **双份真相**：`nextFireAt` 与「触发规则 + `lastFiredAt`」可能不一致，且不一致时无法判断谁是对的

**改为推导**：

```
nextFireAt = NextAfter(trigger, now, state.LastFiredAt, state.FiredCount)
```

| 时机 | 行为 |
|---|---|
| 启动加载时 | **不读** `nextFireAt`，用 `lastFiredAt` + 规则现算 |
| 每次触发后 | 更新 `lastFiredAt` / `FiredCount`，重算下次 |
| 休眠唤醒 / 系统时间跳变 | 重新计算，**不信任任何已排定的绝对时刻** |
| 托盘 tooltip / 面板展示 | 实时算，不读缓存字段 |

代价：`nextFireAt` 每次展示都要算一次。但这是**纯函数计算**（微秒级），且任务数量是几十个量级，成本可以忽略。换来的是「永远不会因为休眠/改时间而卡死」——这笔交易非常划算。

**给 API 层的约定**：前端拿到的 `nextFireAt` 是**计算后填充的派生字段**（`json:"-"` 或单独的 DTO），而不是模型里的持久化字段。这样既满足展示需求，又不会有人误以为它需要落盘。

### 8.4 存储方案：JSON vs SQLite

| 维度 | JSON 整文件（采纳） | SQLite |
|---|---|---|
| 数据规模适配 | 任务几十条、运行记录数千条 → **远未到需要索引** | 优势要到万级以上才显现 |
| 依赖 | **零新增** | 需引入驱动；**本机模块缓存中无任何 sqlite 包**（已核实：`modernc.org`/`mattn`/`glebarez` 均无），引入需联网 |
| 与仓库一致性 | 完全一致（`models.json` / `tools.json` / `permissions.json` / `plans/` 全是 JSON） | 引入第二套持久化范式，维护者要懂两套 |
| 可检查性 | 直接可读、可 diff、可手工修、可 copy 给他人排错 | 需工具（sqlite3 CLI 或写代码） |
| 崩溃一致性 | 需自己做原子写（8.5） | ✅ 事务天然保证——**这是 SQLite 唯一的实质优势** |
| 并发写入 | 单进程 + 互斥锁足够 | 跨进程并发才是它的主场，而我们是**单实例** |
| 迁移 | 用 `version` 字段 + 迁移函数（8.6） | 需 schema migration 框架 |
| 崩溃恢复 | 显式实现（8.5） | 天然 |

**结论：选 JSON。** 决定性理由有三条：
1. **依赖**：SQLite 需联网引入，而第 4 步 ADR-5 的既定取向是「尽量避免新依赖」；为一个几十条记录的场景破例不值得
2. **单实例前提**：第 3 步 F4.3 已用 `SingleInstanceLock` 保证单实例，SQLite 最核心的「跨进程并发写」优势在这里用不上
3. **一致性优先**：仓库已有四套 JSON 持久化，再引一套 SQLite 会让维护者面对两套范式

**同时必须承认 SQLite 的优势并补偿它**：它的真正好处是「崩溃一致性」和「事务」，而这两种好处在 JSON 下需要**显式实现**——即 8.5 的原子写与 8.8 的崩溃恢复。若是依赖这些特性而不做补偿，JSON 方案会不如 SQLite。

### 8.5 并发写入策略

#### 8.5.1 写入者盘点（为什么需要认真处理）

虽然单实例，但**有 5 类并发写入者**（比表面看起来多）：

| # | 写入者 | 触发场景 |
|---|---|---|
| 1 | 调度器 goroutine | 到点推进状态、重算下次 |
| 2 | 前端桥接调用 | 用户在面板增删改任务 |
| 3 | 托盘菜单 | 快速新增提醒、暂停/恢复 |
| 4 | **通知回调** | 点「完成」/「稍后提醒」 |
| 5 | **冷启动激活进程** | 应用未运行时点通知 → 新进程启动（7.3.4） |

尤其第 5 类**真正跨进程**，容易漏掉。

#### 8.5.2 策略

**① 单一内存真相 + RWMutex。** 所有读走 `RLock`、所有写走 `Lock`；磁盘只在写路径上落。沿用 `PlanStore` / `ToolStore` 的既有做法，维护者无需学新东西。

**② 临时文件 + rename 原子替换。** 现有代码用的是 `os.WriteFile`（直接截断覆盖），中途崩溃会留下**半截 JSON**。对 `tools.json` 后果尚轻（有内置默认兜底），但对 `tasks.json` 意味着**用户的全部任务丢失**——不值得冒险：

```go
// 原子写：同目录临时文件 → sync → rename（rename 在同卷上是原子的）
func writeFileAtomic(path string, data []byte, perm os.FileMode) error {
    dir := filepath.Dir(path)
    tmp, err := os.CreateTemp(dir, ".tasks-*.tmp")
    if err != nil { return err }
    tmpName := tmp.Name()
    defer func() { _ = os.Remove(tmpName) }() // rename 成功后该文件已不存在，此处为失败路径兜底

    if _, err := tmp.Write(data); err != nil { tmp.Close(); return err }
    if err := tmp.Sync(); err != nil { tmp.Close(); return err } // 防「文件已改名但内容还在页缓存里就断电」
    if err := tmp.Close(); err != nil { return err }
    if err := os.Chmod(tmpName, perm); err != nil { return err }
    return os.Rename(tmpName, path)
}
```

要点：
- 临时文件必须**同目录**（`os.CreateTemp(dir, ...)`），否则 `rename` 可能跨卷而降级为复制，失去原子性
- **必须 `Sync()`**：只 rename 不 sync，断电后可能出现「文件名是新的、内容是空的」
- 临时文件名用 `.` 前缀（`.tasks-*.tmp`），避免被「扫描 `*.json`」的加载逻辑误读

**③ 用 dot-prefix 保护加载逻辑。** 加载时跳过非 `.json` 与 `.` 开头的文件（`PlanStore.loadAll` 已有「跳过损坏文件」的做法，这里再加一层前缀排除）。

**④ 冷启动进程绝不写。** 第 5 类写入者（冷启动激活）的职责被**严格限定为**「解析 `os.Args` → 通过 `SingleInstanceLock` 把参数交给既有实例 → 自身退出」，**它不打开也不写 `tasks.json`**。否则就会出现两个进程同时改同一个文件。这是 8.5.1 表格里最需要落到实现纪律的一条。

**⑤ 写合并（debounce）。** 连续的状态推进（例如同一秒多条错过补偿）不必逐条落盘：在内存改完后标记 dirty，由一个小的合并窗口（约 200ms）统一落盘一次。注意这是**性能优化而非正确性手段**——正确性由 ①②保证。

**⑥ 读-改-写不跨调用。** 所有变更都是「锁内改内存 → 锁内落盘」，禁止「读出来 → 出锁处理 → 再写回去」的模式（那才是丢更新的来源）。

### 8.6 版本迁移策略

#### 8.6.1 版本号与迁移函数表

```go
const TaskFileVersion = 1 // 版本历史见下

// 迁移函数表：key = 源版本，value = 把该版本升到 key+1
var taskMigrations = map[int]func(*TaskFile) (*TaskFile, string, error){}
```

**版本历史**（照 `ToolFileVersion` 的注释惯例记录每一次结构变更的原因）：

```
1  初版：TaskFile + Task + Trigger + TaskState + GlobalConfig
   （后续每次结构变更在此追加一行，说明「改了什么、为什么」）
```

#### 8.6.2 迁移流程

```
读取 tasks.json
 ├─ 文件不存在 / 空        → 用默认空结构初始化，落盘 v1
 ├─ 解析失败               → 改名 tasks.json.broken，用空结构启动（不阻塞应用）
 ├─ trimmed 以 "[" 开头    → 视为「裸数组」旧格式（tools.json 的 v1 就是这种），按 legacy 解析
 └─ 解析为 TaskFile
     ├─ version > 当前版本 → ★ 高版本保护：只读不写，并提示「配置由更新版本创建」
     ├─ version == 当前    → 直接用
     └─ version <  当前    → 顺序执行迁移函数
                             → 首迁前备份为 tasks.json.bak（已存在则**不覆盖**，保留最早的好备份）
                             → 逐版本升级 → 落盘为当前版本
                             → 迁移失败：保留原文件并提示，用「能解析出的部分」降级启动
```

**逐条要点**

| 要点 | 理由 |
|---|---|
| 首迁备份且**不覆盖已有 `.bak`** | 沿用 `toolstore.go` 的既有做法——用户的配置是资产，第一次迁移前的状态最值得留；若每次都覆盖，就丢掉了最早的可用备份 |
| **高版本保护**（`version > 当前` 时只读不写） | 用户可能回退到旧版本程序。若无保护，旧程序会按旧结构重写文件，**静默丢掉新版本的字段**。这是数据丢失里最隐蔽的一类 |
| 迁移失败**降级启动**而非拒绝启动 | 对齐 F8.3：一个坏文件不能让应用起不来。能解析出多少用多少 |
| 迁移必须**幂等** | 迁移中途崩溃后再次启动，要能从半迁移状态收敛，而不是反复损坏 |
| 保留未知字段（P2 建议） | 若用 `map[string]json.RawMessage` 兜住未识别字段，可让「旧程序读新文件」也不丢数据，配合高版本保护形成双保险 |

#### 8.6.3 迁移的测试要求（非功能，但必须写进方案）

迁移是**最容易出事故又最难测**的路径。要求：把每个历史版本的**真实文件样本**固化为测试夹具（`testdata/tasks_v1.json` 等），用「加载 → 断言迁移结果 → 断言可写回」的用例覆盖。这比读代码审查有效得多——`toolmodel.go` 里 `repairBuiltinExposure` 那个坑（内置工具被误判为 internal）正是靠「保留旧文件样本 + 断言」才可能在回归中发现的类型。

### 8.7 文件布局与生命周期

#### 8.7.1 目录结构

```
~/.local-agent/
├── tasks.json                      # 任务定义 + 全局配置（原子写、有 version、有备份）
├── tasks.json.bak                  # 首次迁移前的备份（仅在迁移时写一次）
├── tasks.json.broken               # 解析失败时的原文件（保留待排查）
├── task-runs/                      # 运行记录（历史）
│   ├── task_1750000000_a1b2c3/
│   │   ├── run_1750003600_x9y8.json
│   │   └── run_1750007200_k7m6.json
│   └── task_1750001111_d4e5f6/
│       └── run_1750004800_p1q2.json
├── sessions/                       # （已存在）执行型任务的完整 transcript 在这里
└── plans/                          # （已存在）计划
```

| 选择 | 理由 |
|---|---|
| 运行记录**按 taskId 分目录** | ① 单任务的历史删除/裁剪只需 `RemoveAll` 一个目录，代价远低于「扫描全目录找该任务的记录」；② 任务删除时能干净地连带清理；③ 手工排查时目录名自带归属 |
| 目录名用 **taskId 原值**（含前缀） | 避免额外映射；`task_` 前缀天然让目录名可辨识来源 |
| 不建全局索引文件 | 索引会带来「索引与实际文件不一致」的新问题；列表需求用「读目录 + 按需读文件」即可，量级允许 |
| 运行记录**不合并进 tasks.json** | 对齐原则 1 与 F6.2：历史是追加型且量大，混进定义文件会导致整文件频繁重写 |

#### 8.7.2 保留与清理（F6.4）

| 项 | 默认 | 执行时机 |
|---|---|---|
| 每任务运行记录条数 | 200 | 启动时 + 每 N 次运行后 |
| 运行记录天数 | 30 天 | 启动时 |
| 清理方式 | 按 `EndedAt` 从旧到新删除文件 | 清理动作**在锁外**做（只删文件，不改内存状态） |
| 关联的会话文件 | **不动** | 会话归 `sessions/` 的既有保留策略管。若删了运行记录却留下会话，属可接受的轻微残留；反之（删会话留指针）会产生悬空引用，因此运行记录读取时需容忍 `runSessionId` 指向不存在的会话（显示「该次运行的详细输出已按保留策略清理」） |

> 最后一条是**必须显式处理**的边界：清理策略让指针可能悬空，UI 与「查看结果」都要优雅降级，而不是报错或崩溃。

#### 8.7.3 删除任务时的数据处置（对齐 F1.3）

| 选项 | 行为 | 默认 |
|---|---|---|
| 保留历史（推荐） | 删除定义，保留 `task-runs/<taskId>/` | ✅ 默认 |
| 一并删除历史 | 同时 `RemoveAll` 该目录 | 二次确认框中显式勾选 |

配套要求：`RunRecord.TaskTitle` 冗余存一份任务名（8.2.8），这样任务删除后历史列表仍能显示「这是哪个任务跑出来的」，而不是一片空白 ID。

### 8.8 启动加载与崩溃恢复

按顺序执行（**顺序重要**，前者是后者的前提）：

| # | 步骤 | 说明 |
|---|---|---|
| 1 | 解析激活参数（`os.Args`） | 7.3.4 冷启动路径；**只记录，不写盘** |
| 2 | 初始化 `TaskStore`（加载 + 迁移 + 备份） | 8.6 |
| 3 | **修正残留的 `running` 状态** | 对齐 `PlanStore.loadAll`：上次遗留的执行中任务置为 `interrupted`，并补一条运行记录说明原因。理由：应用重启不支持断点续跑 |
| 4 | **收敛悬挂的通知台账** | `state.Notified` 存在且 `SentAt` 早于「未处理窗口」→ 转 `ignored` 并写记录（7.10.3）。防止 `notified` 永久悬挂 |
| 5 | **处理错过** | 用 `lastFiredAt` + 规则算出「从现在往前、错过且未被处理」的触发点 → 按 `CatchUp` 策略生成 `MissedPending`（带 50 条上限）。冷启动场景下**不立即弹通知**，等窗口/托盘就绪后再发 |
| 6 | 重建调度（计算所有任务的 `nextFireAt`） | 8.3 推导 |
| 7 | 注册通知 Category | 7.3.1；失败不阻塞 |
| 8 | 启动托盘 + 自启状态核对 | 自启开关与实际注册表项**双向核对**，不一致时以配置为准修正（防手工改注册表后的状态漂移） |
| 9 | 清理过期历史 | 8.7.2；放在最后，且失败不影响启动 |

**步骤 3–5 都属于「把上次非正常退出的后果收敛掉」**，是本方案里最容易被忽略、但直接决定「用户是否信任这个功能」的部分：一个显示「运行中」但永远不会结束的任务，比一个明确的「已中断」糟糕得多。

## 九、非功能需求与风险

### 9.0 结论速览

| 议题 | 结论 |
|---|---|
| 资源占用 | 常驻内存增量目标 **≤ 8 MB**（硬上限 15 MB，不含 WebView）；空闲 CPU **< 0.1%**；**禁止轮询**——按「睡到最近触发点」工作（这是 CPU 预算能否达标的关键） |
| 开机启动耗时 | 插件初始化预算 **≤ 150 ms**，且**不得阻塞窗口首帧**（分阶段/异步）；超时则先可用后补齐 |
| 离线可用性 | 提醒/调度/托盘/自启/通知**全部离线可用**（零网络依赖，已由 ADR-5/6 的「零新依赖」保障）；**执行型任务需模型服务**，离线时必须失败得清晰、可重试、不静默 |
| 权限 | **只写 HKCU，绝不需要管理员/UAC**；不装服务、不写 HKLM；无网络监听端口（选型带来的安全属性） |
| 隐私 | 数据全部本地（`~/.local-agent`）；**无任何遥测**；但要向用户明示「执行型任务的 prompt 与所读文件会随 agent 调用发往用户配置的模型服务」 |
| 安全上最大的风险 | **无人值守的自动执行会真的改工作区**——这是本插件唯一可能造成实质损害的能力，必须靠最小权限 + 预授权 + 串行 + 超时 + **连续失败熔断** + 可全局暂停 来约束 |
| 自动更新 | **本期不做**，但必须有明确的「升级路径说明」；升级带来的两个必做项：配置迁移（8.6）+ 旧注册表项清理（7.12） |
| 与 Windows 任务计划程序 | **本期不用它做主机制**（无 headless 入口、无法交互、要另建 IPC）；仅作为「应用退出后仍提醒」的演进路径，并把「开机自启」作为其当前替代 |
| 最高优先级的三个风险 | R1 托盘自研可行性、R2 Windows 通知在打包态的实际表现、R3/C1 无人值守执行失控 |

### 9.1 资源占用预算

#### 9.1.1 内存

| 项 | 估算 | 说明 |
|---|---|---|
| `TaskStore` 内存驻留 | < 200 KB | 几十个任务的定义 + 状态；**运行记录不驻留内存**（按需读文件，这是 8.7 分目录带来的直接收益） |
| 调度器 + 看门狗 goroutine | < 1 MB | 每个任务**不占一个 goroutine**，共用一个调度循环（见 9.1.2） |
| 托盘（图标 + 菜单 + 消息窗口） | < 2 MB | HICON + 菜单句柄 + 一个 message-only window |
| 通知适配与台账 | < 500 KB | Category 定义 + 未处理通知台账 |
| **合计增量目标** | **≤ 8 MB** | 硬上限 15 MB |

**硬性要求**：内存**不得随运行时间单调增长**。常驻场景（数周不重启 + 每天数十次触发）下，任何「每次触发累积一点」的泄露都会变成明显问题。具体防范：
- 运行记录**不进内存**（只写文件）
- 通知台账**必须有界**（每任务只保留最近一条，历史进运行记录）
- `MissedPending` 有界（8.2.7 的 50 条上限）
- 触发记录列表不缓存（列表查询走文件系统）

**测量方法**：① `net/http/pprof`（Go 自带，临时开启）heap profile 对比「启动后」与「运行 24 小时后」的 `inuse_space`；② Windows 任务管理器 / Process Explorer 的工作集与私有字节；③ soak 测试期间定时采样并断言「波动无趋势」。

#### 9.1.2 CPU

| 场景 | 目标 | 达成手段 |
|---|---|---|
| 空闲（等待中） | **< 0.1%** 平均 | **禁止轮询**。调度循环阻塞在「距最近一次触发的时长」上（F2.11），无触发时处于睡眠态 |
| 触发瞬间 | < 3%，单次 < 200 ms | 触发工作 = 算时间 + 组通知内容 + 落盘 + 调用通知 API，均为轻量操作 |
| 执行型任务运行中 | 不含在本预算内 | 那部分 CPU 属既有 agent 执行链（与手动使用同源） |
| 窗口隐藏/托盘态 | 与空闲态相同 | 隐藏窗口不产生额外开销（WebView 由 Wails 管理，不在本预算内） |

**关键设计约束（必须写进实现规范）**：

1. **绝不为每个任务起一个 `time.Ticker`**。几十个任务各自 tick 会带来每秒数十次无意义唤醒。正确做法：**单一调度循环**，算出「所有任务里最近的下次触发时刻」，睡到那一刻，醒来后处理所有到期任务并重算。
2. **不用「每秒检查一次」的兜底循环**。防漏靠的是「重算 + 单实例锁」，不是高频轮询。
3. **拖拽/前台状态等事件必须节流**（7.5.4 的 500 ms 合并），避免前端高频事件引发后端反复计算。

> 这条约束同时决定了「精度 ±5 秒」（F2.11）是可以接受的：±5 秒的误差来自「睡到整点后的一次性唤醒」，而不是「轮询间隔」。若改用轮询，精度上去了但 CPU 预算会失控——这是刻意的取舍。

#### 9.1.3 磁盘

| 项 | 预算 | 说明 |
|---|---|---|
| `tasks.json` | < 100 KB | 几十个任务的完整定义 + 全局配置 |
| `task-runs/` | 由保留策略封顶：`每任务条数 × 任务数 × 单条 ≈ 2 KB` | 默认 200 条 × 10 任务 ≈ **4 MB**；30 天清理再削一层 |
| 会话文件（执行输出） | **不新增预算** | 复用既有 `sessions/`，其增长属 agent 既有行为，由既有策略管理 |
| 日志 | < 10 MB（滚动） | 见 9.6.2 |

**要求**：磁盘增长必须**可预测且有上限**。无上限的历史是这类功能最常见的长期问题（用户半年后发现 `~/.local-agent` 涨到 GB 级）。

#### 9.1.4 开机启动耗时

| 阶段 | 预算 | 说明 |
|---|---|---|
| 解析激活参数（`os.Args`） | < 5 ms | 8.8 步骤 1 |
| 加载 `tasks.json`（含迁移） | < 30 ms | 几十个任务；迁移仅在版本落后时发生 |
| 收敛残留状态 + 计算错过 | < 30 ms | 8.8 步骤 3–5；`MissedPending` 有上限 |
| 重建调度（算全部 `nextFireAt`） | < 20 ms | 纯函数计算 |
| 注册通知 Category | < 20 ms | 主要是注册表读写 |
| 托盘初始化 | < 30 ms | 创建 message-only window + 加载图标 |
| **合计** | **≤ 150 ms** | 硬预算 |

**硬性要求：不得阻塞窗口首帧。** 理由：开机自启场景（F4.7/F4.8）下用户对「开机变慢」极度敏感，而插件只是应用的一个能力模块，**没有资格让主界面等它**。做法：
- 初始化**分阶段**：先做「窗口可用所必需」的部分（解析参数、读配置），其余（托盘、Category 注册、历史清理、错过补偿通知）**异步补齐**
- 每阶段带**超时保护**：某阶段超时则跳过并记日志，下次启动再补，**绝不无限等待**
- 错过补偿的通知**必须延迟到窗口/托盘就绪后**再发（8.8 步骤 5），否则冷启动时会先弹通知再出窗口，观感错乱

**测量方法**：在初始化各阶段打点（`time.Since`）并汇总到日志；用一个「总耗时」断言在开发期告警。

### 9.2 离线可用性

#### 9.2.1 能力分级

| 能力 | 离线可用 | 说明 |
|---|---|---|
| 调度与触发 | ✅ | 纯本地时间计算 |
| 提醒型通知（SC-1） | ✅ | 通知 API 是本地系统能力 |
| 托盘、开机自启、DND、暂停、历史 | ✅ | 全本地 |
| 任务创建/编辑（含 cron 预览） | ✅ | 表单与纯函数计算 |
| **自然语言创建任务**（F1.8） | ❌ | 需模型 |
| **执行型任务**（SC-2/SC-5） | ❌ | 需模型服务 |
| 任务完成通知（SC-3）/ 无响应告警（SC-4） | ✅（对方在跑） | 依赖运行中的 agent，与网络状况无关 |
| 通知点击动作 | ✅ | 本地路由 |
| 配置迁移/加载保存 | ✅ | 本地文件 |

#### 9.2.2 需求

1. **零网络依赖的构建与运行**：插件自身**不发起任何网络请求**。托盘（`Shell_NotifyIconW`）、自启（注册表）、通知（系统 API）、持久化（本地文件）全部走系统本地能力。这条是 ADR-5/ADR-6「零新依赖」的直接收益，必须被测试保护（见 9.11）。
2. **执行型任务离线时不得静默**：模型调用失败（断网/DNS/超时）必须：
   - 记入运行记录，`Error` 写明「网络不可达」（而非泛化的「失败」）
   - 按 `Policy.MaxRetries` 有限重试（指数退避）
   - 重试耗尽 → 发 L3 通知（N3）说明原因
   - **绝不**表现为「任务跑了、什么都没有、也不提示」
3. **离线不产生假成功**：执行型任务在无网络时应**快速失败**（连接失败即失败），而不是长时间挂起等超时。若模型客户端的超时设置过长，需为定时任务设置更短的连接超时上限。
4. **恢复后可自愈**：网络恢复不要求用户操作——下一次调度照常尝试。但**不补跑**错过的执行型任务（除非用户显式配 `CatchUp=notify` 且任务语义可补），**默认可补的只有提醒**。理由：补跑一次「每日汇总」可能跨越了隔天，语义已错。

### 9.3 权限与安全

#### 9.3.1 系统权限边界（硬约束）

| 项 | 约束 | 理由 |
|---|---|---|
| 注册表 | **只写 `HKCU`**（通知 Category、自启 `Run` 键、AUMID） | 无需管理员，不触发 UAC；Wails 通知实现本身也只在 HKCU 写（已核实） |
| 服务/驱动 | **不安装** | 装服务需提权、需卸载程序，与「能力模块」定位不符 |
| 网络监听 | **不监听任何端口** | 选型（进程内调用）带来的安全属性：本机其他进程无法调用插件能力（对比「本地 HTTP」方案会暴露一个可被任意本机进程访问的端点） |
| 提权 | **不请求** | 任何需要提权的路径都视为设计错误，应改设计而非加提权 |
| 文件写入范围 | 仅 `~/.local-agent` 与「任务指明的工作区」 | 工作区写入由既有权限网关约束，不由插件自行放开 |

#### 9.3.2 无人值守执行的权限风险（本插件的头号安全议题）

**风险本质**：定时任务在**无人可以确认**的时刻执行 agent，而 agent 有能力改代码、执行命令。这与「用户在屏幕前逐步确认」是完全不同的风险等级。

**缓解措施（必须全部落地，缺一不可）**

| # | 措施 | 说明 |
|---|---|---|
| 1 | **默认最小权限档** | 执行型任务的默认权限模式取**只读倾向档**；需要写入必须由用户显式升级 |
| 2 | **预授权白名单** | `ExecSpec.AllowedTools` 显式列出允许的工具；未列出的操作在无人值守下**降级为带理由的拒绝**（复用 `subagentEnforcer` 思路），并把被拒项写进 `RunRecord.DeniedTools`（透明化，不静默） |
| 3 | **默认并发 1 + 串行** | 防止多个任务同时改同一工作区（F5.6） |
| 4 | **超时强制中止** | 默认 600 秒，`timeout` 与 `failed` 语义分开（F5.5） |
| 5 | **连续失败熔断（安全阀）** | 连续失败达阈值（建议 3 次）→ **自动停用该任务**并发 L3 通知。没有这条，一个必然失败的任务会无限重试、持续消耗 token——这是最容易失控的失败模式 |
| 6 | **全局暂停** | 一键停掉所有任务（托盘 + 设置页），且**暂停状态持久化**（`GlobalConfig.Paused`），不会被重启绕过 |
| 7 | **可回滚** | 复用既有 checkpoint/diff 机制（`refs/local-agent/checkpoints`），使自动执行造成的改动**可回退**——这是「敢让它自动跑」的底气来源 |
| 8 | **可选执行前确认** | F5.10（P2）：到点先问「现在执行？」，适合高风险任务 |
| 9 | **默认不打开始通知** | 执行开始不发通知（L0），避免用户以为「有通知就等于跑完了」 |

**明确不做**：不提供「无人值守 + 完全放开权限」的一键配置。用户可以自己逐项配，但插件**不提供**这种便利——因为这正是最可能造成实质损害的组合。

#### 9.3.3 输入与外部数据的信任边界

| 输入源 | 是否可信 | 处理 |
|---|---|---|
| `tasks.json` | **不完全可信**（用户可手工编辑、可能被其他程序改） | 加载时**全量校验**（8.6 的 `normalize` 式做法）：触发规则合法性、路径存在性、模板占位符白名单、时间范围；非法项**跳过并告警**，不静默采用 |
| 通知回传的动作参数 | **不完全可信** | 严格白名单校验：动作 ID 必须在已注册集合内，`taskId` 必须存在，`triggerId` 必须匹配台账 → 不匹配则忽略并记日志。**必须幂等**（重复点击只生效一次） |
| 冷启动命令行参数（`os.Args`） | **不可信**（本机任意进程理论上可伪造） | 同上白名单 + 存在性校验；解析失败**静默退出**（不弹错、不写盘） |
| 模型输出（执行结论） | **不可信** | 结论只作为**文本**进通知与记录；**绝不**把模型输出当配置/路径/命令回填执行（防止「模型输出的 prompt 变成下一次的配置」这类自引用风险） |
| 工作区文件内容 | 不可信（就是被分析的对象） | 由既有 agent 权限网关与文件工具边界约束，插件不新增信任 |

#### 9.3.4 通知内容的信息暴露

Windows 通知会显示在**锁屏、通知中心、其他用户的桌面共享画面**上。因此：

- **敏感任务**需支持「正文只显示任务名」（不带结论、不带到路径）。建议：`NotifySpec` 增加一个「精简通知」开关（正文仅任务名）
- **默认不把工作区绝对路径写进通知正文**（路径会泄露项目名/用户名）
- 执行结论进通知前**截断**（F3.10 的 120 字）本身也起到减少暴露的作用

### 9.4 隐私与数据本地化

#### 9.4.1 数据流向声明（必须对用户可见）

| 数据 | 本地存放 | 是否会离开本机 | 说明 |
|---|---|---|---|
| 任务定义（名称、规则、模板、工作区路径） | `tasks.json` | ❌ | 仅本地 |
| 全局配置 | `tasks.json` | ❌ | 仅本地 |
| 运行记录（结论、耗时、被拒权限、token 用量） | `task-runs/` | ❌ | 仅本地 |
| 执行型任务的执行过程 | `sessions/` | 部分 | **prompt 与 agent 读取的文件内容会随既有 agent 调用发往用户配置的模型服务**——这与用户手动使用 agent 完全同源，但定时场景下用户容易忘记 |
| 遥测/埋点/崩溃上报 | — | ❌ | **完全不引入**，插件不得添加任何统计上报 |

#### 9.4.2 需求

1. **必须明示**：创建执行型任务时，在表单处给出一次性提示——「该任务会按计划自动调用模型，其所读文件内容会发送至你配置的模型服务；请勿把敏感仓库设为自动巡检目标」。这是**知情同意**，不是免责声明。
2. **必须可一键清空**：设置页提供「清空全部运行历史」（删 `task-runs/`），以及「删除任务时一并删历史」的选项（8.7.3）。
3. **不得把敏感内容写进日志**：日志只记任务 ID、动作、结果、耗时、错误摘要；**不记 prompt 全文、不记模型输出全文、不记文件内容**（这些在运行记录/会话里已有，日志再抄一份等于多一处泄露面）。
4. **数据文件权限**：建议 `tasks.json` 与 `task-runs/*.json` 用 **0o600**（仅当前用户可读）。注意这里**有意偏离**仓库既有 `tools.json` 的 `0o644`——因为运行记录可能含代码片段与结论摘要，比工具配置更敏感。
5. **不使用云端同步**：明确不做（4.4 Non-goals）；任务与历史不随任何账号漫游。

### 9.5 异常处理与失败重试

#### 9.5.1 分层异常表

**总原则（对应第 4 步原则三）**：任一层失败**不得**导致应用崩溃、退出或主流程阻塞；失败的可见形式是「记录 + 降级」，不是「静默」。

| 层 | 典型失败 | 影响范围 | 降级行为 | 是否重试 |
|---|---|---|---|---|
| 调度计算 | 规则非法（手工编辑导致） | 单任务 | 跳过该任务、标 `invalid`、面板高亮 | 否（等用户修） |
| 定时器/唤醒 | 系统时间跳变、休眠 | 全部任务 | 重算下次触发点（8.3） | 不适用 |
| 通知发送 | 系统通知被关闭、注册失败 | 单次通知 | 降级为应用内提醒 + 提示一次（7.10.1） | **是**（有限次） |
| 通知动作回传 | 参数畸形、台账不匹配 | 单次动作 | 忽略 + 记日志（幂等） | 否 |
| agent 执行 | 网络、模型报错、超时、权限拒绝 | 单任务 | 记 `RunRecord` + 发 N3（含原因） | **是**（按 `Policy`，带退避） |
| 持久化写盘 | 磁盘满、权限、文件被占用 | 全局 | **内存保留 + 标记 dirty + 稍后重写**；连续失败提示用户 | **是**（写入是必须成功的） |
| 托盘初始化 | 创建失败、图标缺失 | 常驻能力 | 应用仍可用，仅退化为「关窗即退出」；提示一次 | 否（下次启动重试） |
| 注册表（Category/自启） | 无权限、被安全软件拦 | 通知按钮/自启 | 通知降级为无按钮；自启开关状态显示「未生效」并说明 | 否（用户操作时重试） |
| 迁移 | 结构不识别、解析失败 | 全局 | 备份 + 降级启动（8.6.2） | 否 |
| 历史清理 | 删除失败 | 无（不影响功能） | 记日志，下次再清 | 是（下次启动） |
| 前端上报（焦点/全屏） | 长时间无上报 | 免打扰判定 | 按「不在前台」处理（宁可多提醒） | 不适用 |

#### 9.5.2 重试矩阵

| 失败类型 | 重试次数 | 退避 | 上限/熔断 | 备注 |
|---|---|---|---|---|
| 通知发送 | 2 次（间隔 1 s、3 s） | 固定短间隔 | 连续失败即降级到应用内（不再重试） | 通知是「即时性」能力，**过时重试无意义**（5 分钟后弹一条 5 分钟前的提醒是噪音） |
| 执行型任务 | `Policy.MaxRetries`（默认 **1**） | 指数（默认 1 min、5 min…） | **连续失败 3 次熔断并自动停用**（9.3.2 措施 5） | 必须有上限，否则烧 token |
| 持久化写入 | 立即重试 1 次 → 转 dirty 队列 | 下次状态变更时一并写 | 由独立的落盘 goroutine 兜底 | **不允许放弃**：写盘失败意味着用户配置可能丢 |
| 注册表写入 | 用户操作时重试 | 无 | 提示「未生效」 | 不后台反复尝试（可能被安全软件判为异常行为） |
| 历史清理 | 下次启动 | 无 | 无 | 无副作用 |

**两条硬要求**：
1. **重试必须有总上限**（次数上限 + 熔断），禁止无限重试——任何无限重试都是资源泄漏与成本失控的入口。
2. **重试要保留原语义**：一次「因失败而重试」的触发，其 `RunRecord.TriggerKind = retry`，且**不覆盖**原次的记录（保留完整时间线，便于排查「为什么反复失败」）。

#### 9.5.3 熔断与批量保护

| 场景 | 保护 |
|---|---|
| 单任务连续失败 | 3 次自动停用 + L3 通知（可一键重新启用） |
| 同时刻大量任务到期 | 合并通知（7.5.3），执行型任务**排队**（`MaxConcurrentRuns`） |
| 长时间关机后大量错过 | `MissedPending` 上限 50 + 汇总为一条 N5（不逐条补发） |
| 通知风暴（snooze 反复推迟） | 频率上限（7.5.5） |
| 写盘风暴（连续状态变更） | 写合并窗口约 200 ms（8.5.2 ⑤） |

### 9.6 可靠性与可观测性

#### 9.6.1 可靠性目标

| 指标 | 目标 | 说明 |
|---|---|---|
| 提醒准时率 | ≥ 99%（除机器休眠/关机期间） | 精度 ±5 秒（F2.11） |
| 「应用运行中 + 机器唤醒」条件下的漏提醒 | **0** | 这是可信度的底线，也是 F2.10/F8.5 要保证的 |
| 通知重复率 | 0 | 单实例锁 + 幂等 + 台账 |
| 插件导致的崩溃/退出 | **0** | panic 隔离（F8.1） |
| 插件导致的主流程阻塞 | 0 | 调度在独立 goroutine、执行串行、超时约束 |
| 数据丢失（用户任务定义） | 0 | 原子写 + 备份 + 高版本保护 |

#### 9.6.2 可观测性

| 项 | 设计 |
|---|---|
| 日志位置 | 建议 `~/.local-agent/logs/task.log`（滚动，< 10 MB，保留 3 份）；也可兼顾控制台输出（便于开发） |
| 日志级别 | 默认 info；`debug` 记录每次调度决策（「为什么这条没弹通知」——决策树命中哪一步） |
| **必须记录的关键事件** | 启动各阶段耗时、触发（计划时刻 / 实际时刻 / 延迟）、决策树命中分支、通知发送结果与降级、动作回传、执行开始/结束/中止、重试与熔断、迁移与备份、注册表操作结果 |
| 敏感信息 | **不记** prompt 全文、模型输出全文、文件内容（9.4.2） |
| 日志滚动与清理 | 防日志本身成为磁盘增长来源 |
| 可解释性（重要） | 免打扰最容易让用户困惑（「为什么它没提醒我」）。要求每次「未发系统通知」都有**可查的原因**：进 `RunRecord` 或 debug 日志，并在面板上以短理由展示（如「DND 顺延」「窗口在前台」「被暂停」） |

> 最后一条是可用性需求而非技术需求：「没提醒」比「提醒了」更需要解释。

#### 9.6.3 可测试性

| 被测对象 | 方式 |
|---|---|
| 下次触发点计算（`NextAfter`） | **纯函数单元测试**（无时间依赖，是整套逻辑里最值得测的部分）。必测：月末/闰年、跨月/跨年、每周多选、工作日跳过周末、`Until`/`MaxFires` 边界、夏令时（如启用） |
| 调度循环 | 可注入时钟（clock 接口）的集成测试：模拟「睡到点」与「时钟跳变」 |
| 决策树 | 表驱动测试：DND/暂停/前台/限流 组合 |
| 迁移 | 各历史版本 fixture 文件的加载回归（8.6.3） |
| 幂等与去重 | 重复注入同一动作/同一触发的测试 |
| 崩溃恢复 | 构造「残留 running」「悬挂 notified」「未处理的错过」的起始状态文件 |
| 资源占用 | soak 测试 + pprof 采样对比 |

### 9.8 自动更新与升级

#### 9.8.1 现状与本步决策

**现在没有任何自动更新机制**（项目里不存在 updater、无更新检查、无签名分发流程）。本步决策：**本期不做自动更新**。

理由：
1. Wails 桌面应用的自更新需要「下载 → 校验 → 替换正在运行的 exe → 重启」，而**替换运行中的 exe 在 Windows 上会被文件锁阻塞**，需要「重命名自身 + 重启」等技巧，属高风险改造
2. 单机自用场景下，手动替换 exe 完全可接受
3. 引入自更新会带来新的网络依赖与安全面（**下载通道的安全性是最大隐患**：无签名校验的自动更新等于给自己开后门），与 9.2 的「零网络依赖」和 9.3 的最小攻击面取向冲突

#### 9.8.2 但升级带来的两个问题必须处理（这是本步的实际交付）

| 问题 | 处理 |
|---|---|
| **配置结构演进** | 升级后首次启动必须执行迁移（8.6）与高版本保护；旧程序读新文件时不得静默丢字段 |
| **注册表残留** | 若 `outputfilename` 从 `wails-tmp` 改为 `local-agent`（6.9 未决问题 3），则旧键 `HKCU\Software\Classes\AppUserModelId\wails-tmp` 与 `HKCU\SOFTWARE\wails-tmp\NotificationCategories` 会残留，导致通知中心出现幽灵条目或重复来源。**升级时需一次性清理**（7.12 未决问题 2） |
| 自启项指向旧路径 | 若 exe 改名或移动目录，`HKCU\...\Run` 里的旧路径会失效 → 启动时**双向核对**自启开关与实际注册表项（8.8 步骤 8），不一致时以配置为准修正 |
| 版本可见性 | 设置页显示当前版本号，便于用户报错时定位（低成本高收益） |

#### 9.8.3 演进路径（若将来要做）

优先级从低到高：① 手动替换（现在）→ ② 交给包管理器（winget/scoop，占位）→ ③ 自建 updater（**必须带签名校验 + 校验和 + 失败回滚**）。

### 9.9 与 Windows 任务计划程序（Task Scheduler）的取舍

#### 9.9.1 对比

| 维度 | Windows 任务计划程序（schtasks） | 本插件（in-process 调度） |
|---|---|---|
| 应用未运行时能否触发 | ✅ **能**（这是它最大优势） | ❌ 不能（F4.9 明确不做） |
| 能否唤醒睡眠的机器 | ✅ 能（`-WakeToRun`） | ❌ 不能 |
| 可靠性（系统级） | ✅ 极高（系统服务） | 中（依赖应用进程存活） |
| 触发后能做什么 | 只能**启动一个程序/脚本** | ✅ 能操作窗口、发通知带按钮、调用 agent 执行链 |
| 交互能力（点按钮、稍后提醒、定位任务） | ❌ 完全没有 | ✅ 完整 |
| 需要 headless 入口 | ⚠️ **需要**（而本项目当前没有，6.8 已核实） | 不需要 |
| 与 agent 能力的关系 | 需另建 IPC/CLI 才能调用（ADR-3 的禁区） | ✅ 同进程直接调用 |
| 配置与调试 | 差（XML/命令行、系统 UI 里排查、不易版本化） | ✅ JSON 可读可 diff、面板可视 |
| 免打扰/DND/限流/合并 | ❌ 需自己另做 | ✅ 内置 |
| 权限 | 创建系统级任务常需管理员 | ✅ 只写 HKCU |
| 与托盘/通知状态的一致性 | 差（两处状态各说各话） | ✅ 单一真相 |

#### 9.9.2 取舍结论

**本期：不使用 schtasks 作为调度机制。** 决定性问题有三条：

1. **它无法完成「触发后要做的事」。** 我们需要的是「弹一条带按钮的通知 + 到点跑一次 agent + 点按钮回来改状态」，而 schtasks 只能「启动一个程序」。用它就得在这条链路上再架一层 IPC，成本远超收益（ADR-2/ADR-3 的同类推理）。
2. **它需要一个 headless 入口，而项目没有。** 要为它加子命令（`--run-task <id>`）就意味着改动主程序启动路径，且这个入口必须**独立于 Wails** 运行（不能依赖窗口/托盘），等于把「执行链」再抽一层——与 ADR-6「不另写循环」冲突。
3. **「应用未运行时提醒」这一唯一优势，已被其他手段部分覆盖**：开机自启（F4.7）+ 常驻托盘（F4.2）已能覆盖「重启后仍能提醒」的绝大多数实用场景；而 schtasks 带来的主要是「应用已被用户主动退出后仍要提醒」这一狭窄场景。

**但必须承认它是对的解法的地方**，并在文档中明确记录，避免将来误判为「我们已经解决了」：

| 场景 | schtasks 是正解 |
|---|---|
| 用户主动退出应用后仍需提醒 | ✅ 只有它可靠 |
| 需要唤醒睡眠中的机器执行任务 | ✅ 只有它能做 |
| 提醒的可靠性必须达到「系统级」 | ✅ 它的进程模型更可靠 |

#### 9.9.3 演进路径（何时重新评估）

当且仅当出现下列需求时，再引入 schtasks，且**引入方式必须是「兜底触发」而非「另一套调度」**：

```
需求：应用退出后仍能提醒（F4.9 升级为 P0）
方案：为 main.go 增加 headless 子命令 main.exe --run-task <taskId>
      ├─ 该子命令只做一件事：解析任务 → 发通知（不启动 Wails、不依赖托盘）
      ├─ schtasks 只负责「在计划时刻调用这个子命令」
      └─ 仍存在的风险：与主实例的通知去重（需用任务台账 + triggerId 跨进程幂等）
```

即便届时实现，也需保留 **ADR-3 的边界**：headless 子命令**不得**变成第二套执行链（它只做「发通知」与「唤醒主实例」，不自己跑 agent）。

| **R14** | cron 表达式子集与用户预期不符（F2.5） | 中 | 低 | 保存前**强制**显示未来 3 次触发预览（F2.8）；明确说明支持范围 | 用常见 cron 表达式样本做解析测试；对不支持的语法给出明确报错而非静默错算 |

### 9.11 验收与验证计划汇总

| 层次 | 内容 | 时机 |
|---|---|---|
| L1 单元 | `NextAfter` 的边界（月末/闰年/跨年/多选星期/工作日/`Until`/`MaxFires`）、模板渲染、校验逻辑 | 每个 PR |
| L2 集成 | 注入时钟的调度循环、决策树表驱动、幂等、崩溃恢复起始态 | 每个 PR |
| L3 迁移回归 | 各版本 fixture → 加载 → 断言 → 可写回 | 每个 PR；新增版本时补 fixture |
| L4 **打包态验证** | 真实 exe（非 `wails dev`）：通知来源名/图标/按钮、托盘四态与菜单、自启注册、冷启动激活 | 每个里程碑（对应 R2/R10） |
| L5 场景演练 | 休眠唤醒、改系统时间、断网、多实例、DND、暂停、熔断、坏配置文件 | 里程碑 M-B / M-D |
| L6 soak | 72 小时常驻：内存/句柄/磁盘趋势 | 里程碑 M-D 前后各一次 |
| L7 安全走查 | 权限边界（HKCU only / 无端口 / 无提权）、无人值守受限模式、通知内容暴露、日志不含敏感内容 | 里程碑 M-D |
| L8 构建与离线 | 无网环境构建；确认插件自身零网络请求（代码层审查 + 运行时抓包） | 里程碑 M-D |

> **L4 必须单列且必须做**：R2/R10 这类问题**只在打包态暴露**，在 `wails dev` 下全部正常。历史上「开发能跑、装完就坏」的桌面应用问题绝大多数属于这一类。

### 9.12 本步新增的未决问题

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | `tasks.json` / `task-runs` 是否用 `0o600`（有意偏离既有 `0o644`） | 一致性 vs 隐私 | 建议用 `0o600`，并在代码注释中写明偏离原因（与 `tools.json` 不同） |
| 2 | 连续失败熔断阈值（3 次）与是否「自动停用」还是「仅通知」 | 安全阀的激进度 | 建议先「自动停用 + L3 通知（可一键重启用）」；对确定要长期跑的任务可在 `Policy` 里放宽 |
| 3 | 执行型任务离线时是否快速失败（更短连接超时） | 失败反馈速度 | 建议是；需确认现有模型客户端的超时是否可单独设置 |
| 4 | 日志文件是否落盘（还是仅控制台） | 排查长周期问题的能力 | 建议落盘 + 滚动；「为什么没提醒」这类问题几乎只能靠历史日志回答 |
| 5 | 是否要为「敏感任务」引入「精简通知」开关 | 锁屏/共享屏信息暴露 | 建议做（一个布尔字段 + 正文只用任务名），成本极低 |
| 6 | `MissedPending` 耗尽时是否真的「补跑执行型任务」 | 语义正确性 | 建议不补跑（只补提醒），并在文档与 UI 中说明 |
