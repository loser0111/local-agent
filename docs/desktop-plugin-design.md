## 一、背景与目标

### 1.1 背景

local-agent 是一个基于 Wails v2.15 + Vue3 的**本地桌面 agent 应用**：已具备会话、工具循环、计划（plan）、子代理、技能、MCP、权限网关与差异归因（详见附录的现状调研）。

但在「**时间维度**」上存在明显空白——应用只能在用户主动使用时工作：

| 缺失能力 | 现状核实 |
|---|---|
| 定时调度 | **完全没有**。全仓库唯一的 `time.NewTicker` 用于流式分片 flush，无 cron、无任务队列、无「待触发任务」数据模型 |
| 桌面通知 | **后端零代码**。框架能力存在但未被使用 |
| 后台常驻 | `main.go` 是裸窗口配置：**没有**单实例锁、关窗隐藏、启动隐藏（Wails v2.15 其实自带这些能力，只是未启用） |

由此产生三类现实痛点：**容易漏事**（该做的事没人提醒）、**必须盯着**（长任务跑完不知道、卡住了不知道）、**重复劳动**（每天例行检查要手动发起）。

### 1.2 目标

**产品目标**：为 local-agent 增加一个**常驻侧翼**，把「在什么时间、做什么事」从人脑移交给系统，并在需要时复用 agent 的既有能力自动完成。

**一句话定位**：到点用 Windows 通知把人拉回来；需要动手的任务则复用主程序自动执行，把结果摘要推送回来。

**可度量的成功标准**：

| # | 标准 | 度量方式 |
|---|---|---|
| S1 | 设定一个提醒后，在「应用运行中 + 机器唤醒」条件下**不漏提醒** | 场景演练，漏报数 = 0 |
| S2 | 通知**不重复、不轰炸** | 同一触发重复通知数 = 0；超频率上限时被合并 |
| S3 | 关窗后台常驻，**重启后提醒依然有效** | 关窗、重启、休眠唤醒三种场景各验一次 |
| S4 | 自动执行的改动**可追溯、可回滚、可控** | 每次运行有记录；权限操作透明；可一键暂停；可经 checkpoint 回退 |
| S5 | 插件**不影响主程序** | 插件异常时应用不崩溃、聊天不卡顿 |
| S6 | 常驻开销**不成负担** | 内存增量 ≤ 8 MB、空闲 CPU < 0.1% |

### 1.3 范围

**本期要做（In Scope）**

- 定时提醒（一次性 / 每日 / 每周 / 每月 / 工作日 / 间隔 / cron）
- 到点**自动执行 agent 任务**（每日汇总、定时巡检等），结果摘要通知
- 事件驱动的**任务完成通知**与**长时间无响应告警**（含一键中止）
- Windows Toast 通知（含动作按钮、点击唤醒定位）
- 常驻托盘（关窗隐藏）、开机自启
- 免打扰时段、全局暂停、通知节制
- 触发记录与执行历史
- 任务管理 UI（创建/编辑/启停/删除/预览下次触发时间）

**明确不做（Out of Scope）**

1. 云端/远程调度、跨设备同步
2. 多用户、权限分级、审批流
3. 任务间依赖编排（DAG）、复杂重试策略矩阵
4. 第二条工具循环、第二套权限判定
5. 悬浮桌面小组件、任务栏数字角标（技术不可行或性价比低，理由见 4.6）
6. **应用完全退出后仍能提醒**（见 6.9，需系统级方案，列为演进）
7. 自动更新（见 6.8）
8. 改动现有会话/计划/子代理的行为语义（只新增，不重构主链路）

### 1.4 关键决策（已拍板）

| # | 决策 | 依据 |
|---|---|---|
| D1 | **能力边界 = B 层**：定时提醒 **+** 到点自动跑 agent 任务 | 相对纯提醒闹钟，才能实现「每日汇总」「定时巡检」这类真正省事的场景 |
| D2 | **常驻形态 = 常驻托盘**：关窗隐藏，后台继续计时并通知 | 否则机器一休眠/窗口一关就形同虚设 |
| D3 | **目标用户 = 本机开发者自用**：单机、单实例、单用户 | 不需要多用户隔离、配置分享、新手引导 |
| D4 | **落地形态 = 编译期内置能力模块**（非运行期热插拔） | Wails 是单进程、Go 代码编译期链接，无 `.dll` 热加载机制。故：代码组织保持插件化（单一 `Host` 接口依赖主程序），以便独立测试、独立开关、后续可剥离 |
| D5 | **进程模型 = 嵌入 agent 进程**；通信 = **进程内 Go 函数调用** | 关键理由：本项目**没有 headless/CLI 入口**，且 B 层能力要求同进程调用 agent 执行链（详见 4.1/4.2） |

> D5 是整个技术方案的支点：它否决了 Electron/Tauri/WinUI3/WPF（见 4.1），也否决了 HTTP/WebSocket/命名管道（见 4.2）。

### 1.5 术语

| 术语 | 含义 |
|---|---|
| 任务（Task） | 一条定时或事件驱动的配置，分**提醒型**与**执行型** |
| 触发（Trigger/Fire） | 任务的一次到期；一次任务可有多次触发 |
| 运行（Run） | 执行型任务的一次 agent 执行 |
| 宿主（Host） | 主程序；插件通过单一 `Host` 接口依赖它 |
| L 级别 | 通知打断级别 L0–L3（见 4.6） |
| DND | Do Not Disturb，免打扰时段 |
| 无人值守 | 执行型任务的常态：到点时无人在场，无法交互确认 |

## 二、用户场景

### 2.1 目标用户与使用前提

**用户画像**：使用 local-agent 做日常开发工作的开发者，机器即开发机。agent 窗口常驻但**大部分时间不在前台**。技术水位：看得懂 cron 但不想手写。核心诉求：**别漏事、别打扰、别乱动代码**。

**设计所依赖的前提（约束条件）**：

| # | 前提 | 对设计的约束 |
|---|---|---|
| A1 | 应用实现常驻托盘 | 若托盘不可行，插件须能降级为「仅应用开启期间生效」，不能整体不可用 |
| A2 | 机器会休眠/关机，任务可能**错过** | 必须有错过补偿策略，并把选择权交给用户 |
| A3 | 后台执行时**无人可问答** | 需用户**预先**声明允许范围；未允许的操作降级为带理由的拒绝 |
| A4 | 用户多数时间不在窗口前台 | 通知是一等公民；点击通知必须能唤醒并定位 |
| A5 | 单实例单用户 | 无需跨进程并发设计，但仍需 RWMutex（托盘/窗口/回调/冷启动并写） |
| A6 | 自动执行会烧 token、会改工作区 | 每次执行必须可追溯；默认不碰用户正在用的会话 |

### 2.2 核心场景

#### SC-1 定时提醒 · P0

| 项 | 内容 |
|---|---|
| 触发方式 | 时间驱动 |
| 用户故事 | 写代码时容易忘记「11:30 该去吃饭」「周五下班前交周报」，希望到点弹通知，点一下就能确认或推迟 |
| 期望行为 | ① 到点弹 Toast（标题=任务名，正文=备注）② 提供 `完成`/`推迟 10 分钟`/`打开 agent` ③ 点完成→标记本次 done；点推迟→生成 10 分钟后的临时触发 ④ 错过（休眠）后按策略处理，面板标「已错过」 |
| 验收要点 | 设一个 1 分钟后的提醒，全链路可跑；三种按钮各生效一次；休眠错过能被正确补偿 |
| 价值 | 验证「调度 → 通知 → 交互回调」主干，风险最低 |

#### SC-2 每日/每周工作汇总 · P1

| 项 | 内容 |
|---|---|
| 触发方式 | 时间驱动 + agent 执行 |
| 用户故事 | 下班前自动收到「今天改了什么、计划还剩哪些、有无未提交改动」的摘要，不用自己回忆 |
| 期望行为 | ① 到点触发一次 agent 运行（预设 prompt 采集 git 状态/计划进展）② 运行在**独立会话**，不污染当前会话 ③ 结论压缩成通知正文（超长截断），完整内容进历史可点开 ④ 失败时通知说明原因 |
| 验收要点 | 独立会话可验证（不出现在用户会话列表）；结果摘要出现在通知；完整输出可在面板查看 |
| 价值 | **本插件区别于普通闹钟的核心场景**，直接体现 D1 |

#### SC-3 任务完成通知（事件驱动，无定时）· P0

| 项 | 内容 |
|---|---|
| 触发方式 | 运行生命周期事件（非时间驱动） |
| 用户故事 | 让 agent 跑长任务后切去写别的，跑完了希望有通知，而不是回来发现早就结束了 |
| 期望行为 | ① 监听运行/计划/子代理的结束（成功、失败、被取消）② 不满足「不打扰」条件则弹通知，正文给结论 + 耗时 ③ 窗口前台时按策略只做应用内提醒 |
| 验收要点 | 长任务结束后有通知；点通知能定位；窗口前台时不弹系统通知 |
| 价值 | 零调度风险、收益立竿见影；是 SC-4 的基础设施 |

#### SC-4 长时间无响应告警 · P1

| 项 | 内容 |
|---|---|
| 触发方式 | 看门狗（心跳超时） |
| 用户故事 | agent 有时会卡住（等模型超时、等一个不该等的交互），我不想盯着，但 5 分钟毫无进展请告诉我，最好能一键中止 |
| 期望行为 | ① 监控「最后活动时间」（流式分片/工具调用/事件都算活动）② 超过阈值（默认 300s）弹通知 + `查看`/`中止` ③ 点中止走既有取消链路 ④ 同一运行**只弹一次**（防轰炸） |
| 验收要点 | 人为制造卡顿→有通知；点中止→运行状态正确转为中止；不重复弹 |
| 价值 | 把既有取消能力搬到用户手边；**风险点是误报**，阈值与「什么算活动」需明确定义 |

#### SC-5 定时巡检/自动化动作 · P2

| 项 | 内容 |
|---|---|
| 触发方式 | 时间驱动 + agent 执行 |
| 用户故事 | 每天开工时自动检查工作区状态（有无忘提交、TODO 多少），有问题就提醒 |
| 期望行为 | ① 到点跑预设 prompt ② 完整报告进历史 ③ 可配置**静默模式**：只在「需要关注」时才通知（避免每天一条「一切正常」） |
| 验收要点 | 静默条件生效（无问题时不通知）；权限默认只读倾向 |
| 价值 | 把 agent 变成「定时值班」；**风险点是权限与成本** |

#### 候选（本期不做）

SC-6 番茄钟/久坐提醒（与开发工作关联弱）；SC-7 IM/邮件外发通知（需凭据与网络）；SC-8 任务模板分享（自用无需求）。

### 2.3 场景优先级与依赖

| 场景 | 触发类型 | 优先级 | 依赖 | 对应里程碑 |
|---|---|---|---|---|
| SC-1 定时提醒 | 时间 | P0 | 托盘常驻、通知 | M-A / M-B |
| SC-3 任务完成通知 | 事件 | P0 | 运行生命周期事件 | M-C |
| SC-2 每日汇总 | 时间 + 执行 | P1 | SC-1 主干 + agent 执行入口 | M-D |
| SC-4 无响应告警 | 看门狗 | P1 | 运行心跳 + 取消接口（与 SC-3 同源） | M-C |
| SC-5 定时巡检 | 时间 + 执行 | P2 | SC-2 同路径 + 权限策略 | M-D |

## 三、功能需求

### 3.1 优先级定义

| 级别 | 含义 |
|---|---|
| **P0** | MVP 必须。缺失则不可用，或可用但**不可信**（漏提醒、误打扰、丢数据、拖垮主程序） |

### 3.3 MVP 边界（P0）

> **一句话**：能把任务建起来、按本地时间可靠触发、用系统通知提醒且能点按钮交互、关窗后台常驻、执行型任务能隔离地跑一次并留痕、出错不炸不掉不轰炸。

P0 中**最关键的 12 项**（评审重点，也是实现时最易出错处）：

| 需求 | 要点 | 为什么关键 |
|---|---|---|
| F2.8 下次触发预览 | 保存前展示未来 3 次触发时间 | cron/复杂周期**唯一的正确性自检手段** |
| F2.10 时钟跳变鲁棒 | 休眠唤醒/改系统时间后重算，不沿用旧定时器 | 否则静默卡死（S1 失败） |
| F3.4 通知可用性降级 | 以**发送结果**判定不可用（`IsNotificationAvailable` 在 Windows 恒 true，不可用） | 否则用户以为「插件坏了」 |
| F3.3 点击通知唤醒定位 | 复用 `WindowShow`（内部已含聚焦） | 通知的核心价值在此 |
| F4.2 关窗隐藏到托盘 | 插件启用时才生效 | 常驻的前提 |
| F4.3 单实例锁 | 复用 Wails 内置 | 防双进程双定时器 → 重复通知 |
| F5.3 独立会话隔离 | 每次执行新建独立会话 | 不污染用户会话（A6） |
| F5.4 无人值守权限 | 预授权 + 未允许操作降级为带理由拒绝 | 安全底线 |
| F5.6 串行执行（默认 1） | 防多任务同时改同一工作区 | 安全 + 成本 |
| F8.1 panic 隔离 | 触发与通知路径 recover | 不影响主程序（S5） |
| F8.3 坏配置容错 | 改名 `.broken` + 降级启动 | 一个坏文件不能让应用起不来 |
| F8.5 通知去重 | 单实例 + 幂等 + 台账 | 误打扰的主要来源 |

## 四、技术方案与架构

### 4.1 UI 框架选型：四个候选全部否决

| 维度 | Electron | Tauri | WinUI3 | WPF | **采纳：嵌入式 Wails 模块** |
|---|---|---|---|---|---|
| 体积增量 | ~120–200 MB | ~5–15 MB | ~20–40 MB | ~30–60 MB | **≈0**（复用现有 exe） |
| 内存增量 | 150–400 MB | 30–80 MB | 60–150 MB | 60–150 MB | **几 MB** |
| 与现有栈契合 | 差（Node） | 差（Rust） | 差（.NET） | 差（.NET） | **完全契合**（Go 同模块 + 现有 Vue） |
| 能否调用 agent 能力 | ❌ | ❌ | ❌ | ❌ | ✅ 同进程 |
| 结论 | 否决 | 否决 | 否决 | 否决 | **采纳** |

> 体积/内存为数量级估算，用于说明差异级别。

**否决是结构性的，不是成本性的**：

1. **无法调用 agent 执行链**——本项目**没有 headless/CLI 入口**（已核实全库无 `os.Args`/`flag`/`cobra`/`urfave`，`main.go` 只做 `wails.Run`）。外部进程要触发 agent，要么逼主程序长出一套 HTTP/CLI 对外接口（新增安全面），要么在外部框架里**重写工具循环**——后者正是 4.5 原则一明令禁止的。
2. **会造成双份调度与重复通知**——Wails 自带的 `SingleInstanceLock` 只约束 agent 自身，外部进程不受约束。
3. **资源开销与用户画像不符**——为定时提醒常驻 150–400 MB 不成比例。
4. **多一套构建/分发链路**——现在 `wails build` 一条命令出包。

**何时应重新评估**：若「应用退出后仍能提醒」（F4.9）升为 P0 → 选 **Tauri**；若需跨平台同等重要 → **Tauri/Electron**；若主要用户为非开发者 Windows 用户 → **WinUI3**。

### 4.2 进程模型与通信方式

#### 进程模型：嵌入式（in-process）

| 方案 | 结论 |
|---|---|
| **A. 嵌入 agent 进程** | ✅ **采纳**。可直接调 `agentRun`/`runControl`/权限网关；共享 store；零 IPC；单实例天然一致；开销几 MB |
| B. 独立 Go 进程 + IPC | ❌ 无法调 agent 执行链；双定时器风险；需自建 IPC 与协议版本管理；仍需托盘 |
| C. 同 exe 加子命令 | ❌ 需新增 headless 入口并改动启动路径；本期收益为零（留作演进，见 6.9） |

**取舍**：A 的唯一代价是「插件异常可能影响主进程」。但该风险已有成熟解法——子代理同样在主进程内跑完整工具循环，靠 panic 隔离、串行、超时约束控制在可接受范围。插件沿用**同一套约束**，不引入新风险类别。

**但要求「进程内模块化」**：插件放独立包（建议 `plugin/`），只通过单一 `Host` 接口依赖主程序 → 可独立测试、可整体停用、可后续剥离。

#### 通信方式：Go 函数调用

| 方式 | 是否使用 | 理由 |
|---|---|---|
| 本地 HTTP | ❌ | 需监听端口 → 本机任意进程可调（攻击面）、需处理端口占用/生命周期/鉴权。进程内调用零收益成本 |
| WebSocket | ❌ | 同上；且「服务端→前端」已有 `EventsEmit` |
| 命名管道 | ❌ | 只有独立进程才需要 IPC |
| 共享文件 | ❌（仅用于**持久化**，非通信） | `tasks.json` 是状态落盘，不是进程间通信机制；单实例下无需传消息 |
| CLI 调用 | ❌（**预留演进**） | 项目无 headless 入口。但这是「应用退出仍能提醒」的唯一可行路径（6.9） |
| **Go 函数调用（进程内）** | ✅ **主通道** | 零开销、编译期类型检查、可复用 `ctx` 取消链 |

#### 三条实际通道

**通道 1：插件 → 主程序（单一 `Host` 接口——本方案最重要的设计产物）**

```go
// plugin/host.go —— 插件对主程序的唯一依赖面
type Host interface {
    // 通知（主程序负责初始化，插件只负责内容与时机）
    NotifyAvailable() bool
    Notify(req NotifyRequest) error
    RegisterCategories(cats []NotifyCategory) error   // 启动时一次性注册（Windows 落 HKCU）
    OnNotifyResponse(fn func(NotifyResponse))         // 点击/按钮/回复回调

    // 窗口（点通知要唤醒并定位）
    RevealWindow(payload RevealPayload)

    // agent 执行（插件绝不自己跑循环）
    RunAgent(ctx context.Context, req RunRequest) (RunResult, error)
    CancelRun(runID string) error
    SubscribeRuns(fn func(RunEvent))                  // 运行生命周期（SC-3/SC-4）

    // 基础设施
    BaseDir() string
    AppVersion() string
}
```

`RunRequest` 关键字段：prompt、模型、工作区目录、**独立 sessionID**、无人值守权限策略、超时。

**通道 2：插件 → 前端（推送）**——沿用 `EventsEmit`，独立通道 `task:event`：

| 子类型 | 前端反应 |
|---|---|
| `task:changed` | 刷新列表 |
| `task:fired` | 列表状态更新、角标 |
| `task:run:started` / `finished` | 显示运行中 / 结果 |
| `task:missed` | 高亮「已错过」 |
| `task:notify:fallback` | 展示应用内提醒 + 原因 |

**通道 3：前端 → 插件（调用）**——沿用现有绑定机制（`App` 导出方法 → `frontend/wailsjs/go/main/App`），**无需手写任何 HTTP 客户端**。

### 4.4 与主程序的职责边界

| 能力 | 归属 |
|---|---|
| 单实例锁、关窗行为、托盘、退出确认 | **主程序**（插件只「声明需要常驻」；托盘是全局唯一资源） |
| 通知能力初始化、Category 注册 | **主程序**（启动时一次；插件不重复初始化，否则注册表/COM 注册重复） |
| 通知内容与时机 | **插件** |
| 时间源与调度（周期、错过补偿、去重） | **插件**（主程序不感知定时概念） |
| 任务模型与持久化 | **插件**（复用主程序的 JSON+RWMutex+目录约定） |
| agent 执行（工具循环、上下文、模型） | **主程序**（插件**不**自己跑循环） |
| 权限网关 | **主程序**（插件仅提供「无人值守策略」参数） |
| 运行取消 | **主程序**（插件按 runID 调用） |
| 事件推送机制 | 主程序提供机制，**插件定义自己的事件名** |
| UI 挂载点 | 主程序提供机制，插件提供组件与逻辑 |

**三条边界原则**

1. **调度归插件，执行归主程序**——插件到点后不自己实现任何工具调用/上下文拼装/模型调用，只调主程序执行入口。理由：主程序已为子代理把执行链参数化过（`agentRun` + `runRecorder`），再写一份循环必然漂移（本项目 P3 阶段已付过学费）。
2. **主程序管「生命周期与能力」，插件管「策略与内容」**——托盘、窗口、通知初始化不进插件；「几点提醒、说什么、按钮做什么、错过怎么办」全在插件。这样插件**整体可一键停用**，停用后主程序回到今天的样子。
3. **插件不得阻断主程序**——调度在独立 goroutine，任务**逐个串行 + panic recover**，任何单任务/通知异常只记历史，不得让应用崩溃或退出。

**灰区结论**

| 灰区 | 结论 |
|---|---|
| 关窗后隐藏还是退出？ | 主程序决定；**插件未启用时保持「关窗即退出」** |
| 点通知谁唤醒窗口？ | 主程序提供「显示并聚焦 / 定位到某任务」，插件调用 |
| 自动执行用哪个会话？ | **每次独立会话**（对齐子代理隔离），不写进用户正在用的会话 |
| 自动执行走不走权限网关？ | **走**，且走「无人值守」降级策略（未预授权 → 带理由拒绝） |
| 任务定义暴露给模型？ | 建议暴露为工具（`router`/`internal` exposure + 复用 `Ask` 回路确认）。强能力也是风险点，**须用户确认后落盘** |
| 执行历史放哪？ | 独立目录按次落盘；任务文件只存定义与最近状态 |
| 通知强度默认值？ | **克制**：仅「窗口不在前台」弹系统通知；后台静默任务默认不弹成功通知 |

### 4.5 通知与交互形态（要点）

> 详细设计见附录（第 7 节）。

**四种载体分工**

| 载体 | 定位 | 本期 |
|---|---|---|
| **Windows Toast** | 主载体。负责「**过去发生的事**」——到点了、跑完了、卡住了、错过了。必须能脱离窗口独立存在 | P0 |
| **托盘图标与菜单** | 负责「**我现在想操作**」——快捷入口，不打断 | P0 |
| **应用内提醒** | ① 系统通知不可用时的降级出口 ② 窗口前台时的克制形态 | P1 |
| 悬浮小组件/桌面卡片 | 常驻小桌面小窗 | **不做**（Wails v2 无多窗口 API，改动侵入启动路径；托盘 tooltip + 面板已覆盖同等信息） |
| 任务栏数字角标 | — | **不做**（Wails 无 badge/overlay API）→ 用托盘图标态 + 面板角标 + 窗口标题前缀替代 |

**六类通知模板**

| 类型 | 触发 | 级别 | 动作按钮 |
|---|---|---|---|
| N1 定时提醒 | 到点 | L2 | 完成 / 稍后提醒 / 打开 agent |
| N2 执行成功 | 执行型结束 | L1（默认可静默） | 查看结果 / 打开 agent |
| N3 执行失败 | 失败/超时/中止 | **L3** | 查看结果 / 重新执行 / 打开 agent |
| N4 无响应告警 | 心跳超阈值 | **L3** | 查看 / 中止 |
| N5 错过补偿 | 启动/唤醒发现错过 | L2（合并） | 全部知道了 / 稍后提醒 / 打开 agent |
| N6 系统事件 | 自启失败、配置损坏等 | L2 | 打开设置 |

**内容硬约束**：标题 ≤40 字符且含任务名；正文 ≤120 字；**结论必须前置**；失败必须带原因；不使用 `Subtitle`（Windows 不显示）；不用 Markdown。

**四级打断级别**

| 级别 | 名称 | 是否弹 | 合并 |
|---|---|---|---|
| L3 | 需立即处置（失败/无响应/配置损坏） | ✅ **即使前台也弹** | 不合并 |
| L2 | 常规提醒（定时/错过） | ✅（前台活跃降级为应用内） | 同时刻合并 |
| L1 | 低打扰（执行成功汇总） | ⚙️ 默认不弹，仅进面板 | 可合并 |
| L0 | 仅记录 | ❌ | 进面板 |

**免打扰统一决策树**（按序判定，命中即停）

```
一次触发到点
 ├─ 1. 任务级覆盖？     → 按该任务指定执行
 ├─ 2. 全局暂停开启？   → 按错过策略处理，不发通知
 ├─ 3. 级别 = L0？      → 仅记录
 ├─ 4. 全屏/演示中？    → 静默 → 应用内（降一级）
 ├─ 5. 处于 DND 时段？  → 按 DND 策略（默认「顺延到时段结束」）
 ├─ 6. 超频率上限？     → 合并进汇总通知
 ├─ 7. 主窗口前台活跃？ → 仅应用内提醒
 └─ 8. 否则            → 发系统 Toast
```

**提醒状态机**：`scheduled → firing → notified →（done | snoozed | ignored）`；另有 `missed` / `dnd-suppressed` / `skipped`；执行型另有 `running / succeeded / failed / aborted / timeout`。**状态只由插件单点驱动并持久化**（禁止前端推断，否则托盘/面板/通知三处不一致）。

**三个必须规避的坑（已核实）**

1. **无法程序化关闭或替换已送达通知**——Windows 侧 `RemovePendingNotification`/`RemoveDeliveredNotification` 全是空实现。故「完成标记」**不能更新已弹出的 Toast**；必须自维护「已发通知 + 未处理状态」台账，并用未处理窗口（默认 2h）把悬挂状态收敛为 `ignored`。
2. **点击通知是 Foreground 激活**（会拉起 exe）——既有实例走 `SingleInstanceLock.OnSecondInstanceLaunch(Args)`，**未运行时走冷启动 `os.Args`**；两条路径**必须复用同一套参数解析与动作分发函数**，否则会出现「应用开着时点通知有效、没开时无效」的隐蔽缺陷。
3. **`IsNotificationAvailable()` 在 Windows 上恒返回 true**——不可用作探测；改为**以发送结果为准的被动降级**（发送报错即降级到应用内提醒并提示一次原因）。

## 五、数据模型

### 5.1 建模原则

**原则 1：严格区分四类数据。**

| 类别 | 内容 | 变化频率 | 存放 |
|---|---|---|---|
| **定义** | 名称、触发规则、策略、模板、工作区 | 极低 | `tasks.json` |
| **状态** | 上次/下次触发、上次结果、连续失败数、待处理 snooze | 高 | `tasks.json`（只写必要的） |
| **历史** | 每次触发的记录、结论、耗时、被拒权限 | 追加 | `task-runs/` |
| **推导值** | `nextFireAt` | — | **不落盘** |

**原则 2：沿用仓库既有的「判别字段 + 分类配置」写法**（照搬 `ToolSource` 的 `Kind` + 类型化指针，而非弱类型 `map`/`RawMessage`）。触发规则的四种形状是同一类问题，编译期可穷尽分支。

**原则 3：模型不放「前端才需要」的展示字段**（如「还有多久」「是否错过」），一律由 `lastFiredAt`/状态推导。否则同一事实两个来源，三处显示必然不一致。

### 5.2 结构与关键字段

```go
// TaskFile 落盘结构（~/.local-agent/tasks.json）
type TaskFile struct {
    Version  int           `json:"version"`
    Settings *GlobalConfig `json:"settings"`
    Tasks    []*Task       `json:"tasks"`
}

type Task struct {
    ID    string `json:"id"`      // task_<UnixMilli>_<6位hex>
    Title string `json:"title"`
    Kind  string `json:"kind"`    // reminder | exec（不可直接互转）

    Trigger  *Trigger      `json:"trigger"`
    Enabled  bool          `json:"enabled"`            // 用户意图
    Reminder *ReminderSpec `json:"reminder,omitempty"`
    Exec     *ExecSpec     `json:"exec,omitempty"`
    Notify   *NotifySpec   `json:"notify,omitempty"`   // 逐任务通知覆盖
    Policy   *RunPolicy    `json:"policy,omitempty"`   // 错过/重试/DND 覆盖
    State    *TaskState    `json:"state,omitempty"`    // 运行时（与 Enabled 分开）

    CreatedAt int64 `json:"createdAt"`
    UpdatedAt int64 `json:"updatedAt"`
}

type Trigger struct {
    Kind      TriggerKind       `json:"kind"`      // once|interval|recurring|cron
    Once      *OnceTrigger      `json:"once,omitempty"`
    Interval  *IntervalTrigger  `json:"interval,omitempty"`
    Recurring *RecurringTrigger `json:"recurring,omitempty"`
    Cron      *CronTrigger      `json:"cron,omitempty"`
    TZ        string            `json:"tz,omitempty"`
}
```

**几个非显然但重要的字段决定**

| 决定 | 理由 |
|---|---|
| `Enabled` 与 `State` **必须分开** | `Enabled=false` 是「用户要我别跑」，`State=failed` 是「跑失败了」。合一后「暂停一个正在失败的任务」与「重启用一个上次失败的任务」语义无法区分 |
| `Until`/`MaxFires` 放 `Trigger` 而非 `Policy` | 判据：**影响「还有没有下次」的放 Trigger**；**影响「这次触发怎么处理」的放 Policy** |
| `RecurringTrigger` 四种日历模式**共用一个结构** | 差异只在「哪些日子」；拆四个结构会出现四份近似代码（ADR-6 想避免的漂移） |
| `ExportSpec.ContextMode`：`fresh`(默认)/`inherit` | `inherit` **只复制消息、不共享会话**，新会话独立文件，旧会话一字不改 → 定时任务的污染永不回流用户会话 |
| `TaskState.Notified` 台账**不可省** | Windows 通知无法事后查询（`Remove*`/`Delivered*` 空实现），「发出去后用户处理了吗」只能自己记，否则 `notified` 永久悬挂 |
| `MissedPending` 有**上限**（50） | 长时间关机后可能堆积大量错过项，需防状态文件膨胀 |
| 模板只用 **6 个白名单占位符** | `{{task}}`/`{{time}}`/`{{date}}`/`{{weekday}}`/`{{snoozeCount}}`/`{{workspace}}`/`{{lastSummary}}`。不做通用模板引擎 → 非法变量可在**保存时**校验 |

### 5.3 存储方案：JSON（否决 SQLite）

| 维度 | JSON（采纳） | SQLite |
|---|---|---|
| 规模适配 | 任务几十条、运行记录数千条 → 远未需要索引 | 优势要万级才显现 |
| 依赖 | **零新增** | 需驱动；**本机缓存无任何 sqlite 包**（已核实），引入需联网 |
| 与仓库一致性 | 与 `models.json`/`tools.json`/`permissions.json`/`plans/` 完全一致 | 引入第二套持久化范式 |
| 可检查性 | 可读、可 diff、可手修、可 copy 排查 | 需工具 |
| 崩溃一致性 | 需自己做原子写 | ✅ 天然（**其唯一实质优势**） |
| 并发写 | 单进程 + 互斥锁足够 | 跨进程并发才是主场，而我们是**单实例** |

**选 JSON 的三条决定性理由**：① SQLite 需联网引入，与「尽量避免新依赖」取向冲突；② F4.3 已用 `SingleInstanceLock` 保证单实例，SQLite 最核心的跨进程并发优势用不上；③ 仓库已有四套 JSON 持久化，再引一套会让维护者面对两套范式。

**同时补偿 SQLite 的优势**：其真正好处是崩溃一致性与事务，JSON 下需**显式实现**（5.6 的原子写 + 5.7 的恢复）；若不做补偿，JSON 会不如 SQLite。

### 5.4 目录布局

```
~/.local-agent/
├── tasks.json                    # 任务定义 + 全局配置（原子写、有 version）
├── tasks.json.bak                # 首次迁移前的备份（仅写一次，不覆盖）
├── tasks.json.broken             # 解析失败时的原文件（保留待排查）
├── task-runs/                    # 运行记录（历史）
│   └── task_<id>/run_<id>.json
├── sessions/                     # （已存在）执行型任务的完整 transcript
└── plans/                        # （已存在）
```

| 决定 | 理由 |
|---|---|
| 运行记录**按 taskId 分目录** | 单任务历史裁剪只需 `RemoveAll` 一个目录；任务删除可干净连带清理；目录名自带归属 |
| 运行记录**只存 `runSessionId` 指针**，不内嵌 transcript | 每次执行本来就建独立会话，完整输出已在 `sessions/`；避免两份可能不一致的记录，且「查看结果」直接复用现有会话详情 UI |
| **全局配置与任务同文件** | 语义强耦合（`SnoozeDefault`/`DNDBehavior` 影响每个任务），拆两个文件会出现「配置写成功、任务写失败」的不一致 |
| **配置绝不放 localStorage** | 调度器在 Go 侧、且窗口可能**隐藏**（常驻的核心场景），此时后端读不到 → 直接否决了省事做法 |
| `RunRecord.TaskTitle` 冗余存一份 | 任务删除后历史仍可读 |
| 清理后指针可能悬空 | 读取时**必须优雅降级**（显示「详细输出已按保留策略清理」），不报错不崩溃 |

### 5.5 `nextFireAt` 为什么**不落盘**

若持久化 `nextFireAt`，会同时引入三个问题：① **写放大**（每次触发重写文件）；② **休眠/改时间后失效**（它是绝对时刻，休眠 3 小时后已过去，定时器不会自己醒 → 正是 F2.10 要防的静默卡死）；③ **双份真相**（与「规则 + lastFiredAt」可能不一致且无法裁决）。

**改为推导**：`nextFireAt = NextAfter(trigger, now, lastFiredAt, FiredCount)`——启动加载时**不读**它、唤醒后重算、展示时实时算。代价是每次展示多一次纯函数计算（微秒级，任务数是几十个量级），换来「永不会因休眠/改时间而卡死」。

**给 API 层的约定**：前端拿到的是**计算后填充的派生字段**（`json:"-"` 或独立 DTO），不是模型里的持久化字段。

### 5.6 并发写入

**五类并发写入者**（比表面多）：① 调度 goroutine；② 前端桥接调用；③ 托盘菜单；④ **通知回调**；⑤ **冷启动激活进程**（真跨进程，最易漏）。

| # | 措施 |
|---|---|
| 1 | **单一内存真相 + RWMutex**（沿用 `PlanStore`/`ToolStore` 范式，维护者无需学新东西） |
| 2 | **临时文件 + `Sync` + `rename` 原子替换**（现有 `os.WriteFile` 直接截断覆盖，中途崩溃会留下**半截 JSON**——对 `tasks.json` 意味着用户任务全丢，不值得冒险）。要点：临时文件**必须同目录**（否则跨卷降级为复制）；**必须 `Sync()`**（防「文件名是新的、内容是空的」）；用 `.` 前缀避免被 `*.json` 扫描误读 |
| 3 | **冷启动进程绝不写盘**——其职责严格限定为「解析 `os.Args` → 交给既有实例 → 自身退出」。这是最需要落到实现纪律的一条 |
| 4 | **写合并（debounce ~200ms）**——性能优化而非正确性手段（正确性由 1/2 保证） |
| 5 | **读-改-写不跨调用**（禁止「读出→出锁处理→写回」，那才是丢更新的来源） |

### 5.7 版本迁移与崩溃恢复

**迁移流程**

```
读取 tasks.json
 ├─ 不存在/空          → 默认空结构初始化，落盘 v1
 ├─ 解析失败           → 改名 tasks.json.broken，用空结构启动（不阻塞应用）
 ├─ version > 当前     → ★ 高版本保护：只读不写，提示「配置由更新版本创建」
 ├─ version == 当前    → 直接用
 └─ version < 当前     → 顺序执行迁移函数表
                        → 首迁前备份 .bak（已存在则**不覆盖**，保留最早的好备份）
                        → 逐版本升级 → 落盘
                        → 失败：保留原文件 + 提示 + 用「能解析出的部分」降级启动
```

**要点**：① 首迁备份**不覆盖**已有 `.bak`（用户配置是资产，最早的好备份最值钱）；② **高版本保护**——用户回退到旧版本程序时，旧程序按旧结构重写会**静默丢掉新字段**，这是数据丢失里最隐蔽的一类；③ 迁移**必须幂等**（中途崩溃后能收敛）；④ 建议用 `map[string]json.RawMessage` 兜住未知字段，与高版本保护形成双保险。

**崩溃恢复（启动 9 步，顺序重要）**

| # | 步骤 |
|---|---|
| 1 | 解析激活参数（`os.Args`）——**只记录，不写盘** |
| 2 | 初始化 `TaskStore`（加载 + 迁移 + 备份） |
| 3 | **修正残留的 `running`** → 置 `interrupted` 并补记录（应用重启不支持断点续跑） |
| 4 | **收敛悬挂的通知台账** → 超未处理窗口的 `notified` 转 `ignored` |
| 5 | **处理错过** → 按 `CatchUp` 生成 `MissedPending`（带上限）；**不立即弹通知**，等托盘/窗口就绪 |
| 6 | 重建调度（计算所有 `nextFireAt`） |
| 7 | 注册通知 Category（失败不阻塞） |
| 8 | 启动托盘 + **自启开关与实际注册表项双向核对** |
| 9 | 清理过期历史（失败不影响启动） |

> 步骤 3–5 都是「收敛上次非正常退出的后果」，最易忽略但**直接决定用户是否信任这个功能**：一个显示「运行中」但永远不会结束的任务，比明确的「已中断」糟糕得多。

## 六、非功能需求

### 6.1 资源占用

| 项 | 目标 | 达成手段 |
|---|---|---|
| 常驻内存增量 | **≤ 8 MB**（硬上限 15 MB） | 运行记录**不进内存**；台账有界；`MissedPending` 有上限 |
| 空闲 CPU | **< 0.1%** | **禁止轮询**——单一调度循环睡到「最近的下次触发时刻」 |
| 触发瞬间 CPU | < 3%，单次 < 200 ms | 触发 = 算时间 + 组内容 + 落盘 + 调 API |
| 插件初始化 | **≤ 150 ms** | 分阶段 + 每阶段超时保护 |
| 磁盘 | `tasks.json` < 100 KB；`task-runs/` 由保留策略封顶（默认 200 条 × 任务数 × ~2 KB） | 保留策略 + 30 天清理 |
| 日志 | < 10 MB（滚动，3 份） | 防日志自身成为增长源 |

**三条硬要求**

1. **内存不得随运行时间单调增长**（常驻场景下任何「每次累积一点」都会变成问题）。测得方式：pprof heap 对比「启动后」与「运行 24h 后」+ **72h soak 测试**。
2. **绝不为每个任务起一个 `time.Ticker`**，也**不用「每秒检查」兜底**——几十个任务各自 tick 会带来每秒数十次无意义唤醒。
3. **不得阻塞窗口首帧**——开机自启场景下用户对「开机变慢」极敏感，插件只是能力模块，**没有资格让主界面等它**：先做「窗口可用所必需」的部分，其余（托盘、Category、历史清理、错过通知）异步补齐，每阶段带超时。

> 这条约束决定了「精度 ±5 秒」（F2.11）是可接受的取舍：误差来自「睡到点后的一次性唤醒」，而不是轮询间隔。若改用轮询，精度上去了但 CPU 预算会失控。

### 6.2 离线可用性

| 能力 | 离线可用 |
|---|---|
| 调度、提醒通知、托盘、自启、DND、暂停、历史、任务 CRUD、cron 预览 | ✅ |
| 通知点击动作、配置迁移 | ✅ |
| **自然语言创建任务**、**执行型任务** | ❌ 需模型服务 |
| SC-3/SC-4 | ✅（与网络无关，依赖运行中的 agent） |

**要求**
1. **插件自身不发起任何网络请求**（托盘/自启/通知/持久化全走系统本地能力）。这是「零新依赖」的直接收益，须被测试保护（无网构建 + 运行时抓包）。
2. **执行型任务离线时不得静默**：记「网络不可达」（而非泛化「失败」）→ 有限重试 → 耗尽后发 L3 说明原因。**绝不**表现为「跑了、什么都没有、也不提示」。
3. **离线快速失败**，不长时间挂起等超时。
4. **恢复后自愈**（下次调度照常尝试），但**不补跑**错过的执行型任务（补跑「每日汇总」可能已跨天，语义已错）；**默认可补的只有提醒**。

### 6.3 权限与安全

**系统权限边界（硬约束）**

| 项 | 约束 |
|---|---|
| 注册表 | **只写 `HKCU`**（通知 Category、自启 `Run`、AUMID）→ 无需管理员、不触发 UAC |
| 服务/驱动 | **不安装** |
| 网络监听 | **不监听任何端口**——本机其他进程无法调用插件能力（对比「本地 HTTP」方案会暴露可被任意本机进程访问的端点） |
| 提权 | **不请求**；需要提权的路径视为设计错误，应改设计而非加提权 |
| 文件写入 | 仅 `~/.local-agent` 与任务指明的工作区（后者由既有权限网关约束） |

**无人值守执行的权限风险（本插件头号安全议题）**

风险本质：定时任务在**无人可以确认**的时刻执行 agent，而 agent 能改代码、执行命令——与「用户在屏幕前逐步确认」是完全不同的风险等级。

**缓解措施（必须全部落地）**

| # | 措施 | 说明 |
|---|---|---|
| 1 | **默认最小权限档** | 执行型任务默认取只读倾向档，需写入必须显式升级 |
| 2 | **预授权白名单** | `ExecSpec.AllowedTools` 显式列出；未列出的操作在无人值守下**降级为带理由的拒绝**（复用 `subagentEnforcer` 思路），被拒项写进 `RunRecord.DeniedTools` |
| 3 | **默认并发 1 + 串行** | 防多任务同时改同一工作区 |
| 4 | **超时强制中止** | 默认 600s；`timeout` 与 `failed` 语义分开 |
| 5 | **连续失败熔断** | 连续 3 次失败 → **自动停用该任务** + L3 通知。没有这条，必然失败的任务会无限重试持续烧 token |
| 6 | **全局暂停** | 一键停用所有任务，且**暂停状态持久化**，不被重启绕过 |
| 7 | **可回滚** | 复用既有 checkpoint/diff 机制，使自动执行的改动可回退——这是「敢让它自动跑」的底气 |
| 8 | 执行前确认（P2） | 到点先问「现在执行？」，适合高风险任务 |
| 9 | 默认不打开始通知 | 避免「有通知就等于跑完了」的误判 |

**明确不做**：不提供「无人值守 + 完全放开权限」的一键配置——用户可逐项自配，但插件**不提供**这种便利，因为这是最可能造成实质损害的组合。

**信任边界**

| 输入源 | 可信? | 处理 |
|---|---|---|
| `tasks.json` | 不完全 | 加载时**全量校验**（规则合法性/路径存在性/占位符白名单/时间范围）；非法项跳过并告警 |
| 通知回传动作参数 | 不完全 | 严格白名单 + 存在性校验 + **幂等**（重复点击只生效一次） |
| 冷启动 `os.Args` | **不可信** | 同上校验；解析失败**静默退出**（不弹错、不写盘） |
| 模型输出（执行结论） | **不可信** | 只作为**文本**进通知与记录；**绝不**把模型输出当配置/路径/命令回填执行 |
| 工作区文件内容 | 不可信 | 由既有权限网关与文件工具边界约束 |

**通知内容暴露**：Toast 会显示在锁屏、通知中心、共享画面。要求：敏感任务支持「正文只显示任务名」；**默认不把工作区绝对路径写进正文**；结论进通知前截断（120 字）。

### 6.4 隐私与数据本地化

| 数据 | 本地位置 | 是否离开本机 |
|---|---|---|
| 任务定义、全局配置、运行记录 | `tasks.json` / `task-runs/` | ❌ |
| 执行型任务的执行过程 | `sessions/` | **部分**：prompt 与所读文件内容会随既有 agent 调用发往用户配置的模型服务 |
| 遥测/埋点/崩溃上报 | — | ❌ **完全不引入** |

**要求**
1. **必须明示**：创建执行型任务时一次性提示——「该任务会按计划自动调用模型，所读文件内容会发送至你配置的模型服务；请勿把敏感仓库设为自动巡检目标」。这是**知情同意**，不是免责声明。
2. **必须可一键清空**：设置页提供「清空全部运行历史」，以及「删除任务时一并删历史」选项。
3. **日志不记敏感内容**：只记任务 ID、动作、结果、耗时、错误摘要；**不记 prompt 全文、不记模型输出全文、不记文件内容**。
4. 数据文件建议 **`0o600`**（有意偏离既有 `0644` 并在代码注释说明——运行记录可能含代码片段）。
5. 不做云端同步。

### 6.5 异常处理与重试

**总原则**（对应 4.4 原则三）：任一层失败**不得**导致应用崩溃、退出或主流程阻塞；失败的可见形式是「记录 + 降级」，**不是静默**。

| 层 | 影响范围 | 降级行为 | 重试 |
|---|---|---|---|
| 调度计算（规则非法） | 单任务 | 跳过并标 `invalid`、面板高亮 | 否 |
| 定时器/唤醒 | 全部 | 重算下次触发点 | 不适用 |
| 通知发送 | 单次 | 降级为应用内 + 提示一次 | 是（有限） |
| 通知动作回传 | 单次 | 忽略 + 记日志（幂等） | 否 |
| agent 执行 | 单任务 | 记记录 + 发 N3（含原因） | 是（带退避） |
| **持久化写盘** | 全局 | 内存保留 + 标 dirty + 稍后重写 | 是（**不允许放弃**） |
| 托盘初始化 | 常驻能力 | 应用仍可用，退化为「关窗即退出」+ 提示 | 否（下次启动） |
| 注册表 | 按钮/自启 | 降级无按钮通知 / 显示「未生效」 | 用户操作时 |
| 迁移 | 全局 | 备份 + 降级启动 | 否 |
| 历史清理 | 无 | 下次再清 | 是（下次启动） |

**重试矩阵**

| 类型 | 次数 | 退避 | 熔断 |
|---|---|---|---|
| 通知发送 | 2（1s、3s） | 固定短间隔 | 连续失败即降级（**通知是即时性能力，过时重试无意义**——5 分钟后弹 5 分钟前的提醒是噪音） |
| 执行型任务 | 默认 **1** | 指数 | **连续 3 次熔断并自动停用**（必须有上限，否则烧 token） |
| 持久化写入 | 立即 1 次 → dirty 队列 | 下次变更时 | 不允许放弃（写盘失败意味着配置可能丢） |
| 注册表写入 | 用户操作时 | — | 提示「未生效」，不后台反复尝试 |
| 历史清理 | 下次启动 | — | 无副作用 |

**两条硬要求**：① 重试必须有**总上限**（次数 + 熔断），禁止无限重试（任何无限重试都是资源泄漏与成本失控的入口）；② **重试保留原语义**（`TriggerKind=retry` 且**不覆盖**原次记录，保留完整时间线）。

**批量保护**：同时刻大量任务 → 合并通知 + 执行排队；长时间关机 → `MissedPending` 上限 50 + 汇总一条；snooze 循环 → 频率上限；连续状态变更 → 写合并窗口。

### 6.6 可靠性目标与可观测性

| 指标 | 目标 |
|---|---|
| 提醒准时率 | ≥ 99%（除休眠/关机期间），精度 ±5s |
| 「应用运行中 + 机器唤醒」下的漏提醒 | **0**（可信度底线） |
| 通知重复率 | 0 |
| 插件导致的崩溃/退出 | **0** |
| 插件导致的主流程阻塞 | 0 |
| 数据丢失（任务定义） | 0 |

**可观测性**
- 日志建议落盘 `~/.local-agent/logs/task.log`（滚动）；默认 info，debug 记录**每次调度决策**（「为什么这条没弹通知」——决策树命中哪一步）
- 必须记录：启动各阶段耗时、触发（计划/实际/延迟）、决策树命中分支、通知发送结果与降级、动作回传、执行开始/结束/中止、重试与熔断、迁移与备份、注册表操作结果
- 不记：prompt 全文、模型输出全文、文件内容
- **可解释性（可用性需求）**：每次「未发系统通知」都要有**可查原因**并在面板展示短理由（「DND 顺延」「窗口在前台」「被暂停」）。「没提醒」比「提醒了」更需要解释。

### 6.8 自动更新

**决策：本期不做。**

理由：① Windows 上替换运行中的 exe 会被文件锁阻塞，需「重命名自身 + 重启」等高风险改造；② 单机自用下手动替换 exe 完全可接受；③ 自更新引入网络依赖与安全面，**无签名校验的自动更新等于给自己开后门**，与 6.2「零网络依赖」和 6.3 最小攻击面取向冲突。

**但升级必然带来的问题必须处理（本节的实质交付）**

| 问题 | 处理 |
|---|---|
| 配置结构演进 | 升级后首启执行迁移（5.7）+ 高版本保护 |
| **注册表残留** | 若 `outputfilename` 由 `wails-tmp` 改名，旧键 `HKCU\...\AppUserModelId\wails-tmp` 与 `HKCU\SOFTWARE\wails-tmp\NotificationCategories` 会残留 → 通知中心出现幽灵/重复来源，**需一次性清理** |
| 自启项指向旧路径 | exe 改名/移动会使 `HKCU\...\Run` 旧路径失效 → 启动时**双向核对**并修正 |
| 版本可见性 | 设置页显示版本号（低成本高收益） |

**演进路径**：手动替换（现在）→ 包管理器（winget/scoop，占位）→ 自建 updater（**必须带签名校验 + 校验和 + 失败回滚**）。

### 6.9 与 Windows 任务计划程序的取舍

| 维度 | schtasks | 本插件 |
|---|---|---|
| 应用未运行时能否触发 | ✅ **能**（其最大优势） | ❌ 不能 |
| 唤醒睡眠机器 | ✅ 能 | ❌ 不能 |
| 可靠性 | ✅ 系统级 | 中（依赖进程存活） |
| 触发后能做什么 | 只能**启动一个程序** | ✅ 通知带按钮、调用 agent、点按钮改状态 |
| 需要 headless 入口 | ⚠️ **需要**（项目当前没有） | 不需要 |
| 与 agent 能力的关系 | 需另建 IPC/CLI（ADR-3 禁区） | ✅ 同进程 |
| DND/限流/合并/交互 | ❌ 需另做 | ✅ 内置 |
| 权限 | 常需管理员 | ✅ 只写 HKCU |

**结论：本期不用它做主机制**，三条决定性理由：① 它**无法完成「触发后要做的事」**（只能启动程序，要用就得再架一层 IPC）；② 它**需要一个项目没有的 headless 入口**，为它加子命令意味着改动主程序启动路径且该入口须独立于 Wails 运行（与「不另写循环」冲突）；③ 其唯一优势（应用未运行时提醒）已被**开机自启 + 常驻托盘**覆盖绝大多数实用场景。

**但必须记录它才是正解的场景**（避免将来误判为「已解决」）：用户主动退出应用后仍要提醒、需唤醒睡眠机器、要求系统级可靠性。

**演进路径（何时重新评估）**：当 F4.9 升为 P0 时引入，且方式必须是「**兜底触发**」而非「另一套调度」：

```
为 main.go 增加 headless 子命令 main.exe --run-task <taskId>
 ├─ 该子命令只做一件事：解析任务 → 发通知（不启动 Wails、不依赖托盘）
 ├─ schtasks 只负责「在计划时刻调用它」
 └─ 风险：与主实例的通知去重（需台账 + triggerId 跨进程幂等）
```

即便届时实现，也须保留 ADR-3 边界：headless 子命令**不得**变成第二套执行链。

| **W9 历史与可观测** | 历史列表/详情/保留清理 + 日志落盘与滚动 | `history.go`、日志 | W7 | 悬空 `runSessionId` 优雅降级；清理不误删；日志不含敏感内容 | 2–3 |
| **W10 前端完整实现** | 表单 + 时间规则编辑器 + **触发时间预览** + 列表/详情/历史 + 通知跳转定位 + 设置 tab | Vue 组件 | W2–W9 | 保存前必显示未来 3 次触发；从通知能直达任务详情 | 4–5 |
| **W11 硬化与验收** | soak + 坏文件演练 + 迁移回归 + 安全走查 + 打包态回归 + 无网构建 | 验收报告 | W1–W10 | 7.2 的 L4–L8 全部通过 | 3–4 |
| **W12 可选增强（P1/P2）** | cron 表达式、任务模板、自启开关 UI、静默模式、历史筛选、导入导出、模型工具集成（F10.3） | 增补功能 | W11 | 按各需求验收要点 | 6–8 |

### 附录 C：架构决策记录（ADR）汇总

| # | 决策 | 主要理由 | 接受的代价 |
|---|---|---|---|
| ADR-1 | 插件以「进程内 Go 模块」落地 | 需同进程调用 agent 执行链；项目无 headless 入口 | 需 panic 隔离；无法脱离 agent 独立运行 |
| ADR-2 | 不引入任何外部 UI 框架 | 结构性不兼容（4.1）+ 资源不成比例 | 托盘需自研 |
| ADR-3 | 通信为 Go 函数调用 + `EventsEmit` | 零 IPC 开销与安全面 | 插件与主程序需同版本编译 |
| ADR-4 | 插件对主程序依赖收敛到单一 `Host` 接口 | 可测试、可停用、可剥离 | 需先定义并稳定接口 |
| ADR-5 | 托盘自研（shell32），暂不引第三方 | 零新依赖、无联网要求 | 自写 Windows 消息处理，需一次验证（W0） |
| ADR-6 | 执行型任务复用 `agentRun`，不另写循环 | 避免与主循环漂移（P3 已付学费） | 受主程序执行链能力边界约束 |
| ADR-7 | 每次执行建独立会话 | 隔离，不污染用户会话 | 会话数量增长，需保留策略 |
| ADR-8 | 本期不做「应用退出后仍提醒」 | 需 headless 入口或系统服务，成本高 | 退出后提醒失效，须在 UI 明确告知 |
