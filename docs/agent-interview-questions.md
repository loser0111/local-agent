## 一、基础概念（Q1–Q8）

### Q1. 什么是 AI Agent？和普通 LLM 对话有什么区别？
- **LLM 对话**：用户问一句，模型答一句，无自主行动能力。
- **AI Agent**：以 LLM 为大脑，具备**感知、规划、工具调用、记忆**能力，能自主拆解任务、多步执行、根据反馈调整行动，直到完成目标。
- 核心区别：Agent 有**自主性**（autonomy）和**行动力**（actuation），不只是回答，还能"做事"。

### Q2. Agent 的核心组件有哪些？
经典四组件：
1. **Brain（大脑）**：LLM 作为推理引擎，负责理解、规划、决策。
2. **Memory（记忆）**：短期（对话上下文）+ 长期（向量库存储的历史经验）。
3. **Tools（工具）**：搜索引擎、API、代码执行器、数据库查询等。
4. **Planning（规划）**：任务拆解、反思、多步推理。
- 进阶还包含：Observation（观察环境反馈）、Action（执行动作）。

### Q3. Agent 和 Workflow（工作流）有什么区别？
| 对比 | Workflow | Agent |
|------|---------|-------|
| 流程 | 预定义固定路径 | LLM 自主决定路径 |
| 控制权 | 代码/规则控制 | LLM 控制 |
| 确定性 | 高，路径可预测 | 低，路径不可预测 |
| 适用 | 明确步骤的重复任务 | 开放式、需要灵活决策的任务 |
- 经验：能确定步骤用 Workflow（更可控），需要灵活决策用 Agent。生产中常**混合使用**。

### Q4. 什么是 Agent Loop（智能体循环）？
Agent 的核心运行模式——**观察 → 思考 → 行动 → 观察**的循环：
```
Thought（思考）→ Action（调用工具）→ Observation（观察结果）→ Thought → ... → Final Answer
```
- 每轮 LLM 决定下一步做什么，调用工具拿到结果后再决定下一步。
- 循环终止条件：LLM 输出 Final Answer，或达到最大步数限制。

### Q5. Agent 的常见应用场景有哪些？
1. **编程助手**：Cursor/Copilot，读写文件、执行代码、调试。
2. **数据分析**：自然语言转 SQL、生成图表、数据洞察。
3. **客服/运维**：工单处理、日志排查、自动运维。
4. **浏览器自动化**：网页操作、信息采集、表单填写。
5. **知识问答**：RAG + Agent，检索 + 多步推理。
6. **多 Agent 协作**：软件开发（PM + 开发 + 测试）。

### Q6. 什么是 Agent 的自主性（Autonomy）？
- **目标驱动**：用户给一个目标，Agent 自主规划路径。
- **自适应**：执行中遇到错误能调整策略（如工具调用失败换另一个）。
- **多步执行**：不是一问一答，而是多轮推理 + 行动。
- **终止判断**：Agent 自己判断任务是否完成。
- 区别于脚本：脚本是确定路径，Agent 是 LLM 动态决策路径。

### Q7. LLM Agent 和传统软件机器人（RPA）有什么区别？
| 对比 | RPA | LLM Agent |
|------|-----|-----------|
| 驱动 | 规则/脚本 | LLM 推理 |
| 灵活性 | 低，固定流程 | 高，自然语言理解 |
| 异常处理 | 需预定义 | 可自主应对 |
| 开发成本 | 需录制每个步骤 | 自然语言描述目标 |
| 准确性 | 高（确定性） | 依赖 LLM 能力 |

### Q8. Agent 系统中 System Prompt 的作用是什么？
- 定义 Agent 的**角色、能力边界、行为规范**。
- 声明可用工具列表和调用格式。
- 设定输出格式约束（如必须用 JSON）。
- 设定安全边界（不该做什么）。
- 经验：System Prompt 是 Agent 的"岗位说明书"，直接影响行为质量和稳定性。

## 二、推理机制（Q9–Q16）

### Q9. 什么是 ReAct（Reasoning + Acting）？
ReAct 是 Agent 最经典的推理框架，让 LLM 交替进行**推理（Thought）和行动（Action）**：
```
Thought: 用户要查北京天气，我需要调用天气 API
Action: get_weather(city="北京")
Observation: {"temp": 25, "weather": "晴"}
Thought: 拿到结果了，可以回答用户
Answer: 北京今天 25 度，晴天。
```
- 核心思想：**先想清楚再做，做完再想下一步**。
- 优势：推理可追溯（Thought 链可见）、可纠错（Observation 反馈修正）。

### Q10. ReAct 和 CoT（Chain-of-Thought）有什么区别？
| 对比 | CoT | ReAct |
|------|-----|-------|
| 核心 | 纯推理链 | 推理 + 行动交替 |
| 工具调用 | 不调工具 | 可调工具获取外部信息 |
| 外部信息 | 依赖模型内部知识 | 可实时获取 |
| 适用 | 数学推理、逻辑题 | 需要实时信息、工具的复杂任务 |
- CoT 是"只想不做"，ReAct 是"边想边做"。

### Q11. 什么是 Plan-and-Execute（先规划后执行）？
两阶段架构：
1. **Planner**：LLM 先把任务拆成一系列子步骤（计划）。
2. **Executor**：逐步执行每个子步骤，可调用工具。
3. **Replanner**：执行后根据结果重新规划（动态调整）。
- 与 ReAct 的区别：ReAct 是**每步都想**（一步一action），Plan-and-Execute 是**先全量规划再执行**。
- 优势：减少 LLM 调用次数（规划一次执行多步），适合复杂多步任务。
- 劣势：初始计划如果不合理，后续执行都白做（需 Replanner 修正）。

### Q12. 什么是 Tree of Thoughts（ToT）？
- CoT 是**线性思维链**，ToT 是**树状思维**。
- 在每个推理节点生成多个候选思路，用评估函数打分，选最优路径（BFS/DFS）。
- 适合需要探索多种可能性的任务（如数学证明、创意写作、博弈推理）。
- 劣势：LLM 调用次数指数级增长，成本高、速度慢。

### Q13. ReAct 和 Plan-and-Execute 怎么选择？
| 维度 | ReAct | Plan-and-Execute |
|------|-------|------------------|
| 推理频率 | 每步都调 LLM | 规划一次 + 执行多步 |
| LLM 调用 | 多 | 少 |
| 灵活性 | 高，每步可调整 | 中，需 Replanner |
| 适合任务 | 简单、步骤少、需灵活 | 复杂、步骤多、可预规划 |
| 成本 | 高 | 低 |
- 经验：步骤 ≤5 用 ReAct，步骤多且可预规划用 Plan-and-Execute，混合用最佳。

### Q14. Agent 如何做任务拆解（Task Decomposition）？
1. **指令拆解**：LLM 把"帮我分析这份报告"拆成"读取→摘要→提取关键点→生成图表"。
2. **递归拆解**：每个子任务再拆，直到可执行（DAG 任务图）。
3. **拆解策略**：按步骤（顺序）、按角色（分工）、按模块（功能）。
- 关键：拆解粒度要合适，太粗 LLM 执行不了，太细浪费 LLM 调用。

### Q15. 什么是 Reflection（反思机制）？
Agent 执行后**自我评估**，发现错误并修正：
- **Self-Reflection**：LLM 审查自己的输出，判断是否正确。
- **External Feedback**：外部工具/环境给出反馈（如代码执行报错）。
- **Reflexion 框架**：反思 → 记录教训 → 下次尝试时参考记忆中的教训。
- 场景：代码生成失败 → 反思错误原因 → 修正代码再试。
- 价值：显著提升复杂任务成功率，但增加 LLM 调用。

### Q16. Agent 执行中如何处理失败和重试？
1. **工具调用失败**：捕获异常 → 反馈给 LLM → LLM 决定换工具或换参数重试。
2. **结果不满足**：Reflection 判断不达标 → 重新规划或调整参数。
3. **最大重试限制**：设置 max_iterations/max_retries，避免死循环。
4. **降级策略**：多次失败后降级处理（返回默认值/转人工）。
5. **超时控制**：单步超时和全局超时，防止 Agent 卡死。

## 三、工具调用与 Function Calling（Q17–Q24）

### Q17. 什么是 Function Calling？
- OpenAI/各大模型提供的**结构化工具调用能力**：模型根据用户意图，输出一个符合预定义 schema 的 JSON，包含函数名和参数。
- 流程：声明可用函数 → LLM 判断是否需要调用 → 输出函数调用 JSON → 代码执行函数 → 结果返回 LLM → LLM 生成最终回答。
- 示例：
```json
// LLM 输出
{"name": "get_weather", "arguments": {"city": "北京"}}
```

### Q18. Function Calling 和 Tool Use 有什么区别？
- **Function Calling**：OpenAI 最初的设计，一次调用一个函数。
- **Tool Use**：Anthropic Claude 等扩展，支持**并行调用多个工具**，更通用。
- 本质：都是让 LLM 输出结构化的工具调用指令，术语混用。
- 现代 Agent 框架（LangChain/LlamaIndex）已统一为 Tool Use，支持多工具并行。

### Q19. Agent 如何定义一个工具（Tool）？
核心要素：
1. **name**：工具名称（LLM 用来选择）。
2. **description**：自然语言描述（LLM 判断何时用）。
3. **inputSchema**：参数 JSON Schema（类型、必填、枚举）。
4. **handler**：实际执行函数（代码）。
- 经验：description 写清楚"什么时候用"和"不用什么"，LLM 选择准确率大幅提升。

### Q20. LLM 选错工具或参数错误怎么办？
1. **Prompt 优化**：工具描述更清晰，加 few-shot 示例。
2. **参数校验**：代码层校验 LLM 输出的 JSON schema，不合法则反馈错误让 LLM 重试。
3. **错误反馈循环**：工具执行失败 → 错误信息返回 LLM → LLM 修正重试。
4. **限制工具数**：工具太多 LLM 容易选错，建议 ≤10 个，多了用工具路由/嵌套 Agent。
5. **Structured Output**：用 JSON Mode / Structured Output 强制 LLM 输出合法 JSON。

### Q21. 什么是 MCP（Model Context Protocol）？
- Anthropic 提出的**开放协议**，标准化 LLM 与外部工具/数据源的连接。
- 类比：MCP 是 AI Agent 的"USB-C 接口"——统一工具接入标准。
- 架构：MCP Server（提供工具/资源）↔ MCP Client（Agent 端）。
- 价值：工具一次开发，多个 Agent 框架通用；解耦 Agent 和工具实现。
- 生态：文件系统、数据库、GitHub、Slack 等已有 MCP Server。

### Q22. 工具调用有哪些常见的安全风险？
1. **越权调用**：LLM 调用了不该调的工具（如删数据库）。→ 最小权限 + 白名单。
2. **参数注入**：用户输入注入到工具参数（SQL 注入）。→ 参数校验 + 转义。
3. **费用失控**：工具调用产生费用（如付费 API），LLM 死循环调用。→ 费用上限 + 频率限制。
4. **数据泄露**：工具返回敏感信息被 LLM 泄露给用户。→ 数据脱敏 + 访问控制。
5. **代码执行风险**：代码执行工具可能执行恶意代码。→ 沙箱隔离 + 超时 + 资源限制。

### Q23. 并行工具调用是什么？有什么好处？
- 传统：LLM 一次调一个工具，等结果再决定下一步（串行）。
- 并行：LLM 一次输出多个工具调用，代码并行执行后一起返回（如 Claude/OpenAI 支持）。
- 好处：减少往返轮次，加速复杂任务。如"查天气+查新闻+查日历"三路并行。
- 注意：工具有依赖关系时不能并行（如先查 DB 拿 ID 再查详情）。

### Q24. Agent 如何与外部 API 交互？
两种方式：
1. **预定义工具**：手动把每个 API 封装成 Tool（name+description+schema+handler），适合少量固定 API。
2. **OpenAPI/Schema 自动生成**：给 Agent 一个 OpenAPI 文档，LLLM 自己理解 API 并调用，适合大量 API。
3. **HTTP 通用工具**：给一个通用 "http_request" 工具，LLM 自己拼 URL 和参数（灵活但风险高）。
- 经验：生产环境优先预定义工具（可控），探索阶段可用通用工具。

## 四、记忆与上下文管理（Q25–Q30）

### Q25. Agent 的记忆系统有哪些类型？
1. **短期记忆（Working Memory）**：当前对话上下文，放 Prompt 里，容量有限。
2. **长期记忆（Long-term Memory）**：历史对话/经验存向量库，检索召回。
3. **情景记忆（Episodic）**：过去某次交互的完整记录。
4. **语义记忆（Semantic）**：结构化知识（如用户偏好、事实）。
5. **程序记忆（Procedural）**：Agent 学到的技能/工具使用经验。
- 对应人脑：短期 = 工作记忆，长期 = 海马体 + 新皮层。

### Q26. 上下文窗口满了怎么办？
1. **截断**：保留最近 N 轮，丢弃早期（简单但丢失信息）。
2. **摘要压缩**：用 LLM 把早期对话摘要成短文本（Summarization）。
3. **向量检索**：历史存向量库，当前需要时检索相关片段填入。
4. **滑动窗口 + 摘要**：近期保留原文，远期用摘要，混合策略。
5. **分层记忆**：近期→摘要→向量库三层，逐层降级。

### Q27. Agent 的长期记忆怎么实现？
- 核心流程：写入 → 存储 → 检索 → 注入。
1. **写入**：对话/经验经过 LLM 提取关键信息，生成 embedding。
2. **存储**：向量库（Pinecone/Chroma/Milvus）+ 元数据（时间、标签、来源）。
3. **检索**：用当前 query 向量检索 top-k 相关记忆。
4. **注入**：检索到的记忆拼接到 System Prompt 或 User Message 中。
- 进阶：记忆去重、时效性衰减、重要性评分过滤。

### Q28. 什么是 Context Engineering（上下文工程）？
- 比 Prompt Engineering 更广：关注**如何把正确的信息在正确的时间以正确的格式放入上下文**。
- 包括：System Prompt 设计、记忆注入策略、工具结果格式化、上下文压缩、信息优先级排序。
- 经验：Agent 性能瓶颈往往不在 LLM 能力，而在**上下文管理**——给 LLM 太多信息会分散注意力，太少则缺信息。

### Q29. Agent 记忆如何避免"遗忘"和"信息过载"？
- **遗忘**：长期记忆存向量库，不会丢；但检索不到等于遗忘 → 优化 embedding 质量和检索策略。
- **信息过载**：检索 top-k 太多塞满上下文 → 设置相关性阈值 + 限制注入条数 + 摘要压缩。
- **记忆冲突**：旧记忆和新事实矛盾 → 时间戳取最新 + LLM 判断合并。
- **记忆污染**：错误信息被记住 → 写入前校验 + 定期清理低质量记忆。

### Q30. Agent 对话历史如何持久化？
1. **数据库存储**：PostgreSQL/MySQL 存对话记录，按 session/user ID 关联。
2. **向量库**：对话摘要 embedding 存入，支持语义检索。
3. **Redis 缓存**：活跃会话的短期上下文放 Redis，快速访问。
4. **多级**：Redis（热会话）→ DB（完整历史）→ 向量库（语义检索）。
- 经验：生产环境三层结合，Redis 保证低延迟，DB 保证持久化，向量库支持智能召回。

## 五、多智能体与架构模式（Q31–Q36）

### Q31. 什么是 Multi-Agent（多智能体）系统？
- 多个 Agent 分工协作完成复杂任务，每个 Agent 有不同角色和工具。
- 经典模式：
  1. **协作型**：PM Agent 拆任务 → Dev Agent 写代码 → QA Agent 测试。
  2. **辩论型**：多个 Agent 对同一问题给出方案，交叉评审，取最优。
  3. **层级型**：主 Agent 调度子 Agent（Manager-Worker 模式）。
  4. **流水线型**：Agent A 输出 → Agent B 输入 → Agent C（串行管道）。

### Q32. Multi-Agent 和单 Agent 什么时候选哪个？
| 维度 | 单 Agent | Multi-Agent |
|------|---------|-------------|
| 复杂度 | 低，好调试 | 高，调试难 |
| 成本 | 低 | 高（多 LLM 调用） |
| 角色 | 单一角色 | 多角色分工 |
| 适用 | 单一任务、简单流程 | 复杂任务、多角色协作 |
- 经验：先尝试单 Agent + 多工具，不够再拆 Multi-Agent。过早拆多 Agent 增加复杂度而收益有限。

### Q33. Multi-Agent 之间如何通信？
1. **消息传递**：Agent A 输出文本作为 Agent B 的输入（最常见）。
2. **共享黑板（Blackboard）**：多个 Agent 读写同一个共享状态/文件。
3. **结构化协议**：Agent 间用 JSON Schema 通信，避免自然语言歧义。
4. **消息队列**：异步通信，Agent 往 MQ 发消息，其他 Agent 订阅消费。
- 经验：结构化通信比自然语言更可靠，减少信息损失和误解。

### Q34. 常见的 Agent 框架有哪些？
| 框架 | 特点 | 适用 |
|------|------|------|
| **LangChain/LangGraph** | 生态最全，Graph 状态机 | 通用 Agent 开发 |
| **AutoGen** | 微软出品，多 Agent 对话 | Multi-Agent 协作 |
| **CrewAI** | 角色扮演式多 Agent | 任务分工场景 |
| **MetaGPT** | 模拟软件团队 SOP | 软件开发模拟 |
| **OpenAI Swarm** | 轻量级 Handoff 机制 | 简单多 Agent 路由 |
| **Dify/Coze** | 低代码 Agent 平台 | 快速搭建无代码 |

### Q35. 什么是 Agent 的 DAG 任务调度？
- 把多 Agent 任务组织成**有向无环图（DAG）**，节点是任务，边是依赖。
- 有依赖关系的串行执行，无依赖的并行执行。
- 好处：并行化加速、可视化流程、支持断点续跑。
- LangGraph 天然支持图结构 Agent 编排。

### Q36. Multi-Agent 系统的常见问题有哪些？
1. **死循环**：Agent A 让 B 做，B 让 A 做，无限互踢。→ 设置最大轮次 + 循环检测。
2. **信息损失**：Agent 间传递长文本时摘要丢信息。→ 结构化传递 + 关键字段校验。
3. **成本爆炸**：多 Agent 各自多轮 LLM 调用。→ 控制 Agent 数和轮次 + 小模型做简单任务。
4. **调试困难**：多 Agent 交互链路长，定位错误难。→ 全链路日志 + trace_id 追踪。
5. **一致性**：多 Agent 观点冲突。→ 仲裁 Agent 或投票机制。

## 六、工程落地与评估（Q37–Q42）

### Q37. Agent 的最大步数（max_iterations）怎么设？
- 太小：复杂任务没做完就被截断。
- 太大：死循环或费用失控。
- 经验值：简单任务 5-10 步，中等 10-20 步，复杂 20-50 步。
- 策略：设保守上限 + 超时兜底 + LLM 自判断终止（输出 Final Answer）。

### Q38. 如何评估 Agent 的效果？
1. **端到端任务成功率**：最终是否完成用户目标（最重要指标）。
2. **工具调用准确率**：选对工具 + 参数正确的比例。
3. **步骤效率**：完成任务用了多少步（越少越好）。
4. **成本效率**：完成任务花了多少 token/费用。
5. **延迟**：从请求到最终回答的时间。
6. **可追溯性**：Thought 链是否可审查、可解释。
- 工具：LangSmith/Langfuse 做 trace 记录和评估。

### Q39. Agent 的可观测性怎么做？
1. **全链路 trace**：每步 Thought/Action/Observation 记录，类似分布式追踪。
2. **trace_id**：一次会话一个 ID，串联所有 LLM 调用和工具调用。
3. **指标采集**：每步耗时、token 消耗、工具调用成功率。
4. **回放调试**：保存完整上下文，可回放某步的 LLM 输入输出。
5. **告警**：工具失败率超阈值、步数超限、成本异常告警。
- 工具：LangSmith、Langfuse、Phoenix、OpenTelemetry。

### Q40. Agent 生产环境最大的挑战是什么？
1. **可靠性**：LLM 输出不确定，同一输入可能不同结果。→ Structured Output + 重试 + 降级。
2. **延迟**：多轮 LLM 调用累积延迟，可能几十秒。→ 并行 + 缓存 + 流式输出。
3. **成本**：多步多工具 token 消耗大。→ 小模型做简单步骤 + 上下文压缩。
4. **安全**：LLM 可能调用危险工具。→ 最小权限 + 人工审批 + 沙箱。
5. **测试困难**：非确定性逻辑难写单元测试。→ 行为测试 + 回归测试集 + A/B 评估。

### Q41. Agent 如何做流式输出（Streaming）？
- 用户不想等几十秒看到最终结果，需要**实时反馈进度**。
- 方式：
  1. **LLM 输出流式**：LLM token 级流式（SSE/WebSocket）。
  2. **步骤进度流式**：每完成一步（Thought/Action/Observation）推送进度。
  3. **中间结果流式**：工具执行有中间产物时推送。
- 经验：先推步骤进度（"正在搜索..."），再推最终答案，用户体验好很多。

### Q42. Agent 开发的最佳实践有哪些？
1. **Prompt 优先**：先写好 System Prompt 和工具描述，再考虑框架。
2. **从简单开始**：单 Agent + 少量工具 → 逐步增加复杂度。
3. **结构化输出**：用 JSON Mode/Structured Output 强制格式。
4. **错误处理**：每个工具都要 try-catch + 错误反馈给 LLM。
5. **日志全量**：记录每步输入输出，方便调试和评估。
6. **人工兜底**：关键步骤加 Human-in-the-loop 审批。
7. **成本控制**：简单步骤用小模型，复杂步骤用大模型。
8. **渐进增强**：先跑通主流程，再加反思/记忆/多 Agent。
