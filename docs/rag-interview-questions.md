## 一、RAG 基础与流程（Q1–Q8）

### Q1. 什么是 RAG？为什么需要 RAG？
- **RAG（Retrieval-Augmented Generation，检索增强生成）**：在 LLM 生成回答前，先从外部知识库**检索**相关文档，拼入上下文，再让 LLM 基于检索内容生成回答。
- **为什么需要**：
  1. **知识时效性**：LLM 训练数据有截止日期，无法回答最新信息。
  2. **私有知识**：企业内部文档 LLM 没见过。
  3. **减少幻觉**：有依据地生成，降低编造内容。
  4. **可追溯**：回答可引用来源，比纯 LLM 更可信。
  5. **成本**：比 fine-tune 更便宜、更灵活（知识更新只需更新知识库）。

### Q2. RAG 和 Fine-tuning 有什么区别？什么时候选哪个？
| 对比 | RAG | Fine-tuning |
|------|-----|-------------|
| 知识更新 | 更新知识库即可，实时 | 需重新训练，成本高 |
| 知识来源 | 外部知识库 | 内化到模型权重 |
| 可追溯 | ✅ 可引用来源 | ❌ 无法追溯 |
| 幻觉 | 低（有依据） | 仍可能幻觉 |
| 适用 | 事实性问答、动态知识 | 风格/格式/领域能力提升 |
- 经验：知识更新用 RAG，能力/风格提升用 Fine-tuning，两者可结合。

### Q3. RAG 的完整链路是什么？
经典七步：
1. **Query**：用户提问。
2. **文档处理**：加载 PDF/HTML/Markdown 等原始文档。
3. **Chunking（分块）**：把长文档切成小块。
4. **Embedding**：每个 chunk 生成向量。
5. **存储**：向量 + 原文存入向量库。
6. **检索**：用户 query 向量化，检索 top-k 相关 chunk。
7. **生成**：检索到的 chunk + query 拼成 Prompt，LLM 生成回答。
- 进阶在 6 和 7 之间加 **Rerank（重排序）** 和 **Query Rewrite（查询改写）**。

### Q4. RAG 的索引阶段和查询阶段分别做什么？
- **索引阶段（离线/预计算）**：
  - 文档加载 → 分块 → Embedding → 存入向量库。
  - 一次性预处理，后续检索直接用。
- **查询阶段（在线/实时）**：
  - 用户提问 → Query Embedding → 向量检索 → Rerank → 拼上下文 → LLM 生成。
  - 每次用户提问都走一遍。

### Q5. RAG 系统的核心组件有哪些？
1. **文档加载器**：PDF/HTML/DB 等多源数据接入。
2. **分块器**：固定大小/语义/递归分块。
3. **Embedding 模型**：文本转向量（OpenAI/BGE/m3e）。
4. **向量数据库**：存储和检索向量（Pinecone/Milvus/Chroma）。
5. **检索器**：向量检索 + 关键词检索 + 混合检索。
6. **Reranker**：对检索结果重排序（Cohere/BGE-reranker）。
7. **LLM**：生成最终回答（GPT-4/Claude/Qwen）。
8. **Prompt 模板**：组织上下文和指令。

### Q6. RAG 的检索和生成是分离的还是一体的？
- **传统 RAG（检索 + 生成分离）**：先检索 chunk，再拼入 Prompt 给 LLM。两个阶段独立。
- **Joint RAG / Flan-T5 等**：训练时把检索和生成联合优化，端到端。
- **主流是分离式**：灵活可控，可单独优化每个环节。
- **Agentic RAG**：用 Agent 决定是否检索、检索几次、是否补充检索。

### Q7. RAG 的主要痛点有哪些？
1. **检索质量差**：召回不到相关文档，或召回太多噪声。
2. **分块不合理**：切太大 LLM 处理不了，切太小语义不完整。
3. **幻觉**：LLM 不依据检索内容，自己编。
4. **延迟**：检索 + LLM 生成多环节累积延迟。
5. **多轮对话上下文丢失**：用户追问时上一轮的检索结果没保留。
6. **表格/图片**：非文本内容的检索和处理难。
7. **知识更新**：文档变更后向量库要及时更新。

### Q8. RAG 和直接给 LLM 塞长文档有什么区别？
- **直接塞**：把整个文档放 Prompt → token 成本高、LLM 注意力分散（lost in the middle）、可能超出上下文窗口。
- **RAG**：只检索最相关的 top-k chunk → 精准、成本低、可处理超大知识库。
- RAG 优势：**精准检索 + 成本可控 + 可扩展到海量知识**。
- 补充：文档不大时直接塞也可以（无需 RAG），文档量大时 RAG 是刚需。

## 二、文档处理与分块（Q9–Q14）

### Q9. Chunk（分块）为什么重要？切大了切小了各有什么问题？
- **太大**：超出 Embedding 限制、检索精度下降（一个 chunk 混杂多个主题）、LLM 上下文浪费。
- **太小**：语义不完整（一句话被切断）、检索到但 LLM 无法理解、召回数量多但信息零碎。
- **理想**：一个 chunk 包含一个**完整语义单元**（一个段落、一个 QA 对、一个章节）。

### Q10. 常见的分块策略有哪些？
1. **固定大小分块**：按字符数/token 数切（如 512 token），简单但可能切断语义。
2. **按分隔符分块**：按段落/标题/换行符切，语义更完整。
3. **递归分块（Recursive）**：先按大分隔符（章节）切，太大再按小分隔符（段落）切，LangChain 默认。
4. **语义分块（Semantic Chunking）**：用 Embedding 计算相邻句子相似度，相似度骤降处切分。
5. **按文档结构分块**：Markdown 按 ## 标题切，PDF 按页/段落切。
6. **重叠分块**：chunk 之间保留 overlap（如 50 token），防止边界语义丢失。

### Q11. Chunk size 和 overlap 怎么设？
- **chunk_size**：经验值 300-500 token（中文 200-400 字）。
  - 问答场景偏小（300），长文档摘要偏大（800-1000）。
- **overlap**：chunk_size 的 10-20%（如 50-100 token）。
  - 防止边界信息丢失，但太大会增加冗余存储。
- 经验：先 500+50 跑基线，再按效果调整，不同文档类型可不同。

### Q12. 表格和图片怎么处理？
1. **表格**：转成 Markdown/HTML 格式保留结构，或用 LLM 生成表格摘要。
2. **图片**：OCR 提取文字 + 多模态 Embedding（CLIP）或 LLM 生成图片描述。
3. **PDF 复杂版式**：用 Layout 解析（Unstructured/Marker）识别标题/段落/表格/图片，按结构切分。
4. **混合文档**：文本用文本 Embedding，图片用多模态 Embedding，统一存向量库。

### Q13. 什么是 Parent-Child 分块（父子分块）？
- **子块（小）**：用于检索，embedding 精准匹配。
- **父块（大）**：子块所在的更大上下文，检索到子块后返回父块给 LLM。
- 好处：**检索精度（小）+ 上下文完整（大）两全**。
- LangChain 的 ParentDocumentReader 实现：子块建索引，父块存原文映射。

### Q14. 文档更新时向量库怎么同步？
1. **全量重建**：文档变更大时全量重新 embedding（简单但慢）。
2. **增量更新**：只对变更的 chunk 重新 embedding，删除旧向量、插入新向量（高效）。
3. **版本管理**：chunk 加 doc_id + version + hash，检测变更。
4. **软删除**：旧版本标记删除不立即物理删，支持回滚。
- 经验：生产用增量更新 + 定期全量重建校准。

## 三、Embedding 与向量检索（Q15–Q22）

### Q15. 什么是 Embedding？怎么选模型？
- **Embedding**：把文本映射成高维向量（如 768/1536 维），语义相近的文本向量距离近。
- **选型考量**：
  - 语言：中文优先选中文优化模型（BGE-zh/m3e），英文选 OpenAI/BGE-en。
  - 维度：越高表达力越强但存储/检索开销越大。
  - 性能：MTEB 排行榜参考，关注自己领域的子榜单。
  - 部署：本地部署（BGE/m3e）vs API（OpenAI/voyage）。
- 经验推荐：中文 BGE-large-zh / bge-m3，英文 OpenAI text-embedding-3-small。

### Q16. 什么是余弦相似度？为什么用它？
- **余弦相似度**：衡量两个向量方向的夹角，值域 [-1, 1]，越接近 1 越相似。
- **为什么不用欧氏距离**：欧氏距离受向量模长影响，文本长短不同时模长差异大，余弦只看方向更合理。
- **点积（Dot Product）**：向量归一化后点积 = 余弦相似度，计算更快，很多向量库默认用点积。

### Q17. 向量检索的 ANN 算法有哪些？
- **暴力搜索（Brute Force）**：遍历所有向量算距离，精确但慢，只适合小数据。
- **HNSW（Hierarchical Navigable Small World）**：图索引，查询快、召回率高，主流向量库默认（Milvus/Pinecone）。
- **IVF（Inverted File）**：聚类后只搜最近的几个簇，快但精度略低。
- **PQ（Product Quantization）**：向量压缩，内存省但精度损失。
- **ScaNN**：Google 出品，量化 + 各向异性，性能好。
- 经验：HNSW 综合最优，数据量大时 IVF+PQ 省内存。

### Q18. 常见的向量数据库有哪些？怎么选？
| 数据库 | 特点 | 适用 |
|--------|------|------|
| Milvus | 开源、分布式、生态全 | 大规模生产 |
| Pinecone | 全托管 SaaS | 快速上手、不想运维 |
| Chroma | 轻量、Python 友好 | 原型开发 |
| Qdrant | Rust 高性能、开源 | 性能敏感场景 |
| Weaviate | 内置混合检索 | 多模态 |
| pgvector | PostgreSQL 扩展 | 已有 PG 环境 |
| Elasticsearch | 8.x+ 向量检索 | 已有 ES 环境 |
- 经验：原型用 Chroma，生产用 Milvus/Qdrant，已有 ES/PG 则用其扩展。

### Q19. 什么是混合检索（Hybrid Search）？为什么需要？
- **纯向量检索**：语义相似，但专有名词/ID/型号可能检索不到（如"iPhone 15 Pro"的"15"）。
- **纯关键词检索（BM25）**：精准匹配关键词，但不理解语义同义词。
- **混合检索**：向量检索（语义）+ 关键词检索（BM25）两路召回，融合排序。
- **融合方法**：RRF（Reciprocal Rank Fusion）按排名倒数融合，最常用。
- 好处：兼顾语义理解和关键词精准，提升整体召回率。

### Q20. 什么是 Rerank（重排序）？为什么检索后还要重排？
- 检索阶段：向量检索快速召回 top-k（如 50 条），但排序不一定最优（向量相似 ≠ 语义最相关）。
- Rerank：用 Cross-Encoder 模型对 query 和每个 chunk 做**逐对精排**，输出相关性分数，重新排序取 top-n（如 5 条）。
- 为什么需要：
  1. 向量检索是 Bi-Encoder（query 和 doc 独立编码），精度有限。
  2. Rerank 用 Cross-Encoder（query+doc 拼一起编码），精度更高但慢。
  3. 检索快但粗，Rerank 精但慢 → 先粗筛后精排，兼顾速度和精度。
- 模型：Cohere Rerank、BGE-reranker、bce-reranker。

### Q20b. 为什么 Rerank 是 query + doc 拼一起编码？（深入原理）

**两种编码方式的本质区别：**

#### Bi-Encoder（向量检索）——独立编码
```
Query: "iPhone 15 续航怎么样"     → Encoder → 向量 A
Doc:   "iPhone 15 电池容量3274mAh" → Encoder → 向量 B

相似度 = cos(A, B)
```
- query 和 doc **各自独立编码**，编码时互相看不到对方。
- 最后只比两个压缩后的向量距离，**词级别的交互信息已丢失**。
- 类比：两个人各自写简历，然后比简历标签相似度——没有对话交流。

#### Cross-Encoder（Rerank）——拼接编码
```
Query + Doc 拼一起: "iPhone 15 续航怎么样 [SEP] iPhone 15 电池容量3274mAh"
                          ↓ 一个 Encoder（整体）
                   相关性分数
```
- query 和 doc 拼成一段文本，一次性送入 Transformer。
- 模型内部的 **Self-Attention 让 query 的每个词和 doc 的每个词两两计算注意力**：
  - "续航" ←attention→ "电池" → 模型学到：续航在问电池，强相关！
  - "续航" ←attention→ "3274" → 模型学到：续航和具体容量相关！
- 类比：面对面面试，HR 的每个问题和候选人的每个回答实时交互。

**核心原因：Cross-Attention（交叉注意力）。** 拼一起编码时，模型能做 query 词和 doc 词之间的语义关系判断；独立编码时双方完全隔离，只有压缩向量层面的比较。

**为什么不全用 Cross-Encoder？太慢。**
- Bi-Encoder：doc 可**预编码**存入向量库，查询时只编码 query（1 次），从百万条秒回 top-50。
- Cross-Encoder：每次都要把 **query + 一条 doc 拼一起**跑完整 Transformer，50 条 = 50 次推理，百万条不可行。

**生产标准流程：**
```
百万级文档 → Bi-Encoder 粗筛（快，doc 预编码）→ 50 条
                                              ↓
              Cross-Encoder 精排（慢但准，50 次可接受）→ 5 条
                                                          ↓
                                                    注入 LLM 上下文
```

**速记：** Bi-Encoder = 各自编码比距离（快但粗，像比简历标签）；Cross-Encoder = 拼一起编码做词级交互（慢但准，像面对面面试）；先粗筛后精排，兼顾速度和精度。

### Q21. 向量检索的 top-k 怎么设？
- **检索 top-k**（粗筛）：20-100，多一些保证不遗漏。
- **Rerank top-n**（精排后）：3-10，太多塞满上下文且噪声增加。
- 经验：检索 50 → Rerank 取 5，先跑基线再调。
- 太少：遗漏相关信息；太多：噪声多 + token 成本高 + LLM 注意力分散。

### Q22. Embedding 模型更新了怎么办？
- Embedding 模型换了，所有向量维度/语义空间可能变，**必须全量重新 embedding**。
- 策略：双索引并行（新模型建新索引，灰度切换），验证效果后再删旧索引。
- 教训：不要只换模型不重新 embedding——维度不一致向量库直接报错，即使维度碰巧相同，语义空间不同也会导致检索质量骤降。

## 四、检索增强与优化（Q23–Q28）

### Q23. 什么是 Query Rewrite（查询改写）？
- 用户的原始 query 可能口语化、模糊、有指代，直接检索效果差。
- 用 LLM 把 query 改写成**更适合检索的形式**：
  1. **指代消解**："那它的价格呢" → "iPhone 15 Pro 的价格"。
  2. **口语→书面**："咋整" → "如何解决"。
  3. **多查询生成**：把一个 query 改成多个不同角度的 query，分别检索合并（Multi-Query）。
  4. **HyDE**：让 LLM 先生成一个"假想答案"，用假想答案做向量检索（比原 query 语义更丰富）。

### Q24. 多轮对话中 RAG 怎么处理上下文？
- 问题：用户第二轮 "那它支持 5G 吗"中的"它"指代什么？直接检索"它支持 5G 吗"效果差。
- 方案：
  1. **对话压缩**：用 LLM 把历史 + 当前 query 压缩成一个独立 query（"iPhone 15 Pro 支持 5G 吗"）。
  2. **Query Rewrite**：指代消解后检索。
  3. **保留上轮检索结果**：当前轮如果和上轮相关，复用部分上轮 chunk。
- 经验：多轮 RAG 一定要做 query rewrite，否则检索质量断崖式下降。

### Q25. 什么是 Self-Querying（结构化过滤）？
- 用户 query 含**过滤条件**："2024 年发布的价格低于 5000 的手机"。
- 用 LLM 把 query 拆成：**语义部分**（"手机"）+ **结构化过滤**（year=2024, price<5000）。
- 向量库先做 metadata 过滤，再在子集内做向量检索。
- 好处：检索结果精准满足过滤条件，避免检索后再过滤导致 top-k 不足。

### Q26. 什么是 GraphRAG？
- 微软提出的方案：把文档抽取成**知识图谱**（实体 + 关系），再做图检索 + 向量检索。
- 流程：文档 → LLM 抽取实体/关系 → 建图 → 查询时图遍历 + 向量检索 → 生成。
- 优势：能回答"跨文档的全局性问题"（如"这个领域的主要趋势是什么"），传统向量 RAG 擅长局部检索但不擅长全局。
- 劣势：建图成本高、LLM 调用多、维护复杂。

### Q27. RAG 检索效果不好怎么优化？
分环节排查：
1. **检索召回率低**：
   - chunk 策略调优（大小/重叠/语义分块）。
   - Embedding 模型换更好的。
   - 混合检索（向量 + BM25）。
   - Query Rewrite（多查询/HyDE）。
2. **精度低（噪声多）**：
   - 加 Rerank（Cross-Encoder 精排）。
   - 降低 top-k 数量。
   - 加相似度阈值过滤。
3. **知识不全**：
   - 补充文档 / 更新知识库。
   - Parent-Child 分块补充上下文。
4. **多轮问题**：
   - Query Rewrite + 历史压缩。

### Q28. 什么是 Agentic RAG？
- 传统 RAG：固定流程（检索→生成），不论需不需要都检索。
- Agentic RAG：用 **Agent 决策**何时检索、检索几次、检索结果够不够、要不要追加检索。
  - LLM 判断"这个简单问题不需要检索"→直接回答。
  - LLM 判断"检索结果不充分"→追加二次检索。
  - LLM 判断"需要多角度信息"→多路并行检索。
- 价值：按需检索，减少无效检索和 token 浪染，复杂问题多轮检索递进。
- 代价：Agent 多轮 LLM 调用，延迟和成本增加。

## 五、生成与幻觉控制（Q29–Q32）

### Q29. 什么是大模型幻觉？RAG 如何减少幻觉？
- **幻觉**：LLM 生成看似合理但不符合事实的内容。
- **RAG 减少幻觉的方式**：
  1. 提供外部知识作为依据，LLM"看着文档回答"。
  2. Prompt 约束："仅基于以下参考内容回答，不知道就说不知道"。
  3. 引用来源：要求 LLM 标注引用的 chunk 编号。
  4. 后置校验：检查 LLM 输出是否与检索内容一致。
- 注意：RAG 不能完全消除幻觉——LLM 仍可能无视参考内容编造，需配合 Prompt 约束和校验。

### Q30. RAG 的 Prompt 怎么设计？
核心要素：
1. **角色设定**："你是一个基于文档的问答助手"。
2. **约束**："仅基于提供的参考内容回答，不要编造"。
3. **拒答规则**："如果参考内容中没有相关信息，回答'抱歉，未找到相关信息'"。
4. **引用要求**："每个事实陈述后标注来源 [chunk_id]"。
5. **上下文注入**：把检索到的 chunk 按编号拼接。
6. **格式**：指定输出格式（Markdown/JSON）。
```
你是文档问答助手。仅基于以下参考内容回答，不要编造。
如果参考内容中没有相关信息，回答"未找到相关内容"。
每个事实后标注来源 [编号]。

参考内容：
[1] {chunk1}
[2] {chunk2}
...

用户问题：{query}
```

### Q31. LLM 不依据检索内容回答怎么办？
1. **Prompt 强化约束**："你只能从参考内容中提取信息，禁止使用外部知识"。
2. **减少 top-k 噪声**：检索到不相关内容 LLM 更容易自己编。
3. **Rerank 提精度**：确保 top-k 都高度相关。
4. **后置校验**：用另一个 LLM 或规则检查输出是否与参考内容一致（faithfulness 评估）。
5. **引用强制**：要求每句标注来源，无法标注则删除。
6. **Temperature=0**：减少随机性。

### Q32. RAG 如何处理"知识库中没有答案"的情况？
1. **Prompt 约束**：明确要求"找不到就说不知道"。
2. **相似度阈值**：检索结果最高分低于阈值 → 直接返回"未找到"。
3. **兜底策略**：检索不到 → Web 搜索补充 / 转人工客服。
4. **澄清提问**：LLM 判断问题模糊 → 反问用户细化问题。
- 经验：阈值 + Prompt 约束双保险，宁可拒答也不能编造。

## 六、进阶与评估（Q33–Q36）

### Q33. RAG 怎么评估？
核心指标（RAGAS 框架）：
1. **Faithfulness（忠实度）**：回答是否忠于检索内容，不编造。幻觉检测核心指标。
2. **Answer Relevance（答案相关性）**：回答是否切题。
3. **Context Precision（上下文精度）**：检索到的 chunk 有多少是真正相关的（召回质量）。
4. **Context Recall（上下文召回率）**：应该检索到的是否都检索到了。
- 端到端：**答案准确率**（与标注答案对比）。
- 工具：RAGAS、TruLens、LangSmith。

### Q34. RAG 和 Agent 怎么结合（Agentic RAG）？
- Agent 作为 RAG 的"大脑"，决策检索策略：
  1. **判断是否需要检索**：简单常识问题直接回答。
  2. **Query 改写**：Agent 用 LLM 改写 query。
  3. **多轮检索**：第一轮不够，追加第二轮。
  4. **多源检索**：Agent 决定查向量库、查 SQL、查 Web。
  5. **结果筛选**：Agent 判断检索结果是否足够，不够则重检。
- 流程：`用户提问 → Agent 决策 → [检索→评估→补充检索] → 生成回答`

### Q35. 什么是 Modular RAG（模块化 RAG）？
- 把 RAG 拆成可插拔的模块：检索器、Reranker、生成器、记忆模块等。
- 每个模块独立优化、独立替换，不用改整体架构。
- 比传统"检索→生成"线性流水线更灵活：
  - 检索模块可换（向量/BM25/混合）。
  - 生成模块可换（不同 LLM）。
  - 可加/减模块（如加 Query Rewrite、加 Rerank）。
- LangChain/LlamaIndex 都支持模块化组装。

### Q36. RAG 生产的最佳实践有哪些？
1. **分块优化**：递归分块 + 父子分块 + 重叠。
2. **混合检索**：向量 + BM25 + RRF 融合。
3. **Rerank**：Cross-Encoder 精排，检索 50→Rerank 5。
4. **Query Rewrite**：多轮对话必须做指代消解。
5. **Prompt 约束**：仅基于参考内容 + 拒答规则 + 引用要求。
6. **监控评估**：RAGAS 指标持续监控，badcase 收集迭代。
7. **缓存**：热点 query 的检索结果和 LLM 回答缓存。
8. **流式输出**：先返回检索进度，再流式生成回答。
9. **知识库治理**：定期更新、去重、质量评分。
