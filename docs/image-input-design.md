# 图片输入（多模态对话）技术方案

> 目标：让 local-agent 能"看图说话"——用户贴一张报错截图就能问，模型也能主动去看工作区里的图片。
>
> 本文是**调研 + 设计 + 实施记录**三位一体：第 2 节是各条路的对比与选型理由，
> 第 3 节是最终架构与不变式，第 4 节逐文件列出接线点，第 5 节写清取舍与未做的事。
> 动手改代码前请先看第 3 节的不变式——那里每一条都对应一类曾经的坑。

---

## 1. 问题与边界

### 1.1 要解决的

1. **进得来**：用户能把图片给到对话里（截图、设计稿、图表、UI 稿）。
2. **看得见**：图片在对话界面上要能显示——不只是"发送时那一瞬间"，而是**回看历史时**也还在。
3. **存得住**：会话记录里要有这张图的位置，重启应用、切换会话、翻旧记录都还能看到。
4. **认得准**：图片要以正确的形状交给模型，并且**别把上下文窗口烧穿**。
5. **模型也能主动看**：给模型一条路，让它按路径去读工作区里的图片（"看看 docs/mockup.png"）。

### 1.2 明确不做的

- **不做本地 OCR**。理由见 §2.3 的方案 C。需要 OCR 是另一条独立链路（依赖、离线模型、精度），
  而视觉模型对截图里的报错文字识别已经足够好，先不引入第二套失败模式。
- **不做多图拼接 / 画布标注**。入口支持一次多张，但不做"在图上画框"这类交互。
- **不做图片生成**。模型不会产出图片；`read_image` 是"读"，方向单一。
- **不做附件配额与 LRU 回收**。见 §5 的已知取舍。

## 2. 方案调研与选型

### 2.1 图片从哪里进来

| 入口 | 实现要点 | 取舍 |
| --- | --- | --- |
| **粘贴（Ctrl+V）** | 监听 `paste` 事件，从 `clipboardData.items` **与** `files` 取图（只读 `files` 在真机上是空的，见 §6.4） | AI 编程助手里最常用的一条（截图工具 → 复制 → 粘贴）。**必做** |
| 拖拽文件 | `dragover`/`drop` + 遮罩提示，与粘贴共用同一个取图函数 | 从文件管理器拖图，覆盖面广 |
| 按钮选文件 | 隐藏的 `<input type=file accept=image/png,image/jpeg,image/gif multiple>` | 最朴素，兜底 |
| **从链接添加** | 显式的「链接」入口：收 URL → 后端下载 → 按同一条管线存成附件。**只由用户点按触发** | 覆盖"剪贴板里只有一条 URL、没有图片字节"的场景（§6.4 的真实故障）。刻意**不**做成"粘贴链接就自动下载"——那等于让任何一次粘贴都能发起本机出站请求 |
| 工具读图 | `read_image` 工具，模型按路径读 | 不是"输入"而是"工具"，见 §2.4 |

**选型：四个都做，但出口只有一个。** 三个 UI 入口全部收敛到同一个 `addFiles(files)`：
读文件、校验类型、限额、生成预览、进待发送队列。三处各写一份必然漂移
（历史上"三个图标按钮没绑事件"就是这个教训的另一种形态）。

### 2.2 图片存在哪里（"历史文档中如何保存"）

这是本方案最核心的一个决定。

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. base64 内联进会话 JSON** | 自包含，永不丢图；零额外机制 | 会话文件是**每次追加消息都整体重写**的（`SessionStore.saveSession` 用 `MarshalIndent` 写整个 `Session`）。一张 3MB 的图 base64 后约 4MB，贴三张就是十几 MB，此后每发一条消息都要读出来再写回去；`ListSessions` 要读目录下**全部**会话文件才能拿到元数据，单文件膨胀会直接拖慢会话列表 |
| **B. 存进工作区 `.local-agent/attachments/`** | 跟随项目走，换机器打开同一项目还能看到图 | 会污染用户的 git 仓库（要么被提交、要么逼用户加 `.gitignore`）；**更糟的是会被本项目的 diff 归因/回退机制扫到**——用户回退一轮代码时，"图片被创建"也会被当成一次文件改动，甚至被回退掉 |
| **C. 独立附件目录 + 消息只存引用** ✅ | 会话 JSON 保持轻量；内容寻址天然去重（同一张图重发只存一份）；base64 只在真正发请求那一刻才生成；附件目录是应用私有数据，与工作区、diff、回退完全解耦 | 删会话要级联删目录；附件目录被清理后要有降级路径（显示"图片已丢失"而不是破图） |

**选型：C。** 目录布局（内容寻址）：

```
~/.local-agent/attachments/<会话ID>/<sha256 前 16 位>.<ext>
```

消息里存的是**引用**：

```json
{
  "role": "user",
  "content": "这个报错怎么回事",
  "attachments": [
    { "id": "9f2c1a...", "kind": "image", "name": "报错截图.png",
      "mediaType": "image/png", "bytes": 182400, "width": 1240, "height": 860,
      "source": "user", "path": "20260925_101010_ab12/9f2c1a....png" }
  ]
}
```

三个配套决定：

- **用户贴的图与工具读到的图共用同一个字段**（`Message.Attachments`），
  因此"怎么存"（`AttachmentStore`）与"怎么发给模型"（`buildLLMMessages`）各自只有一处实现。
- **删除会话时级联删附件目录**。附件不出现在会话列表里，主会话删掉之后再也没有入口能发现它们，
  不清理就是永久占地的孤儿文件——与 checkpoint ref 是同一类问题。
- **附件 ID 是内容寻址的**：同一张图重复贴只落一份。ID 参与路径拼接，因此必须是
  `[A-Za-z0-9_-]` 白名单校验过的（`safePathSegment`），前端传来的文件名一律不参与拼路径。

### 2.3 以什么形式交给模型（"图片如何识别给到大模型"）

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 原图直传** | 实现最薄；像素级细节不丢 | 一张 4000×3000 的手机照约 5000 token 起（按像素计费）。视觉编码器对超过 ~1568px 的图会在**内部**降采样，多出来的像素一分钱不值却照样计费 |
| **B. 本地 OCR 出文本再喂** | 对"截图里的报错"最省 token | 需要引入 OCR 依赖（本项目沙箱无法拉新模块，离线 OCR 质量参差）；OCR 会丢掉布局/颜色/图标信息，"这个按钮为什么是灰的"就答不了 |
| **C. 入站即规整：解码 → 缩放 → 重编码** ✅ | 按上限压到 1568px，省 token 也省带宽；尺寸一确定，上下文用量就能**在发送前**算准；请求路径零转换（热路径上没有失败面） | 需要在入站做一次编解码；格式选择要讲清楚（见下） |

**选型：C。** 规整规则（`imageproc.go`）：

| 情形 | 处理 |
| --- | --- |
| 尺寸与体积都在限内 | **原样透传**，一个字节都不动（绝大多数截图走这条；不解码、不重编码，PNG 里的文字一个像素不变） |
| 长边 > 1568px | 面积平均（box filter）等比缩放到 1568 |
| 只有体积超限（> 4MB） | 只重编码，不改尺寸 |
| 格式 | **跟随原格式**：PNG/GIF → PNG（截图里的文字转 JPEG 会糊）；JPEG → JPEG（质量 85）。PNG 压不动且超 1.5MB 时退回 JPEG，退回前先压到白底（JPEG 存不了 alpha，直接编码透明区会变黑块） |

上限与常量：

| 常量 | 值 | 为什么是这个值 |
| --- | --- | --- |
| `imageModelMaxEdge` | 1568 | 主流视觉编码器（Claude / GPT-4o 系）的输入上限，再大也是被内部降采样 |
| `maxImageSourceBytes` | 10 MB | 超过直接拒绝：十几 MB 的图多半是误拖进来的原始素材，不是"要看的截图" |
| `imageModelMaxBytes` | 4 MB | 规整后的硬上限 |
| `imagePNGKeepMaxBytes` | 1.5 MB | PNG 优先保留的上限，超过才转 JPEG |

**只支持 PNG / JPEG / GIF，明确拒绝 WebP**：标准库没有 WebP 解码器，无法缩放也就无法保证尺寸上限；
而"原样透传"会让一张 8MB 的 WebP 按原尺寸计费，与上面三条理由都相悖。
宁可给一句明确的错误（请转成 PNG），也不要静默发一张超限的图。

**Token 估算**用 Anthropic 的公开口径 `tokens ≈ (宽 × 高) / 750`，**不是**按 base64 字符数估：
图片计费只与像素数有关、与字节数基本无关。按字符估会得出完全相反的结论——
一张 200KB 的 1568×1568 截图（≈3278 token）比一张 2MB 的 4000×3000 照片贵得多。
向上取整：压缩判定宁早勿晚。

### 2.4 协议形状：图片能出现在哪

这是最容易被低估的一段。两条协议对"图片能放在哪"的规定**不一样**：

| | OpenAI 兼容 | Anthropic Messages |
| --- | --- | --- |
| 用户消息带图 | `content` 是块数组：`[{"type":"text"},{"type":"image_url","image_url":{"url":"data:..."}}]` | `content` 是块数组：`[{"type":"text"},{"type":"image","source":{"type":"base64","media_type":..,"data":..}}]` |
| 工具结果带图 | ❌ `tool` 消息的 `content` 只能是字符串，塞数组会被网关直接拒 | ✅ `tool_result` 块本身能装图片块 |
| 硬约束 | — | `tool_result` 必须是该 user 回合的**第一个**内容块 |

**统一形状**（`buildLLMMessages`，协议中立层）：

- 用户消息带图 → 一条消息，`Images` 挂在上面。
- **工具结果带图 → 工具文本消息 + 紧随其后的一条 user 消息**承载图片。

为什么这一种形状在两条协议下都合法：

- OpenAI：得到一条合法的 `tool` 文本消息 + 一条合法的带图 `user` 消息。
- Anthropic：适配器会把**相邻的同角色消息合并进同一个 user 回合**
  （`appendAnthropicMessage` 的既有逻辑），于是那条 user 消息自动并进 `tool_result` 所在的那一轮，
  顺序正好是 `[tool_result, text, image]` —— `tool_result` 排在最前，满足硬约束，且不会多出一个回合。

**这个形状由 `appendToolResultMessages` 一处产出，工具循环与历史重建共用它。**
两处各写一份的话，第二轮请求里的这条消息就会与第一轮长得不一样——而人只有在"图片突然不见了"时才会发现。

> 附带的一条：脱敏后的图片（请求快照路径）在 Anthropic 侧降级成一行文本说明，
> 而不是编一段假 base64 发出去。报文里"这里本该有张图"这件事仍然可见。

### 2.5 模型主动读图：`read_image`

`read_file` **刻意**对二进制文件报错（`looksBinary`），图片正属于这一类。
所以"看图"必须是独立工具：它的结果不只是文本，还有一张要挂到消息上的图。

**关键设计：把"工具结果里夹带图片"显式建模成一条旁路通道，而不是往文本里塞约定标记。**

```
read_image.Execute ──► imageCollector.add(Attachment)
                          │
工具循环（串行执行 tool_calls）──► 每次 ExecuteToolCtx 之后立刻 TakeImages()
                          │
                          ├─► ToolCall.Images（只存 ID，界面画缩略图）
                          └─► 该次工具结果消息的 Attachments（组装请求时读的是它）
```

- 不用"标记 + 解析"：那需要每个消费方都去解析标记，漏一处就静默丢图。
- **一次调用取一次**（`take` 而不是只读）：收集器是整个工具视图共用的，
  中间不取走就再也分不清哪张图是哪次调用产的。循环本就是串行执行 tool_calls 的，
  "执行一次取一次"因此能保证归因准确。
- 没有附件存储时 `read_image` **不注册**（`BuildOptions.Attachments == nil`）。
  注册一个"存不了图的存图工具"只会每次调用都失败，白耗模型一轮——
  这与 `spawn_agent` 在没有 spawner 时不注册是同一个手法。

**read_image 把工作区里的图复制成会话附件，而不是在发送时按路径去读**，理由有三：

1. 入站即规整：尺寸/格式在上限内统一，发送路径零转换。
2. **历史可回放**：工作区里的文件随时会被改掉、删掉或切分支。"当时模型看到的那张图"属于对话记录，
   应当与对话一起稳定存在；否则回看历史时模型对着一张已经不存在的图作答，人却无从察觉。
3. 作用域干净：附件目录是应用私有数据，不进 diff 归因，也不会因为用户回退一轮代码而"被回退"。
   反过来，若引用工作区路径，就还得决定"工作区外能不能读"——
   现在这个问题由权限层按路径统一回答（见 §4.7）。

代价是同一张图可能在工作区与附件目录各存一份。对"看几张图"这个量级可以接受。

## 3. 最终架构

### 3.1 数据流

```
用户粘贴/拖拽/选文件
   │  FileReader → base64
   ▼
App.SaveAttachment(会话ID, 文件名, base64, "user")
   │  DecodeUpload → normalizeImage（嗅探/解码/缩放/重编码）
   ▼
AttachmentStore.Save  ──►  ~/.local-agent/attachments/<会话ID>/<hash>.<ext>
   │  返回 Attachment 引用（id/宽高/媒体类型/字节数）
   ▼
appendMessage(role=user, content, attachments)  ──►  sessions/<会话ID>.json
   │
   │  发送消息
   ▼
buildRunMessages  ──►  buildLLMMessages(history, prompt, loader)
   │                        │  loader = AttachmentStore.LoadImages
   │                        ▼  每条消息的 Attachments → []LLMImage（读盘 + 组协议载荷）
   ▼
LLMReq.Messages
   ├─ json.Marshal → LLMMessage.MarshalJSON（有图 → content 块数组）→ OpenAI 兼容网关
   └─ toAnthropicRequest → appendAnthropicImages（→ image 块）/ tool_result 合并 → Anthropic 网关
```

工具侧的图走同一条后半段：

```
read_image.Execute ──► imageCollector ──► 工具结果消息的 Attachments ──► 同上
```

### 3.3 六条不变式

改这块代码前请先确认这几条还成立：

1. **会话 JSON 里没有图片字节，只有引用。** 一旦有人图省事把 base64 写进 `Message`，
   会话文件就从 KB 级变成 MB 级，且每次追加消息都要整体重写——性能会以"莫名其妙变慢"的形式暴露，
   很难定位到这里。
2. **`Message.Attachments → LLMImage` 只有一处实现**（`buildLLMMessages` 经由 `imageLoader`）。
   用户贴的图与工具读的图共用它，所以"怎么存"与"怎么发"不会各自漂移。
3. **工具结果的形状只有一个产出点**（`appendToolResultMessages`）。
   工具循环里"刚产生的这条"与下一轮"从会话重建的这条"必须逐字节一致。
4. **无图的 `LLMMessage` 序列化结果必须与加图片之前完全一致**（`MarshalJSON` 走 `plain` 分支）。
   请求快照、既有测试、各家网关都依赖这个形状。
5. **图读不出来必须留下痕迹。** 附件目录被清理、会话文件被手改、附件存储没装配，
   三种情况都要在消息文本里留一行说明，而不是静默少一张图——静默会让模型对着不存在的图瞎答。
6. **附件路径不来自前端。** 前端只给 `(会话ID, 附件ID)`，路径由后端推导；
   `Attachment.Path` 从会话文件读回时按"用户可改的输入"对待（`pathInside` 校验）。
7. **带图的消息必须同时带一个文本块**（正文为空时由 `textPartFor` 补一句占位）。
   纯图片消息（内容数组里只有 image 块）在真机上被证明读不到——而同一次对话里
   带说明文本的工具结果图能读到。缺了这个文本块，失败方式是"图静默不见了"，
   见 §6.4 与 `TestImageOnlyMessageCarriesTextPart`。

## 4. 接线点（逐文件）

### 4.1 会话消息（`sessions.go`）

```go
type Message struct {
    ID          string
    Role        string
    Content     string
    ToolCalls   []ToolCall
    ToolCallID  string
    CreatedAt   int64
    Attachments []Attachment `json:"attachments,omitempty"`
}

type ToolCall struct {
    ...
    Files  []string `json:"files,omitempty"`
    Images []string `json:"images,omitempty"` // 只存附件 ID
}
```

`ToolCall.Images` 只存 ID：字节与元数据的**唯一真源**是那条 tool 结果消息的 `Attachments`；
这里放 ID 只是为了让工具卡片能画出缩略图（tool 结果消息在前端是被过滤掉不展示的）。
两者在同一次工具执行里由同一个切片写出，不存在漂移。

**纯图片消息的标题兜底**：`titleSource(content, attachments)`——正文为空时用第一张附件的名字。
否则会话列表里会出现一行空白，用户认不出是哪个会话。

### 4.2 协议中立层（`chat.go`）

```go
type LLMImage struct {
    MediaType string
    Data      []byte
    Bytes     int  // 快照脱敏后仍要能显示"这里原本有一张多大的图"
    Width     int
    Height    int
    Redacted  bool
}
```

- `LLMImage.dataURL()` → OpenAI 形状（`data:<type>;base64,<...>`）。
- `appendAnthropicImages()` → Anthropic 形状（`media_type` 与裸 base64 分成两个字段）。
  两处形状差异都在适配器里吸收。
- `LLMMessage.MarshalJSON`：无图走 `plain(m)`（别名类型，避免递归），有图输出块数组。
- `imageLoader func([]Attachment) ([]LLMImage, []string)`：**第二返回值是失败说明**。
  走依赖注入而不是直接调 `AttachmentStore`，是为了让"图片读取失败"这类场景可被精确构造与断言。

### 4.3 Anthropic 适配（`anthropic.go`）

`toAnthropicRequest` 的 user 分支：文本块在前、图片块在后（与 Claude Code 的实际行为一致）；
判空条件从"内容为空"改成"正文与图片皆空"，否则**纯图片消息会被整条丢掉**。

### 4.4 上下文（`contextmgmt.go`）

- `imageTokens(w, h)`，计入 `messageTokens` / `storedMessageTokens`。
  不这么做的话，一张图能被"压缩省下 0 token"，而它实际占了三千多。
- `buildRunMessages(session, prompt, forceTruncate, loader)`：多了一个 `loader` 参数，
  一路上传给 `buildLLMMessages`。它必须是参数而不是去全局取——这一层要做的是"取哪几条消息"，
  取图的动作属于协议组装，到最后一刻才发生。
- `buildCompactTranscript`：图片**不进**摘要素材（摘要请求只发文本），但留下一行
  "（附带 N 张图片：名字（宽×高））"。被摘要覆盖之后那张图不会再出现在后续请求里，
  摘要若不记一笔，模型就完全不知道"用户曾给过一张图"——而用户后面完全可能问
  "刚才那张图里第三行是什么"。

### 4.5 请求快照（`requestlog.go`）

`redactMessages`：把图片换成 `Redacted` 占位（保留媒体类型与尺寸，丢掉字节）。
几 MB 的 base64 进快照之后，这份排障视图既没法读又占内存，
而排障真正需要的只是"这条消息带了几张多大的图"。
深浅拷贝的处理：切片是浅拷贝，但每条带图的消息都换成**新的** `Images` 切片，因此不改到调用方的数据。

前端 `RequestPreviewDialog.vue` 同步适配：带图消息的 `content` 是数组，
渲染前折叠成"文本 + `[图片] 图片已省略：…`"，避免出现 `[object Object]`；
并对 `data:` 开头的 URL 再做一层兜底截断。

### 4.6 附件存储（`attachments.go`）

```go
func NewAttachmentStore(root string) *AttachmentStore
func (s *AttachmentStore) Save(sessionID, name string, data []byte, source string) (*Attachment, error)
func (s *AttachmentStore) Load(att Attachment) ([]byte, error)          // 校验 Path 不越界
func (s *AttachmentStore) LoadImages(atts []Attachment) ([]LLMImage, []string) // 实现 imageLoader
func (s *AttachmentStore) DataURL(sessionID, id string) (string, error) // 只收 ID，不收路径
func (s *AttachmentStore) DeleteSession(sessionID string) error
func DecodeUpload(payload string) ([]byte, error)                       // base64 / data URL
```

- **nil 接收者是安全的**（`sessionDir`/`LoadImages` 都先判 nil）：测试里构造的 `App` 没有附件存储，
  生产链路漏传时给出的是可读说明而不是 panic。
- `DataURL` 只收 `(会话ID, 附件ID)`：拼路径这件事一旦交给调用方，就等于把"读任意文件"的能力
  开给了前端。它按 ID 在会话目录里 glob 查找，找不到就是文件确实丢了——
  那种情况必须能被区分出来（界面显示"图片已丢失"，而不是一个破图占位）。

### 4.7 权限

`read_image` 的判定主体是**路径类 + 读**（`pathSubjectFor`），因此：

- 落在只读默认放行里（不弹窗）；
- 但**不是**工具级放行——读工作区之外的图照样落到规则判定上；
- 敏感路径的内置模式（`.env`、`~/.ssh/`、`id_rsa` …）依然生效。

`read_image` 不写工作区（图写进附件目录），因此不产生 diff 归因，也不参与撤销。

### 4.8 前端

- **三个入口收敛到 `addFiles`**；本地态只存"未落盘"的这一批，贴错了直接删掉，
  后端不留任何垃圾文件。本地预览用 `URL.createObjectURL`，移除/卸载时 `revokeObjectURL`。
- **取粘贴内容必须同时看 `items` 与 `files`**，不能只读 `files`。
  Chromium 系粘贴图片时填 `files`；**macOS 上 Wails 用的是 WebKit（WKWebView），
  它经常只填 `items` 而 `files` 是空的**。只读 `files` 的写法在浏览器里好使、在真机上失效，
  而且失效方式很隐蔽（见 §6.4）：没被 `preventDefault`，浏览器接着执行默认粘贴，
  把剪贴板里的**文本表示（那张图的 URL）**插进输入框——用户以为图发出去了，
  模型却只看到一串链接。同理，`dragover`/`drop` 也走同一个 `imageFilesFrom`。
  另外"声称有图但拿不到字节"时也要 `preventDefault` 并明确提示，不能让那串 URL 溜进去。
- 发送顺序是**先落附件、再落消息**：消息里挂的引用因此一定是完整的，
  不会出现"消息已入库、图还在路上"这种读了会报错的中间态。
  单张上传失败不阻断整条消息（其余照发，失败的在通知里点名）。
- 纯图片消息允许发送（`"这张报错图怎么回事"`是常见开场）；
  计划模式带图时**明确提示并改走普通对话**——规划器是无工具的文本调用，图片到不了它那里，
  与其产出一份"看不见图"的计划，不如说明白。
- 历史消息的图按需向后端要，由 `stores/chat.js` 按 `${会话ID}:${附件ID}` 缓存
  （消息列表会因流式输出、滚动、工具卡片状态变化频繁重渲染，没有缓存就是每渲染一次要一次图）。
  `undefined`（加载中）/ `''`（取不到）**必须区分**，否则会先闪一下"图片已丢失"再变成图。
- 从链接抓来的图**在"添加"那一刻就已经落盘**，待发送队列里存的是 `attachment` 引用，
  发送时直接引用、不再上传一次；预览也直接用后端存下来的那一份
  （与模型看到的完全同一张图，不另存一份原始数据）。

### 4.9 从链接抓取（`imagefetch.go`）

有一类截图工具与内部控制台，复制图片时放进剪贴板的**不是图片字节，而是一条 URL**。
此时前端拿不到任何 `File`，"粘贴图片"从源头就不成立。所以补了一条显式入口：

```
「链接」按钮 → askText 收 URL（用户能看到完整地址）→ FetchImageURL → 与贴图同一条管线落盘
              → 直接进待发送队列（已落盘，发送时不再上传）
```

**安全边界，每条都是刻意的**：

| 约束 | 为什么 |
| --- | --- |
| 只由**用户点按**触发 | 它不是工具、不进工具注册表，模型无法触发——因此不存在"提示词注入骗本机去抓一个内网地址"的通路 |
| 只允许 http / https | `file://` 之类一旦放进来，这个接口就成了任意文件读取 |
| 重定向 ≤ 3 跳且**逐跳重新校验** | 只在入口校验一次的话，第一跳合法、第二跳换协议/换主机就绕过了 |
| 整体超时 + 响应体边读边限长 | 先 `ReadAll` 再判大小，等于让一个超大响应把内存吃掉 |
| 内容必须嗅探成受支持的图片 | 判断复用 `normalizeImage`，不另写一套；顺带排除"下回来一个 HTML 登录页"的情况 |
| **不按 IP 段拦内网** | 内部图床 / 日志平台几乎都在内网，拦掉内网会让这条链路在真实工作流里直接不可用。等价的安全边界是"用户看着完整 URL 点确认"——他本来也能在浏览器里打开它。要收紧只改 `assertFetchableURL` 一处 |

前端配套：粘贴时若剪贴板**只有链接、没有图片字节**，弹一条提示（**不拦**默认粘贴，
因为用户可能就是想发这个链接）并指向「链接」入口——把"静默地发了串 URL"变成"说清楚"。

## 5. 已知取舍与未做的事

1. **只支持 PNG / JPEG / GIF**：WebP 无标准库解码器，明确拒绝而不是静默透传（见 §2.3）。
2. **动图只看首帧**：超限的 GIF 会被解码为首帧再编码成 PNG；
   未超限的 GIF 原样透传（仍是动图），但视觉模型本来也只读首帧。
3. **同一张图可能存两份**（工作区 + 附件目录）：`read_image` 复制而非引用，换历史可回放。
4. **没有附件配额与 LRU 回收**：目前只在删会话时级联清理。
   长期重度使用会积累体积，需要时再加"按会话总量/最后访问时间清理"。
5. **每次组装请求都要重读并 base64 编码历史里的每一张图**：
   一次请求几毫秒，换来"只有一个转换点"。加缓存是后续优化项
   （按附件 ID 缓存 base64，注意设容量上限）。
6. **压缩后旧图不再发给模型**，摘要里只留一行"曾附带 N 张图片"。
   这是设计内行为（省 token 的主要来源），但意味着模型不能"回头再看一眼那张图"。
7. **计划模式不支持图片**（规划器无工具、纯文本）。
8. **`allowed-tools` 与图片无关**，但注意技能机制里那条既有的未完成项
   （`allowed-tools` 未接入权限网关）不受本次改动影响。
9. **「从链接添加」是一条出站网络能力**（§4.9）。它刻意只由用户点按触发、不做自动抓取，
   但"不拦内网地址"是个有意的取舍：拦掉内网就等于放弃内部图床/日志平台的使用场景。
   代价是——若用户被诱导粘贴并确认一个内网地址，本机会真的去请求它，并把结果交给模型。
   要收紧只改 `assertFetchableURL` 一处（加私网/回环判断即可）。
10. **从链接添加的图若被用户从待发送队列里删掉，附件会留在磁盘上**（没有"删除单个附件"的接口）。
   它不可见、且会在删除会话时一并清掉；要彻底解决需要一个 `DeleteAttachment` 接口。

`out` 是 `encodeImage` 返回的 `[]byte`，被当成了图像。已改为取**被编码的那张图**的

### 6.4 真机反馈：粘贴图片变成了一串 URL（2026-09-26）

现象：在真机上粘贴一张图，模型回"我看到用户发了一张图片，但我无法直接访问该 URL"。
产物时间线先排除了"前端没重建"（`frontend/dist` 与 wails 绑定都在改动之后重建过），
问题在粘贴处理本身。

**根因**：`handlePaste` 只读了 `clipboardData.files`。macOS 上 Wails 跑在 WKWebView 里，
粘贴图片时 WebKit 经常**只填 `items`、`files` 为空**，于是代码判定"这不是图片粘贴"，
既没取到图、也没 `preventDefault`；浏览器的默认粘贴行为接着执行，把剪贴板里的
**文本表示（那张图的 URL）**插进了输入框。整条链路上没有任何一环报错——
它是"静默地做成了另一件事"，最难查的一类失败。

**修法**：`imageFilesFrom(dt)` 同时读 `items`（`kind === 'file'` → `getAsFile()`）与 `files`；
粘贴时只要有图就 `preventDefault`；"声称有图但取不到字节"时也 `preventDefault`
并提示用户另存为文件。拖拽走同一个函数。

**顺带补了系统提示词**：明确告诉模型"图片会作为图像内容直接出现；如果只看到图片 URL，
说明图没传进来，你没有抓取外部链接的能力，不要声称能下载/查看、也不要花轮次尝试"。
原来的提示词对此完全沉默，模型于是自己编了一条"让我尝试通过工具下载"的路，白耗一轮。

**另一条可选的后续**：让后端直接抓取图片 URL（用户贴链接也能看图）。
这需要新开一条"出站抓取任意 URL"的能力，涉及安全边界（内网地址、超大响应、重定向），
属于独立决策，本次没做——现在的行为是把话说清楚，让用户改用粘贴或工作区路径。

**补充（同日后半）：确实做了，但做成了显式入口。** 用户第二次反馈同一现象，
且链接形如 `https://maas-log-prod…`（内部平台），我当时据此判断
"剪贴板里只有链接、没有图片字节"，于是加了 §4.9 的「链接」入口。

**但这个前提后来被证伪**：用户回答"粘贴后出现的是一个**图片缩略图/预览条**"，
即前端确实拿到了图。所以「链接」入口不是这次故障的解法（对"只有链接"那种情况仍有用）。

**（第三次逼近，也是真正定位）根因：纯图片消息缺一个文本块。**

第二个反馈给出了**决定性对照**——同一次对话里：

| 消息 | content 数组 | 模型能看到 |
| --- | --- | --- |
| 用户粘贴的图 | `[图片块]` ← **没有文本块** | ❌ |
| `read_image` 工具结果的图 | `[说明文本, 图片块]` | ✅ |

而"38 字符"正是这条推断的**算术证明**：那句占位文案
`[图片] 图片已省略：1518×1074，image/jpeg，300 KB` 恰好 38 个字符；
若消息里有任何正文，长度会是 `正文长度 + 1 + 38`。也就是说那条消息的
content 数组里**只有图片块**。

**修法**：`textPartFor(content, images)` —— 带图但正文为空时补一句
`（用户发来一张图片，没有附加文字）`。两条协议共用这一条规则
（OpenAI 侧 `MarshalJSON`、Anthropic 侧 `toAnthropicRequest`），
回归测试 `TestImageOnlyMessageCarriesTextPart` 把它钉住。
补的那句话写成有信息量的一句而不是空串：模型由此知道"用户只发了图"，不至于反过来猜。

**顺带纠正提示词里一句错话**：原来写的是"你没有抓取外部链接的能力，不要花轮次尝试下载"——
而 `exec_shell` 就在工具列表里、`curl` 真能跑通，模型也确实去下载了。
它下的是链接里那张**旧图**，于是用户看到的现象是"它描述的图片不是我最新上传的那张"。
已改成：先说清"有图就直接看、不要再下载"，再承认"只有链接时可以用 curl 下载到工作区
再用 read_image 看，但那未必是用户这次想给你看的那张，动手前先确认一句"。
**把能力说清楚并给出边界，比说一句不成立的话有效。**

> **诚实标注**：上面那条"缺文本块"的结论，证据是"38 字符"的算术（它只证明**我的应用
> 发出的**那条消息没有文本块）加上"工具图能看 / 用户图不能看"的对照。
> 这两条都成立，但**都还没有证明文本块就是模型看不到图的原因**——修复本身无害且值得做
> （多一个文本块对两条协议都合法），但我不能声称它就是根因。
> 判定根因要靠 `/vision`：它测的正是应用现在真正使用的形状（文本 + 图），
> 所以它与真实链路同形，通过与否直接回答"端点能不能看图"。

**复盘：这一轮我错了三次。** 先归因"剪贴板没有图片字节"（改了前端），
再归因"图没传进来"（去加日志），然后归因"端点不支持看图"（加了 /vision）——
三次都是在**证据不足时下结论**。真正破局的不是推理，而是两组**对照**：
"38 字符"给出的算术，和"工具图能看 / 用户图不能看"的差异。
**拿两个只差一处的样本比一比，比对着现象设想原因快得多。**

**第四次逼近：模型自述"收到的图片只以 URL 形式出现"。**

模型在承认自己描述有误时给出了关键自述：

> 我实际接收到的内容中，图片仍然只以 URL 链接的形式出现，我并没有真正"看到"图像的像素内容

它还报出了"**RGBA 格式**"——这个细节我的 `read_image` 返回文本里**没有**
（我返回的只有名字、尺寸、媒体类型与 KB 数）。RGBA 只可能来自它自己跑命令
（`file` / `ls`）看下载到工作区那个文件的元数据。也就是说：
**工具结果里的文字它看得到，图像内容看不到。**

这与"网关把多模态内容压成文本"一致，也解释了最早那句"我无法直接访问该 URL"。

**但模型的自述不能当判据**——这场故障里它编过一次（把历史里的链接说成"用户发的 URL"）。
所以这一轮不再根据它下结论，而是把它变成可测的：

- `/vision` 增加**纯文本对照组**（先确认端点本身通不通）。只有对照组通过、图像探针失败，
  结论才能干净地落在"端点不接受图像"上；否则可能是鉴权/网络/模型名的问题（用「测试连接」排除）。
- 新增 `logAnthropicImageShape`：带图的请求在**出站时**打印实际形状
  （消息数 / 内容块数 / 图像块数 / 首个图像的 media 与 base64 长度）。
  必要性在于：`「请求」对话框展示的是内部中立格式`，Anthropic 侧还会再转一次
  （图片变成 `source` 块），转换出问题时对话框里看不出来。
- `/vision` 的报告开头写明"用的是**自动生成的合成测试图**，与用户发过的任何图片无关"。
  原因是模型把上一次自检的结论（"红绿蓝三个竖条"）当成了用户那张截图的内容——
  自检结果留在历史里，会把后来的判断带偏。

**待验**：`/vision` 的两条探针分别是什么结果。对照组通过 + 图像探针未通过 ⇒ 换端点，
代码侧无待办；两条都通过 ⇒ 端点没问题，要回到「请求」快照继续查。

---

### 6.5 收口：`/vision` 实测结果 —— 根因是端点能力（2026-09-26）

```
看图能力自检（用的是自动生成的合成测试图，与用户发过的任何图片无关）
模型：glm-5.2-discount
1）纯文本对照：通过
2）文本 + 图：未通过 ❌   它的回答是「无法回答」
```

**结论**：端点**能通文本、但不把图像交给模型**（`glm-5.2-discount` 是文本模型）。
本应用的图片链路——剪贴板 → 落盘 → 读回 → 组装请求 → 出站——已由**「请求」快照**
（那条消息带 `[图片] 图片已省略：…`）与**纯文本对照组**双重证明是正确的。
要能看图，需要换一个支持视觉的端点；换完用 `/vision` 一测即知。

**这一轮最后做的事：不让模型继续误导人。** 既然结论可测，就把它落盘
（`~/.local-agent/vision-check.json`）并在下一个请求里用上：

- `visionverdict.go`：`VisionVerdictStore` 按模型名记住"测过且未通过"。
  **"没测过"与"测过且未通过"必须区分**——前者不该影响任何行为。
  结论还**与端点绑定**（同时记下当时的 ModelID 与 URL）：用户很可能换了端点却沿用同一个
  配置名（把 `glm-5.2-discount` 的 URL 改指向一个视觉模型），那时旧结论必须自动失效——
  否则它会继续告诉模型"你看不到图"，**在用户刚修好的时候说反话比不说更糟**。
  配套的 `modelCallID()` 收口了"ModelID 为空则回落到配置名"这一条口径：
  写入与读取各写一份的话，只要一边漏了，键就对不上，表现为"测过了但警告永远不出现"。
- `runToolLoop`：检测到 `ar.VisionUnsupported` 就给系统提示词补一段
  （`visionUnsupportedNote`），明说"你很可能收不到图像内容，直接如实说明，
  **不要**去 curl 下载、不要编造图片内容、也不要让用户另存文件"。
  这三种行为在真机上都出现过，每一种都让用户更难排查。
  这不修复端点（能力改不了），但把它从"静默地乱试"变成"一句话说清"。

**关于 `textPartFor`（纯图片消息补文本块）**：保留，但**它不是本故障的根因**——
根因是端点能力。补文本块对两条协议都是更保守的写法、成本为零，所以留着；
但文档不能把"我们改了 X"讲成"X 就是原因"。

**这一轮的完整教训**（值得单独记）：
1. 现象相同、原因不同的路径很长时（剪贴板 → 存 → 读 → 组装 → 出站 → 网关 → 模型），
   **不要对着现象猜原因**；先想办法把中间状态变成可读的（快照、日志、对照探针）。
2. **对照比推理有效**：两个只差一处的样本（工具图 vs 用户图、纯文本 vs 带图）比一比，
   比设想原因快得多。
3. 自检要**成对设计**：只有"图像探针"失败时，你分不清是端点坏了还是不支持图；
   加一个纯文本对照组，结论才干净。
4. 结论要**落盘并回灌**：测出来的事实不拿去改行为，等于白测。
