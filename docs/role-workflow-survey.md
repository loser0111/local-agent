# 角色化工作流：现有方案调研与 local-agent 落地映射

> 需求原型:预定义若干角色(产品 / 前端 / 后端 / QA),指定一条工作流,让一个任务从「问题提出」走到「上线」。
>
> 本文分三部分:**① 现有方案盘点**(四类)、**② 一个必须先知道的反方观点**、**③ 逐条映射到 local-agent**。
>
> 材料来自公开资料检索(2026-09),标注了「已核实(读了本项目代码)」与「据公开资料」的区别。

---

## 0. 结论先行

1. **这个形态不新,而且已经卷过一轮。** 最贴近你描述的是 MetaGPT / ChatDev 的「虚拟软件公司」和 BMAD-METHOD 的「角色 + 阶段产物」。**但它们共同的教训是:`角色划分` 本身不产生价值,`阶段产物` 才产生价值。** 角色只是"用哪份提示词 + 用哪些工具"的打包方式;真正让流程跑通的是每一阶段留下能传给下一阶段的**文档**(需求 → 设计 → 任务 → 代码 → 测试报告)。

2. **local-agent 已经有一半积木了,而且缺的不是"角色"这一块。** 技能(SKILL.md)已经有 frontmatter 形状(name / description / allowed-tools),计划(Plan)已经有串行步骤 + 状态 + 摘要。真正缺的是三样:**步骤与角色的绑定**、**产物作为一等公民**、**角色专属工具集真正生效**。

3. **最该先想清楚的不是"怎么定义角色",而是"允不允许两个角色同时写代码"。** 这是这条路线上唯一会造成数据损坏的坑(见 §2),而 local-agent 当前的 diff 归因是全局单基线,恰好踩在这个坑上。

## 1. 现有方案盘点

### 1.1 开源多代理框架

| 方案 | 形态 | 可借鉴的点 | 对你的适用性 |
|---|---|---|---|
| **MetaGPT** | 模拟软件公司:PM / 架构师 / 项目经理 / 工程师 / QA,用 SOP 串起来,产出从需求文档到代码 | **角色之间交接的是文档而不是对话**;每个角色有固定的产出物模板 | 形态最贴近,但研究导向、偏 demo;它的价值在于"给每个角色规定死产出格式"这一点 |
| **ChatDev** | 虚拟软件公司,CEO/CTO/程序员/评审/测试,靠多轮对话推进 | 评审角色独立于实现角色 | 同样偏研究;对话式推进的可控性差 |
| **CrewAI** | `Agent(role, goal, backstory)` + `Task` + `Crew`(顺序 / 层级流程) | **角色是显式数据结构**;流程模式只有"顺序"和"层级"两种,刻意不做复杂图 | 它的角色定义形状适合直接抄成配置;但要 Python 生态 |
| **LangGraph** | 图编排,有 supervisor / hierarchical / handoff 几种官方模式 | **supervisor 模式**:由 LLM 决定下一个交给谁,取代硬编码路由;**状态持久化**是它被反复强调的核心价值 | 它强调的"状态不能蒸发"正是你 `Plan` 已经在做的事 |
| **AutoGen (Microsoft)** | 对话式多代理,GroupChat + 发言选择策略 | 发言顺序策略可以交给模型决定 | 偏研究/实验 |
| **OpenAI Agents SDK** | 原语是 agents / **handoffs** / guardrails / tracing;2026-04 加了原生沙箱、sub-agents | **handoff 让子代理直接与用户对话**,而不是事事回编排者——省一层转发延迟 | 若只接 OpenAI 生态可考虑 |
| **Google ADK** | 2.0 起有**图式工作流** + A2A 协议;Python/TS/Go/Java 都有 | **Go 版本存在**——这是唯一和你技术栈同语言的主流选择 | 值得单独看一眼 |

**这一类里最值得抄的两条设计**:

- **CrewAI 的角色是数据,不是代码。** `role / goal / backstory` 三个字符串加工具列表就是一个角色,不需要写类。你的 SKILL.md frontmatter 已经非常接近这个形状。
- **LangGraph 反复强调的是状态持久化,不是编排能力。** 多代理系统真正的难点是"上下文别蒸发",而不是"能不能画图"。你已经有 `Plan` 落盘 + 步骤摘要,起点比多数人好。

### 1.2 商业产品与 IDE 内置

| 方案 | 角色机制 |
|---|---|
| **Claude Code subagents** | `.claude/agents/*.md`,frontmatter 就是 `name` / `description` / `tools` / `model`,**正文即系统提示词**;由主代理按 description 自动委派;支持顺序、并行、嵌套 |
| **Roo Code** | 内置 Architect(只读)/ Code / Debug / Ask / **Orchestrator** 五种模式,**每个模式可以记住各自的模型**;支持自定义模式和"boomerang 任务"(Orchestrator 把活扔给别的模式再收回来) |
| **Cline** | 更简单:只有 Plan / Act 两态,每步要用户批准 |
| **AWS Kiro** | 不是角色制,而是**规格驱动**:`requirements.md` → `design.md` → `tasks.md` → 实现;另有 Agent Hooks(文件事件触发的后台工作流)与 steering rules(强约束代码风格/架构) |
| **Devin / Copilot cloud agent / Factory** | 单代理为主,读 issue → 规划 → 改代码 → 提 PR;**产品化的是"从 issue 到 PR"这条链路**,不是角色划分。Copilot 的 agent 还会自己修 CI 失败再交 PR |
| **Devin Desktop(原 Windsurf)** | 用 ACP 协议把 Devin / Codex / Claude Code 并排放在一个界面里,**共享代码库上下文**——注意它是"多个工具并存",不是"多个角色协作" |

**这一类里最值得抄的两条**:

- **Claude Code 的角色定义形状**:一个 markdown 文件,frontmatter 里 `tools` 是**窄名单**(官方明确说"只给真正需要的"),`model` 可为该角色单独指定。**"窄工具集"是角色定义里最有实质意义的一栏**——它同时是安全边界和成本控制手段。
- **Roo Code 的 Orchestrator 模式**:它的价值不在"多角色",而在**每个模式可以绑定不同的模型**。让 Architect 用推理强的贵模型、Code 用快的便宜模型,这是角色化最直接的收益之一。

### 1.3 方法论型方案

**BMAD-METHOD**(Breakthrough Method for Agile AI-Driven Development)是这一类里最完整的,而且它明确支持你要的全流程:

- 角色:分析师 / 产品经理 / UX / 架构师 / Scrum Master / 开发 / QA / 技术文档 / **Orchestrator**
- 阶段:分析 → 规划 → 方案设计 → 实现
- **刻意前置**:大量设计发生在写第一行代码之前
- 每阶段产出物喂给下一阶段;**Full Method**(大改动)与 **Quick Flow**(小改动)两条路径

**GitHub Spec Kit** 用五个 slash command 把同一件事做成了工具链:
`/speckit.constitution`(不可违背的项目原则)→ `/speckit.specify`(spec.md)→ `/speckit.plan`(plan.md)→ `/speckit.tasks`(tasks.md)→ `/speckit.implement`。另有 `/speckit.clarify`、`/speckit.analyze` 做阶段间质检。

**这一类里最值得抄的两条**:

- **"两档路径"**:大改动走全流程,小改动走快捷通道。**没有这一条,角色工作流会在第一个小需求上就被用户抛弃**——因为跑一遍五个角色的成本远大于改一行代码。BMAD 把它做成了显式的两条路径,而不是让用户自己判断。
- **`constitution`(不可违背的原则)**:它是一个**跨所有角色共享的约束文件**。这解决了一个真问题:五个角色各写各的,风格和架构决策会互相打架——见 §2。

### 1.4 纯 prompt 编排套路

不以代理框架为单元,直接写提示词/规则:

- **spec-driven development**:把 spec 当作"可执行的合约",代码偏离 spec 就算构建失败
- **角色卡片**:把角色的职责、输入、输出格式、禁止事项写成一段固定模板,贴在会话开头
- **steering rules / project rules**(Kiro、Cursor):一组始终注入的约束,等价于你系统提示词里那几个 `##` 段

**这一类的价值在于它指出了最常见的错误做法**:很多人以为"角色"就是"换个称呼",于是写出「你现在是一个资深前端工程师」这种一句话人设。**有效的角色定义必须包含四样:输入是什么、输出格式是什么、能用哪些工具、什么事不许做。** 前两样才是协作真正依赖的东西。

## 2. 一个必须先知道的反方观点

这条路线上最重要的反方材料是 Cognition(Devin 团队)的 **"Don't Build Multi-Agents"**,以及它后来的修正:

- 原始立场:把任务拆给并行子代理**很脆弱**。原因是上下文没有充分共享,各代理的决策"局部合理、全局冲突"。核心论据是 **"actions carry implicit decisions"**——一个代理改了代码,就隐含地对风格、边界情况、代码模式做了选择,而另一个代理会做出不同选择,两边一叠加就碎片化。
- 修正后的立场:并行**写**仍然不行,但还是能用的形态是——**写保持单线程,额外的代理只提供"智力"而不直接动手**。原文举的例子是"干净上下文的评审者抓 bug"和"一个聪明朋友指出你没想到的细节"。
- Anthropic 那边的经验是"orchestrator-worker"(主管派研究员并行搜集),效果显著——**但那是在广度优先的检索/调研场景**,它的收益来自"多个独立上下文窗口 + 并行探索",不是来自"角色分工"。

**对 local-agent 的直接含义有三条:**

1. **不要让两个角色同时改同一份代码。** 你的 diff 归因是**全局单基线**——多会话并行改同一仓库时,"同一次改动可能被两边窗口同时归因",你自己在注释里标了"已知取舍,偏向多算"。在多角色场景下这不是显示问题,而是**归因错乱**:回退一个角色的改动会连带影响另一个角色。真要并行,先给 diff 归因加仓库级锁或改成按会话前缀扫描。

2. **角色化最稳妥的落点是"读"和"评审",不是"写"。** 产品、架构、QA 这三个角色天然是读者和评审者;前端、后端是写者。**把写者限制成同一时刻只有一个**,是这条路线能跑通的前提。

3. **共享约束比你想象的更重要。** 多角色最容易出现的问题是"五个角色各自做局部决定,合起来不一致"。BMAD 用 `constitution` 解决,你的对应物是**跨角色共享的项目级约束文件**(可以挂在项目级记忆或一个固定的 system prompt 段里)。

## 3. 映射到 local-agent

### 3.1 已有的积木(已核实,读了代码)

| 积木 | 现在能做到 | 离"角色"差什么 |
|---|---|---|
| **技能 SKILL.md** | frontmatter 有 `name` / `description` / `allowed-tools` / `disable-model-invocation` / `user-invocable`;正文按需加载;`scripts/` 用 exec_shell 跑 | **`allowed-tools` 只用于展示与路由控制,没有接入权限执行**——也就是说它现在是"声明"而不是"约束"。这是角色化最关键的缺口。 |
| **子代理** | `runSubagent(parentRun, parent, dir, model, task, maxTurns)`:独立会话、独立上下文、结论回传(截断 4096 字符)、禁止嵌套 | **没有角色概念**:模型/权限/工具全部继承父会话,系统提示词是固定的 `buildSubagentPrompt(dir)`。它是"上下文隔离机制",不是"角色机制"。 |
| **计划** | `Plan` 落盘 + `[]*PlanStep`(标题/要点/状态/摘要/错误/起止时间),串行执行,`awaiting_approval` 状态已存在,执行中把进度注入系统提示词 | **步骤不能指定角色/模型/工具集**;步骤之间**只有摘要字符串**这一种交接方式。 |
| **权限** | 规则引擎 + 询问回路 + 三层配置 + 按路径/命令逐段判定 | 不缺,而且比多数开源框架强——**角色化时它是现成的工具集收窄手段**。 |
| **记忆** | L1 索引常驻 + L2 按轮召回 + 跨会话 | 可以承载"共享约束/项目宪法"的角色。 |

### 3.2 直接可复用(不用改)

- **角色定义的数据形状**:SKILL.md 的 frontmatter 已经是 `name / description / allowed-tools`——和 Claude Code 的 subagent 定义几乎同构。**角色不需要一个新文件格式**,把技能扩展一点就能当角色用。
- **`awaiting_approval` 这个状态**:BMAD / spec-kit 强调的"每阶段人工确认后再往下",你的计划已经有这个状态位了。
- **步骤摘要**:它已经是"产物交接"的雏形,只是太薄(一个字符串,没有结构、没有落盘成独立文件)。
- **权限引擎**:一旦 `allowed-tools` 接进权限执行,角色的"窄工具集"就是现成的。

### 3.3 需要改造(改动不大,但是关键路径)

1. **把 `allowed-tools` 从声明变成约束。** 技能/角色声明的工具白名单要真正作用到工具视图装配上(`BuildOptions.EnabledTools` 已有这个能力,只是没从技能那边传)。**不做这一步,"角色"就只是一段提示词,没有任何约束力。**

2. **角色与技能的合并或分层。** 现在技能是"按需加载的知识包",角色是"长期在场的职责"。两者都靠 SKILL.md 的形状,但生命周期不同。**建议不要合并**,而是让角色**引用**技能:角色定义里写 `skills: [...]`,角色在整条工作流里始终在场,技能按需加载。

3. **计划步骤增加"角色"与"产出物"两个字段。** `PlanStep` 加 `Role string` 和 `Artifacts []string`(产出文件的路径)。执行某一步时:用该角色的系统提示词 + 该角色的工具集 + 把前置步骤的产出物**文件内容**注入,而不是只塞一句摘要。

4. **产物落盘为一等公民。** 角色之间交接的应该是**文件**(`docs/prd.md`、`docs/design.md`、`tasks.md`、测试报告),而不是上下文里的字符串。这一点 MetaGPT / BMAD / spec-kit 三个方案是一致的——它们不约而同地把"阶段产出文档"当作流程的骨架。而且落盘还顺带解决了上下文预算问题:下一个角色按需读文件,而不是全文注入。

### 3.4 真正的缺口(需要新写)

| 缺口 | 为什么必要 | 难度 |
|---|---|---|
| **步骤 → 角色的绑定与调度** | 现在计划步骤是"同一个代理接着做下一步",没有角色切换 | 中。要动 `executePlan` 的循环和 `buildPlanSystemPrompt` |
| **产物作为一等公民**(声明、落盘、校验、注入) | 不看文件、只看摘要的话,下游角色拿不到足够信息,会重复劳动或跑偏 | 中 |
| **共享约束(项目宪法)** | 防止五个角色各自做局部决定、合起来不一致 | 低。一个始终注入的提示词段 + 落盘位置 |
| **两档路径**(全流程 / 快捷通道) | 没有它,工作流会在第一个小需求上被抛弃 | 低。规划器多一个判断,或用户显式选择 |
| **多写者的串行化保证** | §2 的第 1 条;不做的话并行角色会破坏 diff 归因 | 高。要改 diff 归因的全局基线 |

### 3.5 建议的分期

**第一期(最小可用,能验证核心假设):**

- 角色 = 一个带 `role: true` 的 SKILL.md(复用现有解析,只加一个字段),内含系统提示词正文 + 工具白名单 + 可选模型
- `allowed-tools` 接入工具视图装配(**这是第一期唯一必须动的执行层改动**)
- 计划步骤加 `Role` 字段;执行时按角色装配 `agentRun`
- 人工卡点复用已有的 `awaiting_approval`

**验证点**:同一个任务,分别用「单代理直做」和「产品 → 研发 → QA 三角色」跑一遍,**产出的代码质量与总 token 成本对比**。如果三角色的质量没有明显更好而成本明显更高,这条路线的价值假设就不成立——这是最该先验的事,而不是先把五种角色都定义出来。

**第二期:** 产物落盘 + 步骤间按文件交接 + 共享约束文件 + 两档路径。

**第三期:** 多角色并行的读侧(多个角色同时评审)、并行写者与 diff 归因的改造。**这一期风险最高,建议放到最后**。

## 4. 一句话总结

你要的形态在业界叫「角色 + SOP + 阶段产物」,方案很多(MetaGPT / BMAD / spec-kit 是最接近的),但它们的共同经验是**价值来自阶段产物和人工卡点,不来自角色数量**。local-agent 的独特优势是**权限引擎和 diff 归因已经存在**——这两样恰恰是"多个角色同时动手"最容易出事的地方,而多数开源框架在这一层是空的。所以这条路线对你来说,难点不在"怎么定义角色",而在"**允不允许并行写**",以及"**把 `allowed-tools` 从声明变成真的约束**"。
